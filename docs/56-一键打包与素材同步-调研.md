## 3. 问题 1 · 「一键打包」到底打包什么

### ① 事实

| 事实 | 三态 | 出处 |
| --- | --- | --- |
| 库目录与记录靠 `id` + `relFolder` 对齐；`Asset.id` 是 UUID 稳定主键（改名/改库/改大类不变），`relFolder` 是 posix 相对库根 | `【查证】` | `types.ts:254`/`:262-263` |
| `folder` 是**绝对路径**（机器相关），不能跨机原样带；跨机必须靠 `relFolder` 现算 | `【查证】` | `types.ts:260-263`；`importer.ts:318-337`（路径不一致的历史 bug） |
| 索引/标记在 Dexie，导入后若**只带目录不带记录**，rescan 会生成新 UUID、用户标记全丢 | `【查证】` | `rescan.ts:138`（生成新 UUID、按 folder 命中沿用旧 id）；`db.ts:113-117` |
| 现有插件快照契约已定义「资产记录 → 紧凑 JSON」字段子集（`apiVersion:"1"`、只增不删），可复用思路 | `【查证】` | `docs/39 §3.2`；`pluginSnapshot.ts:97-132` |

### ② 可选形态

| 形态 | 打包内容 | 跨机对账方式 |
| --- | --- | --- |
| **A1 只带素材目录** | 按 `relFolder` 原样铺开 + 一个极简 `manifest.json`（版本/条数/校验和） | 目标机全量 rescan，靠目录结构重建记录；**UUID 与标记全丢** |
| **A2 目录 + 索引快照**（推荐） | `manifest.json` + `index.json`（Asset 记录的可移植字段子集）+ 素材目录 | 导入时按 `id` 命中已有记录、按 `relFolder` 落盘，恢复标记；需处理冲突（§6） |
| **A3 只带索引快照** | `index.json` 不含素材 | 不可独立使用，只能做「清单备份」；不作为打包形态 |
| **格式** | (i) 单文件 zip（≤4 GB 受 FAT32/exFAT 限制 & 内存压力）｜(ii) **zip 分卷**（推荐）｜(iii) 目录 + 清单不打 zip | 分卷便于网盘/U 盘搬运、断点续传；目录形态最省事但不便于单文件搬运 |

### ③ 推荐

**A2 + zip 分卷**：`manifest.json`（`apiVersion` / 导出版本 / `libraryRoot` 原值仅留档 / `generatedAt` / `count` / `indexSha256`）+ `index.json`（`id`/`relFolder`/`kind`/`category1/2`/`source`/`files[]`/`size`/`cover`/`favorite`/`rating`/`colorTag`/`styles`/`renderParams` 等可移植字段；**去掉 `folder` 绝对路径**）+ 素材目录按 `relFolder` 原样；分卷大小按用户拍板（Q-4）。

### ④ 理由 / 代价

- `【查证】` 只带目录必然丢 UUID 与标记（`rescan.ts:138`），而 `Asset.id` 是「唯一锚点」（`docs/38 §7`），所以**必须带索引快照**。
- `【查证】` `folder` 绝对路径跨机无效（`types.ts:260`），清单里必须换成 `relFolder` 现算。
- `【推断】` 复用 `docs/39 §3.2` 的紧凑 JSON 字段子集思路可少定一套 schema；但本包是**换机迁移**，字段范围比插件快照大（要含标记/词表），不能直接照抄。
- `【推断】` 分卷带来「缺一卷整包不可用」的风险 → 清单里放每卷 SHA256（复用现有 SHA256 口径 `docs/39 §3.1`），导入前先验完整性。

## 4. 问题 2 · 「自动检测哪些需要提取 / 不需要提取」的真实歧义

### ① 事实

| 读法 | 含义 | 支持证据 |
| --- | --- | --- |
| **① 打包时挑选** | 导出端自动挑「值得带走」的资产（已分类 / 有封面 / 最近用 / 非回收站），跳过垃圾 | 【推断】用户说「这个包里面哪些东西是需要提取的」——「包」可指整个库 |
| **② 导入时识别** | 目标机导入时自动识别包结构，只提需要的内容（按清单跳过缓存/隐藏目录） | 【推断】用户说「自动检测这个包里面哪些东西是需要提取的，哪些是不需要提取的」——「包」可指导出的那个包 |

`【查证】` 用户原话只出现一次「包」，两种读法都讲得通；**PM 不替用户定死**，并列进 §10 Q-2。

### ② 可选形态

| 形态 | 做什么 | 与现有能力关系 |
| --- | --- | --- |
| **① 导出端筛选** | 打包时按规则过滤：`.trash` / `.idbox` 不带（实测 0.36 GB + 隐藏目录），未分类可勾选是否带 | `【查证】` `.trash` 是软删保留区、`.idbox` 是内部目录（§2.1 实测） |
| **② 导入端识别** | 导入时读 `manifest.json`，只按 `index.json` 的 `files[]` 提需要的文件；跳过 thumbs / 球图 / hdr-cache 等可再生缓存 | `【查证】` 缓存目录在 userData 不在库（`settings.json` 实测）；库内 `cover`/`thumb` 文件命中数见 §2.1 |
| **③ 两头都做** | 导出筛选 + 导入识别 | 成本最高、最可控 |

### ③ 推荐

**② 导入端识别为主、① 导出端只做最小过滤**：导出端只排除 `.trash` / `.idbox`（明确垃圾），其余原样带；导入端严格按清单 `files[]` 提取，遇到清单外文件一律跳过。

### ④ 理由 / 代价

- `【查证】` 用户核心痛点是「扔进家里电脑后要能用」，导入端识别直接决定能否对上；导出端「智能挑选」容易误删用户想带的东西。
- `【推断】` 「最近用 / 有封面」这类筛选规则需要新增判据与 UI，且会引入「用户不知道哪些没被带走」的信任问题 —— 与数据敏感画像冲突。
- `【待核实】` 用户是否真的想要「挑着带」（可能只是担心把缓存/垃圾一起带走）⇒ Q-2 直接问。

## 5. 问题 3 · 三种方案对比（A 本地包 / B 网盘直连 / C 第三方同步工具）

### ① 事实

| 方案 | 已有事实 | 出处 |
| --- | --- | --- |
| **A 本地包手动搬运** | 已有保存对话框 + zip 导出范式（日志 zip / rbz / 索引备份）；`importPaths` 已是统一导入通道 | `main/index.ts:2103`/`:2172`/`:2576`；`ipc.ts:7` |
| **B 网盘直连** | 主程序当前零网络依赖（README「不收集遥测，不上传任何素材或路径」）；百度/阿里云盘开放 API 口径**查不到稳定承诺** | `README.md:350`；`【待核实】`（本轮只读源码与 docs，未做网盘 API 检索） |
| **C 第三方同步工具** | 用户有绿联 NAS 背景（team-lead 转述）；早期 PRD 曾判 NAS 同步不做（单机前提） | `docs/01:363`/`:546`；team-lead 派工背景 `【查证】` |

### ② 可选形态（六维对比）

| 维度 | A 本地包 | B 网盘直连 | C 第三方同步工具（Syncthing / NAS） |
| --- | --- | --- | --- |
| 实现成本 | **低**：复用对话框 + zip + 清单校验 | **高**：账号/OAuth/API 适配/限流，且 API 不稳定 `【待核实】` | **低**：ID BOX 只需把库目录放在同步文件夹；不做新功能 |
| 隐私 | **最好**：文件不过第三方、不经账号 | **差**：素材路径与内容上云，与数据敏感冲突 | **中**：文件经用户自有 NAS / P2P，不经我们；但 NAS 厂商可见 |
| 容量 | 受单文件/U盘/网盘限额；可分片 | 受网盘配额；14 GB 单次上传耗时大 | 受 NAS 容量；增量同步友好 |
| 增量同步 | **无**（全量包） | 可做但要自己实现增量协议 | **天然有**（工具负责） |
| 离线优先 | **不破坏** | **破坏**（必须联网） | 不破坏（局域网/本地同步） |
| 用户身份边界 | 无账号、用户自控 | 需网盘账号，暴露身份 | 需 NAS 账号，但用户自有 |

### ③ 推荐

**A 为本版本调研后的首选形态**；C 作为「不写代码的替代路径」明确告知用户（把库目录放进 Syncthing/NAS 同步文件夹即可，ID BOX 只读取同一目录）；**B 不推荐**，且不承诺任何网盘 API。

### ④ 理由 / 代价

- `【查证】` A 的三个零件（保存对话框 / zip / `importPaths`）都已存在（`main/index.ts:2103/:2576`、`ipc.ts:7`）；B 三者皆无。
- `【推断】` 用户「数据敏感、本地优先」画像与 B 直接冲突（`README.md:350` 逐字「不收集遥测，不上传任何素材或路径」）。
- `【推断】` C 的代价是**索引与磁盘的一致性**：两个机器同时写库目录、各自 Dexie 独立，容易对不上（§6）——但至少不破坏离线优先。
- `【待核实】` 用户是否接受「C 方案下 ID BOX 不参与同步、只做读取」；这决定要不要做 A。

## 6. 问题 4 · 增量与冲突

### ① 事实

| 事实 | 三态 | 出处 |
| --- | --- | --- |
| `Asset.id` 是稳定主键，导入按 `folder` 命中已有记录时沿用旧 id | `【查证】` | `types.ts:254`；`rescan.ts:138` |
| 判重键 `dedupeKeyOf(name, kind)` = `kind:名称归一化`；同名包会走 `uniqueName()` 加 `-2` 后缀 | `【查证】` | `naming.ts:330`、`:283` |
| 软删走 `.trash/`，有保留期；恢复/彻底删有独立流程 | `【查证】` | §2.1 实测 `.trash`；`README.md:24` |
| 非原子双写已被识别为风险（分类指派等），项目已有串行写队列与事务收口 | `【查证】` | `docs/16:12-18`；`settings.ts:227-230` |

### ② 可选形态

| 冲突类型 | 形态 a（全量覆盖） | 形态 b（按 id 合并） | 形态 c（只导入不回写） |
| --- | --- | --- | --- |
| 同名资产 | 目标机整库被替换 | 同 `id` 用较新 `updatedAt`；不同 `id` 同名按判重键转 `-2` | 只在目标机追加新记录 |
| 已删除资产 | 源端删了 → 目标机也删 | 墓碑机制（谁后删谁生效） | 目标机保留（删除不跨机同步） |
| 分类改派 | 源端分类覆盖目标机 | 按 `updatedAt` 取新 | 目标机保留自己的分类 |
| 标记（收藏/评分） | 被覆盖 | 并集（任一为真则真） | 目标机保留 |

### ③ 推荐

**最小可行版本只做「全量导出 + 全量导入」（形态 a 的受控版 + c 的保守规则）**，明确**不做双向同步、不做自动合并**：导入时要求目标机是空库或用户显式确认覆盖，冲突一律弹窗让用户选，不静默合并。

### ④ 理由 / 代价

- `【查证】` 判重键与 UUID 规则已存在（`naming.ts:330`、`types.ts:254`），但「双向合并」需要墓碑 / 时间戳 / 冲突解决三层新机制，项目现状没有（`db.ts:113-117` 三表无同步字段）。
- `【推断】` 用户场景是「一次打包扔进家机」，属于**单向拷贝**，不是持续同步 —— 全量导出/导入已满足 80% 价值。
- `【推断】` 静默合并会违背「用户对自己库有完全控制权」的画像；宁可多问一句。

## 7. 问题 5 · 体积与性能

### ① 事实

`【查证】` 真实库 **13.935 GB / 743 文件**，HDRI 独占 10.218 GB（73%）、`.trash` 0.361 GB（§2.1 实测）。`【查证】` 现有 zip 导出（日志 / rbz）规模远小于此（`main/index.ts:2576`/`:2172`）。`【待核实】` 20 GB+ 库、单文件 >4 GB（exFAT/FAT32 限制）、网盘单文件上限均未实测/未查。

### ② 可选形态

| 形态 | 做法 | 代价 |
| --- | --- | --- |
| 单文件 zip | 一个包 | 14 GB 单文件对 U 盘格式/网盘上传都不友好；内存与耗时风险 |
| **zip 分卷**（推荐） | 按 Q-4 拍板大小切卷 + 每卷 SHA256 | 缺一卷整包不可用；需断点续导 |
| 目录 + 清单 | 不打 zip，直接拷目录 | 最省 CPU；但不便单文件传输、无完整性校验 |

### ③ 推荐

**分卷 + 进度 + 断点续导**：导出按卷写（流式，不整包进内存）、显示进度与剩余时间；导入验每卷 SHA256、支持从中断处续。分卷大小默认给选项让用户拍（Q-4），不写死。

### ④ 理由 / 代价

- `【推断】` 14 GB 量级一次性读进内存不可接受，必须流式；分卷天然支持流式与分批搬运。
- `【推断】` HDRI 是体积大头，若用户愿意「先不带 HDRI」，包可降到 ~3.7 GB —— 这是 Q-2（挑选口径）的实际价值所在，但**必须由用户决定**，PM 不预设。
- `【待核实】` 真机导出 14 GB 的耗时 / 磁盘 IO 峰值需 QA 阶段实测，本调研不编造数字。
