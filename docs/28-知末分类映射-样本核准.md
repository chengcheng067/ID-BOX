### 1.2 采样口径（逐条可核对）

1. **遍历**：`E:/ModVault/Library` 下的 `模型` / `材质` / `HDRI` 三个大类，递归找**含文件的最深目录** = 一条资产。只 `readdir` / `stat`，**不写库**。
   - 库现状：212 个目录 / 737 个文件 → **130 条叶子资产**。
2. **本地分类**：由目录路径取 `[大类, 一级, 二级]`，即 `模型/灯具/壁灯/<资产名>` → 本地 `灯具/壁灯`。
3. **知末 ID**：与 `src/shared/naming.ts: zhimoIdFromText()` **同一条口径**（脚本是 `.mjs`，正则逐条复制，改口径时两处必须同步）：
   - ① `ID_<6位以上数字>`（含 `ID-` / `id 1234567` / `…ID_1166965084_resize`）；
   - ② `znzmo-<6位以上数字>`（包内文件名 `znzmo-1180221079-1.skp`）；
   - ③ 裸 9–10 位数字（左右不能是数字）。
   - 结果：**59 条有 ID**，其中 23 条来自资产名、36 条来自包内文件名。
4. **站方分类**：`https://su.znzmo.com/sumoxing/{ID}.html` → `__NEXT_DATA__` → `props.pageProps.res.classifyBaseName`；同时取 `pageProps.breadcrumb_data[].showName` 作为**站方父链**（用来判断站方自己的层级，避免按名字猜语义）。
   - 可行性依据：`docs/23` 已实测「无需登录、无签名、无 cookie、WAF 常规 GET 不触发」。
   - 结果：**58/59 成功**；失败 1 条是 **ID 1146900274**（`无缝白色肌理漆…涂料…`），详情页 HTTP 200 但 `classifyBaseName` 为空 —— 如实记为「站方没给」。
5. **不做的判断**：脚本**不写 category、不猜分类**，只记录「站方说什么 + 本地现在是什么」。

**局限（必须如实说）**：

1. 这是**单库单机**的 130 条，不是全站随机抽样；样本偏「灯具/壁灯」（15 条）与 HDRI（33 条）。

4. 表里资产名超过 44 字会截断显示（`…`），完整名以脚本输出为准。
5. 站方数据自身有错挂：样本 ID 1146709125 的父链是 `灯具 > 植物 > 乔木`（植物挂在灯具下），本表按名字落到 `植物/乔木` 并在代码里留了 note。

## 6. 结构性发现（会影响接线设计）

1. **`classifyBaseName` 是「最深节点」而不是「二级」**：58 条里大量三级名（茶柜/餐椅/办公椅/餐厅吊灯/餐桌椅/庭院小品/镜子/茶具/食物饮料/窗帘）。
   → 落库前必须做「三级 → 本地二级」的归并，本表已经做了（每行带 `stationPath` 可复核）。
2. **站方二级轴与本地二级轴不是同一套**：
   - 软装陈设：站方 `墙饰墙绘` / `布艺软饰` / `摆件`；本地 `挂画` / `窗帘布艺` / `摆件` / `花艺` …
   - 厨卫五金：站方 `厨房用品`；本地没有这一层。
   - 贴图：站方 `木纹 > 木材`（木材是二级），本地 `木纹` 和 `木材` 是**两个一级**。
   → **不能把站方父链直接写成本地目录**，只能取「最深名字 → 本地两级」。
3. **站方词表比本地宽**：本次实测到 **8 个本地没有直接同名的站方名字**（夹胶玻璃/红砖/金属网格/海洋板/水泥墙/茶具/食物饮料/植物组合）。
   其中 2 个能按**站方父链**落到本地已有二级（海洋板 → 木材/板材、水泥墙 → 墙面地面屋面/水泥），
   `木纹` 走一级-only，剩下 6 个按用户拍板走**就近归并**（`approx:true`，§5.3）—— 6 条都能靠站方原话 + 资产 ID 重新取回并重映射。
4. **同名跨频道 10 组**（§5.1）。
   → 贴图与材质落盘同属「材质」容器，**单靠分类名无法区分**；2026-10-26 已拍板**把 `kind` 传给映射函数按大类分流**（见 §5.1）。
5. **本地有些一级名同时是另一个一级下的二级**：`玻璃` / `金属` / `石材` / `木材` / `皮革` / `涂料` 都是 `模型/SU材质` 的二级。
   → 以这些**一级名本身**作为站方分类名（如 `玻璃`/`金属`）时**不能**按一级-only 处理（会与 `SU材质/玻璃` 二义）→ null。
   → 但 `夹胶玻璃 → 玻璃` 是**以站方父链的一级做近似**（带 `approx:true` + `level:1`），按用户"就近归并"裁定返回，并在 `approxReason` 里写明上述二义；两者不是同一件事。
6. **近似归并必须可回溯**：`ZHIMO_APPROX` 每条都带 `stationName` / `approxReason` / `source`；
   落库侧看到 `approx:true` 要单独打日志，纠正时按该标记一次性筛出。规则**不在** importer/store 里。
7. **本地库里有词表外的旧值**：`模型/家具/椅子`（词表是 `椅子/凳子`）、`模型/软装陈设/窗帘布艺` 以外的 `SU材质/布艺` 等，都是历史自动分类留下的。
   → 本次不清理（不写库）；接「自动落库」时需要决定是否顺带纠正存量。

  `大理石 / 高光木纹 / 工字拼木地板 / 方形地毯 / 棉布 / 金 / 打孔皮革 / 透明玻璃 / 高光塑料 / 高光陶瓷 / 乳胶漆 / 地坪漆 / 花草 / 小区景观 / 瓷砖 / 路面 / 自然水 / 压纹皮革 / 水晶`
- **发现 `docs/18` 的 106 条不是材质树全集**（采集深度限制），并新增两条**只记录、不映射**的缺口：

  | 站方名 | 站方父链 | 为什么没有安全落点 |
  | --- | --- | --- |
  | `墙砖` | `石材 > 墙砖 > 其他石材`（三级） | 本地石材组没有「墙砖」；归 `砖材/外墙砖` 属**用途猜测**（墙砖也可能是内墙/装饰砖），按纪律不做 |
  | `玻璃屏幕` | `玻璃 > 玻璃屏幕 > 其他玻璃`（三级） | 本地玻璃组没有「玻璃屏幕」；`玻璃幕墙` 是建筑构件、与"屏幕"不是一回事，不能互替 |

  → 材质树也有第三层；`docs/18` 与 `docs/07 §5.11` 一样是"两级抄录"，全覆盖需补抄第三级（走 `docs/06 §12.2`）。
  → 这两个名字**不是站方一级名**，也不适用一级-only；正确做法就是保持 `null`，等补抄录。
- **材质侧也存在"一级名即最深"**：`涂料`、`石材` 直接作为 `classifyBaseName` 出现（与模型侧 `木纹` 同类现象）。
  但它们在本地**同时是 `模型/SU材质` 的二级**（二义）→ 按既有纪律仍返回 `null`，没有硬凑一级-only。
- **`木板` 已补齐**：父链 `木材 > 板材`，与 `海洋板`（→ 木材/板材）同父链，2026-10-26 收尾时按同一口径补成
  **两级精确落点**（`mapZhimoCategory('木板','texture')` → `{木材, 板材}`；source = 库内实测 ID 1153222981）。
- **采样方法警告**：站方分类页列表**混了推荐商品** —— 40 条里有 8 条的详情分类 ≠ 所在二级页
  （`墙纸`页出`墙砖`、`人物皮肤`页出`瓷砖/路面`、`蔬菜`页出`压纹皮革/涂料`、`书籍报刊`页出`玻璃屏幕/石材`）。
  → 读 `classifyBaseName` 必须以**详情页自己**为准，不能拿"从哪个分类页点进来"当分类标签。

### 9.4 本节局限（如实写）

1. 站方侧只覆盖 **20 个一级各 1 个二级页**（每页前 2 个商品），不是随机抽样，也未覆盖其余 86 个二级；
2. 用户库材质资产共 40 个叶子目录，只有 **25 个有知末 ID**（其余是本地自制/无 ID），24 条可读；
3. 采样期间用户库仍在变动（新增了 5 个材质资产），本节的 40/25 是**采样时刻**的快照；
4. 未对材质频道做风格/属性采样（不在本次范围）。

> 结论：`docs/18` 的材质二级**方向正确、逐项可用**（19 项实测全中，kind 分流后无冲突）；
> 但它**不是全集**（至少缺 `墙砖` / `玻璃屏幕` 这类更深层名字），且详情页分类可能与浏览入口不一致。
> 这两点必须在接线前写进落库侧的前提，不能当成"材质树已 100% 掌握"。
