## 3. 反馈 3 · 材质大类合并

### 拍板

**升为属性，保住二级精度**：

- 落盘大类目录合并为 `材质/`，四层不变：`材质/<一级>/<二级>/<资产>`。
- `贴图` / `材质预设` 降为 `kind` 属性值（Dexie 保留 `texture` / `material`），**筛选器仍可单独筛**。
- 一级分类 = 贴图 21 项 ∪ 材质 21 项，**9 个同名合并**（石材 / 木材 / 木地板 / 地毯 / 金属 / 皮革 / 玻璃 / 涂料 / 外景），共 **33 项**。

### 迁移窗口

用户库 `E:/ModVault/Library` 当前只有 **7 个资产**：

```
模型/挂画/未分类、模型/未分类/未分类
贴图/木纹/未分类、贴图/砖材/仿古砖、贴图/未分类/未分类
```

现在迁移最便宜，越晚越贵。

### 关键约束

- `LEVEL2_MAP` 原先「键全局唯一」，9 个同名一级会撞键 → 必须升级为按大类嵌套或频道前缀（v1.0.3 已写成显式不变式，正是为此预留）。
- `Asset.id = relFolder` → 目录改名即主键变化 → Dexie 主键不可原地改，要走「事务内删旧建新」。
- 迁移必须**幂等 + 可回滚**（manifest 记录），同目录下的同名一级要 merge 而非覆盖。

## 10. 后续决策记录

### 10.1 语义兜底：embedding + kNN（已定方向，暂不实施）

- **2026-10-20 用户拍板**：将来做本地语义兜底，走 **60MB 级 embedding + kNN**，**不内置 1B/2B 生成模型**。
- **暂不实施**，等用户把当前版本的实际 bug 体验完再排。
- 触发条件：库规模上到几百个资产、且积累了用户手动改分类的真实标注样本。
- 否决生成模型的理由（写进决策，避免以后重新讨论）：
  1. 体积：1B-Q4 约 600–700MB，是当前整包（81.8MB）的 8 倍；2B 约 1.2–1.4GB。
  2. **模型救不了「词表里没有目标类目」**（诊断里 P3/P5 共 12.5%：屏风、花瓶、射灯）——模型只能归到已有类目。
  3. 生成模型会瞎编类目，必须靠强校验闸门补救；embedding+kNN 天然只能返回已有类目。
  4. 无标注数据可训：用户库里资产数量不足以训练，用词表合成训练数据等于让模型背词表。
- 候选实现：`bge-small-zh-v1.5` int8 ONNX（约 24–30MB）+ `onnxruntime-node`（约 30MB）；把资产名与 375 个二级词条分别向量化，最近邻取分类；阈值可用用户改分类的记录校准。
