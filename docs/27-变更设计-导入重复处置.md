# 27 · 变更设计：导入重复处置（跳过 / 覆盖 / 同时存在并重命名）

- 版本基线：0.6.9（`package.json:3`）
- 状态：设计稿（**只写文档，不含任何源码改动**）
- 关联：`docs/22`（0.6 范围）、`docs/24`（知末 ID）、`src/renderer/logic/duplicates.ts`（既有「重复资产」视图口径）

需求原话：

> 「再增加一个功能：用户拖入的文件包内如果有内容和我们现在已经存在本地库的文件有重复的情况，弹窗告知用户素材可能重复，让用户选择跳过、覆盖，或者是二者同时存在并重命名。」

## §1 判重口径

### 1.1 复用既有基础设施（不另造一套）

| 能力 | 位置 | 本次怎么用 |
|---|---|---|
| `dedupeKeyOf(name, kind)` | `src/shared/naming.ts:330` | 新素材用**原始资产名**（`uniqueName()` 之前）算 key；库里记录直接用已存的 `dedupeKey` |
| `baseNameOf(name)` | `naming.ts:313` | 快照条目 `dedupeKey` 缺失时（极老数据）兜底重算 |
| `zhimoIdFromSources(archiveName, assetName, fileRels)` | `naming.ts:241` | 新素材算知末 ID，**调用点从「落盘后」提前到「落盘前」**（理由见 §1.3） |
| 「重复资产」视图的 `keyOf()` | `duplicates.ts:59` | 判重语义必须与它对齐，否则「导入时说没重复、进库后出现在重复视图」自相矛盾 |

### 1.2 判定流程（每条源文件）

```
资产名 assetName = 现有逻辑（importer.ts:322-324 / :577）
kind      = primaryKind(files)（importer.ts:325）/ 调用方给定（单图 = texture、HDR = hdri）
zhimoId   = zhimoIdFromSources(itemName, assetName, files.map(f=>f.rel))
dedupeKey = dedupeKeyOf(assetName, kind)

① zhimoId 非空 且 快照里存在同 zhimoId 的条目      → 冲突 reason='zhimo-id'，候选 = 这些条目
② 否则 dedupeKey 命中快照（快照条目 dedupeKey 为空则用 baseNameOf(name)+kind 现场算）
                                                  → 冲突 reason='same-name'，候选 = 这些条目
③ 双方都有 zhimoId 但值不同                        → **不冲突**（D02），直接走正常导入
④ 都不命中                                        → 不冲突
```

命中多个候选时（库里同一 key 已有 2 份以上）：

- 弹窗只展示 **`importedAt` 最早的一份** 作为「库内已有」（与重复视图「最早导入 = 原件」一致，`duplicates.ts:98-101`）；
- 其余份数记进 `existing.otherCopies`，弹窗显示「该素材库里本来就有 N 份」；
- **覆盖只处置这一份**，其余份一根手指都不碰（避免一次覆盖误删用户还没清理的历史副本）。

### 1.3 为什么 `zhimoId` 必须在落盘前算

现状 `importer.ts:456` 的调用点在 `moveDir()`（:360）与 `uniqueName()`（:358）**之后**，用的是 `finalName`。本次判定发生在移动之前，必须提前计算；且**应该用 `assetName`（原始名）而非 `finalName`**：

- `finalName` 可能带 `-2` 后缀，而 `zhimoIdFromSources` 的裸数字规则（`naming.ts:78`）对 `名字ID_1234567890-2` 仍然取得到 ID（`rightmostMatch` 取最右），但用痕迹更干净的原始名更稳；
- 这同时消除了「第二条同 ID 素材因为 `finalName` 变形而取不到 ID」的历史隐患。

`Asset.zhimoId` 落库时仍按「新包解析值 ?? 旧值」写（见 §3.2.3）。

### 1.4 内容哈希：本轮不做（明确结论）

**不做**，理由按优先级：

1. **判据不匹配**：真实重复的主要来源是「同一件知末商品被下过两次」，名字被下载器改成 `xxxID_1234567890` 或 `znzmo-1234567890-1`，**ID 恰好是最稳的判据**（`naming.ts:241` 的三来源已经覆盖）。用户真正需要的「改了个名的同款」已被 `zhimoId` 命中。
2. **成本不可接受**：要拿内容哈希做判重，必须**为全库预计算**（950 个资产、GB 级模型/贴图）→ 需要 Dexie 新版本 + 一次性全量 IO（用户升级后首次启动长时间卡顿），而增量补算只能覆盖「从今往后导入的包」。
3. **与解压争 IO**：单包可能 GB 级，主进程算哈希会与 7z 解压、缩略图生成抢磁盘，直接反噬导入速度（`DEFAULT_CONCURRENCY = 3`，`importer.ts:39`）。
4. **收益只剩窄缝**：仅覆盖「内容相同 + 名字不同 + 无 ID + 大小恰好相同」这一小类；这类场景用 D05 的体积提示 + 弹窗里的「大小 / 导入时间」足够让用户判断。

下轮候选写法（不在本轮）：**只对新导入包算 xxHash64（流式、<5% 时间开销），库内按需懒补**，`Asset.contentHash?` 非索引字段。已记入 §7。

### 1.5 与「库内回灌守卫」的关系

`isInsideLibraryDir()`（`importer.ts:169`）在**进并发链路之前**就剔除库内路径（`importer.ts:189-200`），优先级高于判重。本次不改它：拖进来的东西如果本来就在库里，连 staging 都不建，与「重复」是两件事。

## §2 交互形态

### 2.1 结论：整批聚合、一次弹窗，顶部批次默认档 + 每行可覆盖

```
┌──────────────────────────────────────────────────────────────────────┐
│  发现 3 个可能重复的素材                                       [✕]  │
│  还有 7 个包正在检查；若也有重复，将按下方「其余重复项」处理          │
├──────────────────────────────────────────────────────────────────────┤
│  其余重复项按此处理：  [ 跳过 ] [ 覆盖 ] [ 保留两者 ]   ← 批次默认档  │
├──────────────────────────────────────────────────────────────────────┤
│ ☐ 卧室双人床.skp.rar                             同名素材 · 486 MB   │
│   库内已有：卧室双人床   家具/卧室   2026-09-12   512 MB ⚠ 体积差 5% │
│   处置：[跳过] [覆盖] [保留两者]                                     │
├──────────────────────────────────────────────────────────────────────┤
│ ☐ 现代壁灯ID_1232108421.rar                  同一件素材(ID) · 42 MB │
│   库内已有：现代壁灯     灯具/吊灯   2026-10-02   42 MB              │
│   处置：[跳过] [覆盖] [保留两者]                                     │
├──────────────────────────────────────────────────────────────────────┤
│ ☐ 灰水泥贴图.zip                                 同名素材 · 1.2 GB  │
│   库内已有：灰水泥贴图   材质/混凝土  2026-08-30  610 MB ⚠ 体积差 97% │
│   处置：[跳过] [覆盖] [保留两者]                                     │
├──────────────────────────────────────────────────────────────────────┤
│  跳过 = 不导入，原文件保留在原位。 覆盖 = 用新内容替换库里那份，       │
│  旧版本进系统回收站（需清空回收站才真正释放空间）。                    │
│                                            [ 全部取消 ]  [ 确定 ]    │
└──────────────────────────────────────────────────────────────────────┘
```

要点：

- **顶部三档 = 批次默认档**，标签写「其余重复项按此处理」，默认选中**跳过**（最安全，见 §4.4）。点顶部任意一档 = 把下面所有行都设为该档（方便「这批全部覆盖」）。
- 每行三个小按钮可单独改，改完行内高亮。行内被单独指定后，顶部再点只会改「跟随批次默认」的行 —— 简化实现：**顶部点击 = 覆盖所有行**，这是用户显式动作，不存在误伤（弹窗内容全部可见）。
- 「同一件素材(ID)」vs「同名素材」是两种强度的标签，让用户知道该不该信。
- `⚠ 体积差 N%` 只在 `sizeMismatch` 时出现（D05），文案照抄重复视图的口径「可能不是同一套资产」。
- 底部两行小字是**必读语义**（尤其"需清空回收站才真正释放空间"，见 §3.2.2）。
- `[全部取消]` = `cancelled:true`，等价于全部「跳过」。

### 2.2 为什么是聚合而不是 per-item

| 理由 | 说明 |
|---|---|
| 批次是 20 包（`docs/22` G1），并发 3 | per-item 弹窗会连弹 N 次，且并发导致**弹出顺序与用户预期不符** |
| 用户是在做一次决定 | 「这次拖进来的东西要不要重复保留」是一个策略问题，逐条问等于让用户重复回答同一个问题 20 次 |
| 可比较 | 聚合后能一次看到全部条目，判断"这批都是同一套图的两个版本"比逐条看更准 |
| 不阻塞不冲突的项 | 弹窗期间其余包继续导入（非冲突项不受影响），进度条不会停 |

### 2.3 提示时机：解压之后、落盘之前

最早的可行时机是**解压完成**（资产名来自解压内容的顶层目录，`importer.ts:307-324`；单图路径则直接用文件名，`importer.ts:577`），最晚必须早于 `mkdir`（`importer.ts:349-350` / `:595-596`）。

**不做「解压前预判」**：只用压缩包名里的 ID 预判确实能省一次解压，但那时拿不到 `kind` / 大小 / 文件清单，弹窗信息不全，且会造成「同一个包有时先问有时后问」的不一致。成本：用户选「跳过」的包已经解压过一次（解压是 IO 成本，不是用户等待成本 —— 弹窗本来就是要等的）。

等待期间该条状态用既有 `status:'organizing'` + `message:'检测到重复素材，等待你的选择…'`（`ImportEvent.message` 已存在，`types.ts:364`；`ImportQueue.tsx:112-119` 直接渲染 message）。**不新增"等待中"状态**。

## §3 三种处置的精确语义

### 3.1 跳过（skip）

| 维度 | 语义 |
|---|---|
| 新内容 | staging 在 `finally` 中清掉（`importer.ts:511-518`），**不移动任何东西进库** |
| 磁盘 | 不 mkdir / 不 makedir 分类目录：判定发生在 `mkdir(cat2Dir)` **之前**（`importer.ts:349`），因此连空分类目录都不会产生 |
| **原压缩包 / 原图** | **绝不处置**。`disposeArchive()` 一次都不调用（`importer.ts:501-507`、`:716-720` 不动）；不管 `archiveDisposal` 是 `recycle` / `delete` / `keep`，一律**视同 keep** |
| 索引 | 不产生 `Asset`、不写 Dexie、不产生 done 事件 |
| 事件 | `deps.emit({ status:'skipped', message:'已跳过重复素材（原文件保留在原位）', conflict:{...} })` |
| 结果 notice | 批次结束后底部 toast：`已跳过 N 个重复素材，原文件保留在原位`；明细在导入队列里逐条可见（`status='skipped'` + 文案） |

**为什么原包一律 keep**：用户选「跳过」= 这次导入**没发生过**。此时若按 `delete` 档删包，等于「拒绝导入还把用户唯一的安装包删了」——库里那份可能被改过、可能是 720p 版本，包才是完整原件。另外 `docs/22` 的 `archiveDisposal` 语义是「**导入成功后**处置原包」，跳过不满足前置条件。这条是硬约束，实现里不允许出现「跳过分支里顺手调 dispose」的写法。

### 3.2 覆盖（overwrite）

#### 3.2.1 位置与身份：原位替换

| 字段 | 覆盖后取值 | 理由 |
|---|---|---|
| `id` | **沿用旧 id** | `Asset.id` 是稳定主键（`types.ts:261`「永不因改名/改库目录/改大类而变」）。沿用后渲染层的 `db.assets.put()` 天然是「替换同一行」，不需要 delete+put，也不会丢字段（`store.ts:1306`） |
| `name` | **旧名** | 用户认知里"这件资产"就是这个名字；新包名可能是下载器加工后的 `xxxID_123` 噪声 |
| `category1/2`、`folder`、`relFolder` | **旧值**（旧分类为双哨兵时才用新包预分类，见 3.2.3） | 用户手工指派过的分类是最贵的信息（`assignCategory` 会真搬目录） |
| `files` / `size` / `cover` / `coverSource` / `thumbPath` / `thumbStatus` / `suVersion` / `suMajor` / `mojibake` / `materialMeta` | **新值**（新包的） | 这些是内容派生量，必须跟着内容走 |
| `zhimoId` | 新包解析值 `??` 旧值 | 只增不减：新包能解析出 ID 而旧记录没有 → 补上（0.6.3 的封面抓取依赖它） |
| `dedupeKey` | 重算 `dedupeKeyOf(旧 name, 新 kind)` | 因为 name 不变，结果与旧值相同；重算只是为了自洽 |
| `importedAt` | 新时间 | 覆盖后这份就是"当前的"；重复视图里它变成最新 |
| `updatedAt` | 新时间 | — |
| `favorite` / `rating` / `colorTag` / `tags` / `styles` / `note` | **旧值** | 用户元数据，见 3.2.3 |

**「同 ID 不同名」与「同名同 ID」两种输入都收敛到同一条路径**：因为选择保留旧名与旧分类，目标路径**恒等于** `existing.folder`。这就是「覆盖 = 原位替换」，不存在"路径可能同名也可能不同名"的分叉——分叉被设计消除了。

#### 3.2.2 旧内容去哪：系统回收站

旧资产目录 `existing.folder` → `trashOne(existing.folder, strategy)`（`src/main/trash.ts:40`，即 `shell.trashItem` 优先 + `trash` 包兜底）。

**为什么不用库内 `.trash`**：

- 库内回收区的**可见性由 Dexie 驱动**：`deletedAt` / `trashRel` 写在资产记录上，UI 的「最近删除」按这两个字段列表。覆盖复用了同一个 id 的记录，无法同时表达「旧目录在回收区、新内容在原位」；
- 绕开它去写一条孤儿 meta（`trash.ts:251`）会造出「回收区里有、UI 里看不到、只能靠超容量清理才会消失」的隐形占用，比直接进系统回收站更糟。

代价必须写进弹窗文案（§2.1）：**进系统回收站后，磁盘空间要等用户清空回收站才真正释放**。这跟 `docs/20 §4`（「删除 ≠ 立刻省空间」是同一批用户认知问题，见该文 :109）是同一套说法，不新造概念。

#### 3.2.3 用户元数据继承

```ts
// 覆盖记录元数据的唯一实现（importer 内私有一处）
const inherit = existing.meta                      // 来自渲染层快照，见 §4.2
const keepCategory = !(inherit.category1 === UNCLASSIFIED && inherit.category2 === UNCLASSIFIED)
asset = {
  ...newAsset,
  id: existing.id,
  name: existing.name,
  category1: keepCategory ? inherit.category1 : newAsset.category1,
  category2: keepCategory ? inherit.category2 : newAsset.category2,
  favorite: inherit.favorite,
  rating: inherit.rating,
  colorTag: inherit.colorTag,
  tags: inherit.tags,
  styles: inherit.styles,
  // 空串不覆盖：HDR 的全景参数写在 note 里，新包没写就保留旧值
  note: inherit.note || newAsset.note,
  zhimoId: newAsset.zhimoId ?? existing.zhimoId,
  dedupeKey: dedupeKeyOf(existing.name, newAsset.kind)
}
```

> 标记：本节与 §3.2.4 里的 `existing` 指**快照条目** `ImportDedupeEntry`（带 `folder` / `meta`），不是弹窗载荷里的 `ImportConflictExisting`（那是给 UI 看的瘦投影）。执行覆盖时用的是前者。

- **双哨兵判定**（`未分类/未分类`）：说明用户从没指派过分类，此时新包可能命中词表（`classifyAssetName`，`importer.ts:340-344`）→ 用新结论，属于纯增益。
- 旧分类非空 → **一律保留**，即使新包能预分类出更"对"的类别。理由是用户手工意志 > 词表猜测（`docs/06 §9.1` 词表只是建议）。
- 备注 `note` 全量覆盖继承（HDR 的全景参数写在 note 里，`importer.ts:673` —— 若旧资产是 HDR 而新包的 note 为空，继承旧值才不丢信息）。实现上取 `inherit.note || newAsset.note`（空串不算覆盖）。

#### 3.2.4 三步执行顺序（先立后破 → 同路径时改为「先挪后立再破」）

目标路径被旧目录占着，`fs.rename` 无法覆盖非空目录，所以：

```
1. 挪旧： rename(existing.folder → sibling 临时名 .idbox-old-<id>[-<ts>])
           （同父目录，同盘 O(1)；`.` 开头 → rescan 天然跳过，rescan.ts:54-56）
   │  失败 → 直接报错，磁盘零改动，本条导入失败（staging 照常清理）
2. 落新： moveDir(contentRoot → existing.folder)
   │  失败 → rename 临时名回 existing.folder（回滚），本条导入失败
3. 销毁旧： trashOne(临时名)
   │  失败 → 不回滚（新内容已就位、数据正确），保留临时目录 + logWarn +
   │          该条 done 事件的 message 追加「旧版本未能移入回收站，已暂存为 .idbox-old-*」
```

要点：

- 第 1 步先 `pathExists(临时名)`，存在则加 `-<Date.now()>` 后缀（崩溃残留兜底）；
- 第 3 步失败**绝不** `fs.rm` 兜底（那是永久删除用户数据，超出"覆盖"的授权）；
- 临时目录名用 `.` 开头有两个好处：rescan/watcher 全部跳过（`rescan.ts:54`、`watcher.ts:18-25`），且不会出现在任何视图里。

**退化分支（不满足原位替换的前提时）**：

| 前提不成立 | 处置 |
|---|---|
| `existing.folder` 在磁盘上已不存在（用户手工删了/移走了） | 退化为**正常导入**（用新名/新分类/新路径），`id` 仍沿用旧 id（覆盖陈旧记录） |
| `existing.folder` 不在库目录内（快照脏数据） | 同上退化，并 `logWarn('import:conflict:folder-outside')`（安全：绝不对库外路径动手） |
| 新包 `kind` 与旧记录 `kind` 不同 | 同上退化（四层路径的顶层是大类目录，kind 变了路径必然变） |
| 覆盖执行中 `trashOne` 不可用 | 第 3 步的降级，见上 |

退化分支必须以 `status:'done'` + `message:'已覆盖（原目录已不存在，按新素材落盘）'` 上报，不能静默。

#### 3.2.5 缩略图与球图缓存

沿用旧 id → `ensureThumb(id, newCoverAbs)` 的缓存文件名含「封面路径 + mtime + 字节数」盐（`src/main/thumb.ts:71-77`），新内容必然换新文件名，**不会出现 Chromium 缓存旧图**。旧文件名成为孤儿，由既有 `pruneThumbs(liveIds)`（`preload/index.ts:112`）清理，本次不写额外删除逻辑。

### 3.3 同时存在并重命名（keep-both）

| 维度 | 语义 |
|---|---|
| 行为 | **就是现状**：`uniqueName(assetName, taken)` → `名字-2`（`importer.ts:358` 压缩包 / `:607` 单图） |
| 名字 | **纯自动**，弹窗里不给输入框 |
| `dedupeKey` | 必须用 `uniqueName()` 之前的 `assetName`（`importer.ts:492-495`、`:705-706` 的既有注释），本次不改 |
| 新 id | 新 UUID（与旧资产并存） |
| 原包 | 按 `archiveDisposal` 正常处置（导入成功） |

**不给自定义名的理由**：① 弹窗里打字成本高，且用户此刻还没看到新素材长什么样；② 并发 3 下用户输入的名字大概率也被占用，还得再弹一次冲突，体验更差；③ 现有重命名链路完整（`RenameDialog` + `IPC.renameAsset`，`preload/index.ts:73`），导入后改是 3 秒的事。

### 3.4 三档对照表

| | 跳过 | 覆盖 | 同时存在并重命名 |
|---|---|---|---|
| 新内容 | 丢弃（staging 清理） | 写入 `existing.folder` | 写入新目录 `名字-N` |
| 旧目录 | 不动 | 系统回收站 | 不动 |
| 旧记录 | 不动 | **同位替换**（沿用 id/名/分类，换内容+派生字段） | 不动 |
| 新增记录 | 无 | 无（替换） | 1 条 |
| 原压缩包 | **保留原位（强制 keep）** | 按 `archiveDisposal` 处置 | 按 `archiveDisposal` 处置 |
| 事件 | `status:'skipped'` | `status:'done'` + `conflict.resolution='overwrite'` | `status:'done'` + `conflict.resolution='keep-both'` |
| 磁盘峰值 | 0 | 旧 + 新 + 系统回收站里的旧（直到清空回收站） | 旧 + 新 |
| 可逆性 | 无操作 | 系统回收站可手工捞回 | 直接可用 |

### 4.3 主进程侧实现要点（`src/main/index.ts`）

```ts
// 模块级：一次导入一个批次
let batchChain: Promise<unknown> = Promise.resolve()
const pendingAsks = new Map<string, (a: ImportConflictAnswer) => void>()

ipcMain.handle(IPC.importPaths, (_e, paths: string[], ctx?: ImportConflictContext) => {
  const run = batchChain.then(() => runImport(paths, ctx))   // D18 串行
  batchChain = run.catch(() => {})                            // 失败不卡死链
  return run

ipcMain.handle(IPC.importConflictAnswer, (_e, answer: ImportConflictAnswer) => {
  const resolve = pendingAsks.get(answer.requestId)
  if (!resolve) return          // 幂等：超时后到达的答复直接丢弃
  pendingAsks.delete(answer.requestId)
  resolve(answer)
})
```

### 4.4 超时兜底：默认「跳过」

| 场景 | 处置 |
|---|---|
| 120s 内用户不答 | 全部按 `skip`（= 不落盘、原包保留） |
| 用户按 Esc / `[全部取消]` | 全部 `skip` |
| 窗口关闭 / 渲染进程崩溃 / 窗口尚未创建 | 全部 `skip`（立即，不等待） |
| 答复里 `requestId` 已过期（超时后才到） | 丢弃，幂等 |

**为什么默认 skip 而不是 keep-both**：

1. **零副作用**：跳过的动作集合是空集——不写盘、不删旧、不动原包。任何一种"替用户做决定"的默认档都可能造成不可逆后果，唯独 skip 不会；
2. **可恢复**：用户随时可以把包再拖一次（包还在原位，这正是 §3.1 强制 keep 的意义）。若默认 keep-both，用户会得到一堆不知从哪来的 `-2/-3` 副本，清理成本远高于重拖；
3. **反例排除**：默认 `overwrite` 会让"窗口失焦时正好有 20 个包在跑"变成一次静默的批量替换——这是本功能最不能接受的失败模式。

**120s 的取值理由**：20 行明细 + 逐条判断，60s 会掐断正在认真读的用户；180s 会让整批导入（含冲突项）停摆太久（冲突项的 staging 一直被占着）。120s 是"够读完、又不至于让人以为卡死"的折中。弹窗**不做**倒计时进度条（会逼用户仓促决定），超时只写日志。

**失焦不取消**：用户很可能要切到文件夹/浏览器去核对两个包是不是同一套。失焦即取消会让这个正常操作变成"手一抖全跳过"。

### 4.5 询问次数：一次导入**只问一次**

机制：`conflictGate` 持有 `batchDefault`（由答复确定）+ `decisions: Map<conflictKey, resolution>`。

```
第 1 次（唯一一次）：第一个冲突到达 → 开聚合窗口（800ms，每来一条新冲突 +400ms，上限 2500ms）
                   → 把窗口内累积的冲突一次性发出去 → 等答复
答复后：batchDefault 生效；后续冲突先查 decisions（同键复用同档），否则用 batchDefault，不再询问
超时/取消：批次策略**锁定为 skip**，后续冲突直接跳过，**不再弹窗打扰**
```

- 结论：**用户视角就是一次弹窗**，20 个包里有 15 个重复也只弹一次。`remainingItems` 让用户知道"后面还会有，按我选的办"。
- 超时后不再问的理由：没人应答就说明用户不在电脑前，再弹一次只会在用户回来时堆出 N 个过期弹窗；而 skip 已经是最安全的落点（§4.4）。
- **为什么不"等所有包解压完再问"**：那要求 N 个 staging 同时存在（20 包可能几十 GB），直接违反 P0-3 空间预检的前提（`importer.ts:256-274`）。
- **为什么不 per-item**：见 §2.2。
- `MAX_ASKS_PER_BATCH = 3` 只作为**协议防御上限**（正常路径不可达，例如未来放开"分批询问"时兜底）；超过即套用批次策略。

### 4.6 向后兼容

- `ctx` 可选：不传（或 `index` 为空数组）→ 完全不判重、不询问，行为与 0.6.9 一模一样；
- 老渲染层 + 新主进程：不传 ctx → 旧行为；新通道无人订阅 → 不会触发（无 ctx 就不问）；
- 新渲染层 + 老主进程：`invoke(..., paths, ctx)` 第二个参数被忽略 → 旧行为，不报错。

## §5 边界与坑

### 5.1 同一批里 A、B 互相重复（库里都没有）

**不问**（D15）。理由：这是**一次用户动作**，两个同款包同时进来，用户意图就是"都要"（多半是一个高清一个轻量）；此时问"要跳过哪个"是在信息最少（都还没入库、看不到内容）的时候逼用户做取舍。走现状：第二个 `uniqueName` 加 `-2`。

**顺手修一个真实缺陷**：压缩包路径的 `existing` 来自 `fs.readdir(cat2Dir)`（`importer.ts:352-358`），并发 3 下 A 与 B 可能同时读到"目录里没有 X"，都算出 `X`，然后 `moveDir` 第二个撞上已存在的目标（`fs.rename` 到非空目录在 Windows 上失败）→ 该条以 `error` 收场。修法：批次内台账

```ts
export class BatchLedger {
  /** cat2 绝对路径 → 已保留的目录名（含磁盘现状 + 本批次已占用的） */
  reserve(cat2Dir: string, base: string, diskNames: string[]): string
  release(cat2Dir: string, name: string): void   // 导入失败时归还，避免白占
}
```

`reserve()` = 把 `diskNames` 与本批已保留名合并成 `Set` → `uniqueName(base, set)` → 记入台账。单图路径的 `mkdir` 占位锁（`importer.ts:609-619`）保留（它防的是跨进程/外部抢占），只需把台账名并入初始 `taken`。

### 5.2 单张图片 / HDR

**口径与压缩包完全一致**（D16），落地点：

- `assetName = sanitizeName(stripNoise(文件名去扩展名))`（`importer.ts:577`）；
- `dedupeKey = dedupeKeyOf(assetName, kind)`，`kind` 由调用方给（`texture` / `hdri`，`importer.ts:248-252`）；
- `zhimoId = zhimoIdFromSources(itemName, assetName, [itemName])`（`:669` 同款）。

**同名不同 kind 不判重**：`dedupeKeyOf` 里 kind 是前缀（`naming.ts:331`），「木纹.jpg」(texture) 与库里的「木纹」模型 (model) key 不同 → 不判重。这是**正确**的：它们的落盘大类目录本来就不同，物理上不冲突。

覆盖单图时的差异：不是 `moveDir(contentRoot)` 而是「`mkdir` 旧路径 + `copyFile` 新文件」。文件名用**新包的文件名**（可能是 `.png` 而旧的是 `.jpg`），`Asset.files` 也随之换新；资产名（= 目录名）保持旧值。

### 5.3 回收站里的旧资产算不算「已存在」

**不算**（D17）。快照构建时过滤 `isDeletedAsset(a)`（`store.ts:1496` 已用它过滤删除目标）。

副作用（预期，不是缺陷）：还原时目标位置可能已被新导入占用 → `restoreFromLibraryTrash` 会 `uniqueName` 追加 `-2` 并返回 `renamed:true`（`src/main/trash.ts:302-311`），渲染层已有"已改名还原"提示链路。**不额外处理**。

### 5.4 导入进行中又拖入一批（重入）

**批次串行**（D18）：`runImport` 外层串成一条 promise 链（§4.3）。

- 第二批在 `ImportQueue` 里以 `pending` 挂着（`store.ts:1474-1479` 先插 pending 再 await），用户看得到"在排队"；
- 串行的必要性：两个批次并发写同一个 cat2 目录时，`uniqueName` + 台账 + 覆盖的「挪旧/落新」会互相踩（尤其覆盖时把旧目录改名，另一批正好在读到这个名字）；
- 副作用：watcher 的后台导入会排在用户批次之后。可接受（后台导入没有时效要求），且避免了两条链路争 IO；
- 死锁风险：第一批在等用户答复（最长 120s），第二批在排队 —— 不构成死锁（答复/超时必然发生）。但 UI 必须让弹窗**压在其他弹窗之上**（`Modal.tsx:14` 是固定 `z-50`，本弹窗若同时打开了设置/详情弹窗，需要显式提到更高层，否则用户看不见它还以为是卡死）。

### 5.5 监控目录（watcher）自动导入

**不问**（D19）：`restartWatcher` 的回调直接 `void runImport([p])`（`index.ts:299-302`），没有 ctx → D21 退化 → 静默保留两者 = 现状。理由：后台任务弹窗会在用户不在电脑前时长期挂起；且"下载目录里又下了一份"通常不是用户在场时的主动决定。

### 5.6 `ignored` 上报是否复用 `IgnoredReason`

**不复用**（D20）。`IgnoredReason = 'depth' | 'not-dir'`（`types.ts:681`）的语义是"rescan 发现目录结构不符合固定四层"（`rescan.ts:37-45`），UI 文案是「N 个目录结构异常已跳过」（`RescanResult`）。塞进"重复跳过"会让用户去查一个根本不存在的结构问题。

跳过的上报走 `ImportStatus='skipped'` + `ImportEvent.conflict`，落点是导入队列与底部 toast，与 rescan 的 ignored 完全分离。

### 5.7 其它必须挡住的坑

| 坑 | 处置 |
|---|---|
| 渲染层传来的 `folder` 不在库内（脏索引 / 注入） | 覆盖执行前 `isInsideLibraryDir(libraryDir, folder)`（`importer.ts:169`）二次校验；不过 → 退化分支（§3.2.4）+ logWarn |
| 快照来自 `libraryDir` 之前的旧目录（用户刚改库目录） | 同上：校验失败即退化，绝不会去 trash 旧库的文件 |
| 覆盖时 `existing.folder` 里正被 DCC 打开/占用 | `trashOne` 失败 → 第 3 步降级（保留 `.idbox-old-*` + 提示），数据正确 |
| 崩溃残留 `.idbox-old-*` | `.` 开头 → rescan/watcher 跳过；下次同资产覆盖时先检测同名临时目录并加时间戳；不主动扫描清理（不引入新的启动开销） |
| 快照过期（导入期间用户删了/改了那条资产） | 覆盖执行前 `stat` 一次 `existing.folder`；不存在 → 退化分支。批次锁已挡住并发导入，本轮不同步并发删除 |
| 覆盖后 `dedupeKey` 与名字不一致 | 覆盖恒定用旧名重算，天然一致；单图/HDR 同理 |
| 弹窗里 20 行太长 | 超过 8 行时列表区内部滚动（`max-h`），不折叠、不分页（用户需要一眼看全） |
| 用户拖入 200 个包 | `remainingItems` 让用户知道规模；弹窗只列聚合窗口内到达的那批（并发 3 时通常 ≤3 条），其余套用批次策略；不设上限（策略已定，明细不是必须逐条看） |

### 6.3 端到端验收清单（给 QA）

1. 拖入 1 个与库内**同 ID** 的包 → 弹窗标「同一件素材(ID)」；选覆盖 → 库内只有 1 条、名字/分类/收藏/备注不变、内容为新的、旧目录在系统回收站。
2. 选跳过 → 库内无变化、导入队列该条显示「已跳过」、**原压缩包仍在原位置**（哪怕设置是"彻底删除"）。
3. 选保留两者 → 库内 2 条（`X` 与 `X-2`），重复视图把两条归到同一组（key 一致）。

5. 弹窗不操作 → 120s 后全部跳过，原包全在。
6. 弹窗期间 `kill` 渲染进程 → 主进程不死等，日志有 `timedOut/render-gone` 记录。
7. 导入中再拖一批 → 第二批排队，结束后正常导入，无同名覆盖/无 `-2` 错乱。
8. 单张同名图片 / 同名 HDR 各走一遍三档。
9. 回收站里的资产同名 → **不弹窗**，正常导入。
10. watcher 自动导入重复包 → **不弹窗**，得 `-2` 副本（现状）。

## §7 明确不在本轮的范围
