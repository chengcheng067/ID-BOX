## 一、TL;DR

v1.2 第一版应用内文件浏览器**方向正确**（用户已确认），但深度不足：只有「列表 + 面包屑 + 双击」一条交互路径，缺少返回/前进历史、视图切换、右键菜单、多选、排序五大资源管理器基础能力。本 PRD 以 **Windows 资源管理器核心交互模型为对标基准**，给出 8 个设计域的「现状 → 可选 → 推荐 → 理由」逐项取舍（A/B/C 共 14 个待批注项），并在末尾给出两个范围方案：

- **方案一（推荐）：纯只读浏览 + 视图/排序/右键菜单/多选/历史栈** —— 不引入任何写操作，安全边界零放宽；
- **方案二：方案一 + 写操作（新建文件夹/重命名/删除）** —— 需新增 IPC 写通道 + 回收站化策略，代价与风险见 §8。

用户明确要求：**先在 ardot 里把 UI 画完，再进代码实现**（§10 下一步编排）。

### 2.3 定位重新校准（本 PRD 的核心判断）

第一版实质是「**资产视图的复用**」——交互语言全部来自 idbox 的资产网格/文件视图（双击=打开、Esc=回首页、面包屑样式同中栏头）。用户点破的正是这一点：**我们要做的是文件资源管理器，不是资产列表的套壳**。因此本 PRD 的原则是：

1. **交互模型向资源管理器对齐**：返回/前进历史栈、三态右键菜单、多选、排序切换、视图切换——这些是资源管理器的「肌肉记忆」，缺失即「深度不够」的直接来源；
2. **视觉气质保持 ID BOX**：不引入系统默认控件、不照搬资源管理器的工具栏满配（ribbon/侧栏树/地址栏输入框），每个能力裁剪到「钉选目录浏览」场景真正需要的最小集；
3. **安全边界不因能力扩充而放宽**：现有 `pinnedDirGuard` 的只读边界是资产，方案一不动它；写操作（若选方案二）另立通道另行评审。

| 用户故事 | 映射能力域 |

## 三、清单（8 个设计域 · 逐项取舍 · A/B/C 待批注项）

> 每项格式：现状 → 可选 → 推荐 → 理由。待批注项编号 A1…A14，用户逐条勾选「采纳推荐 / 选其他 / 有其他想法」。

### 3.1 导航体系

**A1 · 返回/前进历史栈（用户原话第一条的直接回应）**

| 项 | 内容 |
|---|---|
| 现状 | 只有一个「← 返回」按钮，且语义是**回首页**（关闭浏览器），不是「上一级目录」【查证 `PinnedFolderBrowser.tsx:178-185`】。下钻 3 层想退 1 层，只能点面包屑倒数第二个节点——用户说「返回上一步的方式不够明了」即指此 |
| 可选 | ① 面包屑可点回跳已够，不加历史栈；② 加「← 上一级」「→ 下一级」两个按钮；③ 加完整历史栈：返回/前进 + Backspace=上一级，跳转历史保序 |
| 推荐 | **③ 精简版**：顶行放「← 返回（上一级）」「→ 前进」两枚按钮 + Backspace 快捷键；**「回首页」独立保留**为顶行最右侧一个明确入口（图标或文案），与「上一级」彻底分离。历史栈 = segments 快照数组 + 游标，面包屑回跳视为一次新跳转（清掉游标之后的前进记录，同资源管理器行为） |
| 理由 | 用户原话把「返回上一步」与「回首页」的混淆点出来了——两个动作必须分成两个明确控件。历史栈在 segments 数据模型上是自然延伸（`PinnedFolderBrowser.tsx:97` 的段数组本就是唯一状态源），实现代价低 |

**A2 · 面包屑样式：可点分段 vs 可输入路径**

| 项 | 内容 |
|---|---|
| 现状 | 可点分段，根=钉选名，逐级可回跳【查证 `PinnedFolderBrowser.tsx:167-209`】 |
| 可选 | ① 保持可点分段；② 资源管理器式「点击空白处变成可输入路径框」；③ 分段 + 每级下拉显示同级子目录（Windows Vista 式） |
| 推荐 | **① 保持现状**，仅在面包屑旁加当前层级的只读相对路径展示（鼠标悬停 title 已有，不做输入框） |
| 理由 | 【推断】路径输入框暴露「绝对路径概念」，违背「绝对路径全程不进渲染层」的安全叙事（`PinnedFolderBrowser.tsx:46-47`）；③ 的下拉树在深目录下收益有限、实现成本高 |

**A3 · 侧栏（常用位置/子目录树）**

| 项 | 内容 |
|---|---|
| 现状 | 无侧栏 |
| 可选 | ① 不加；② 加资源管理器式左栏（常用位置+目录树）；③ 轻量版：仅显示当前 pin 的子目录树（可折叠） |
| 推荐 | **① 不加（首版）** |
| 理由 | 【推断】场景是「浏览某一个已钉选的目录」，资源管理器左栏的常用位置在 ID BOX 里已由**首页钉选卡本身**承担（首页即常用位置页）；目录树属于大工程（异步懒加载 + 状态同步），与「深度不够」的用户痛点（返回/视图/右键）不重合。留待后续版本按反馈决定 |

### 3.2 视图模式（用户原话第二条的直接回应）

**A4 · 视图切换：入口与档位**

| 项 | 内容 |
|---|---|
| 现状 | 仅列表视图，无切换 |
| 可选 | ① 列表 + 大图标两档；② 列表 + 大/中/小图标三档（同资源管理器）；③ 四档（含「内容」视图，Windows 8+） |
| 推荐 | **① 列表 + 图标两档**（图标视图 = 资产网格同款密度，一张卡 = 类型图标 + 文件名，网格排布） |
| 理由 | 【推断】三/四档是资源管理器在通用场景下的档位，ID BOX 的浏览对象相对单一（素材目录），两档够用且与首页 GlassFolder 卡片、资产网格的视觉语言最接近；档位越多，记忆与实现的复杂度都涨。切换入口放顶行（详见 §3.6 A10） |

**A5 · 图标视图的信息密度：真实缩略图？**

| 项 | 内容 |
|---|---|
| 现状 | —（无图标视图） |
| 可选 | ① 类型图标（沿用 `icons.tsx` 自绘的 IconFolder/IconFile，按扩展名细分几种）；② 真实图片缩略图（主进程读文件生成） |
| 推荐 | **首版 ① 纯类型图标**；真实缩略图**明确列入不做项**（§7） |
| 理由 | 缩略图要新增「读用户文件字节→解码→缩放→缓存→失效」一整条管线，且图片解码在主进程是性能敏感点（大图、恶意构造文件、内存占用），与首版目标「把交互骨架做对」无关。图标视图先把**布局、选中、右键、排序**这些骨架立起来，缩略图作为独立增量另立 PRD |

**A6 · 视图记忆：按 pin 记 vs 全局记**

| 项 | 内容 |
|---|---|
| 现状 | — |
| 可选 | ① 全局一个偏好（settings 单字段）；② 每个 pin 各自记忆（存进 `HomePinnedFolder`） |
| 推荐 | **② 按 pin 记忆**，且与「排序偏好按 pin 记忆」（A11）合并为同一字段 `{view, sortKey, sortDir}` |
| 理由 | 【推断】不同钉选目录内容形态不同（素材库适合图标、交付目录适合列表），按 pin 记忆符合资源管理器「按文件夹记忆视图」的心智；数据面只是钉选结构加一个可选字段，32 封顶的量级无压力【推断】 |

### 3.3 右键菜单（用户原话第三条的直接回应）

**A7 · 三套菜单的项**

裁剪原则：对标资源管理器，但只保留「浏览一个只读目录」场景下有意义的项；写操作项全部标注「方案二才出现」。

| 菜单 | 首版项（方案一） | 方案二追加项 | 理由 |
|---|---|---|---|
| 文件夹 | 打开（=双击）、在资源管理器中显示 | 新建文件夹、重命名、删除 | 「在资源管理器中显示」复用现有 `home:pinnedOpen` 兜底通道【查证 `PinnedFolderBrowser.tsx:18`，主进程已有 shell 打开能力【待核实】】 |
| 文件 | 打开（系统默认程序，=`fs:openEntry`）、在资源管理器中显示 | 重命名、删除 | 打开项复用现有 IPC，零新增通道 |
| 空白处 | 在资源管理器中显示当前文件夹、刷新 | 新建文件夹、粘贴（视后续） | 空白处菜单保持极简，刷新解决「目录内容外部变了」的真实痛点【推断】 |

**A8 · 右键菜单的实现形态**

| 项 | 内容 |
|---|---|
| 现状 | 无任何右键（组件头注释明确「零系统默认控件…没有原生右键」【查证 `PinnedFolderBrowser.tsx:10-11`】） |
| 可选 | ① 拦截 `contextmenu` + 自绘浮层菜单（复用项目内已有自绘右键菜单组件，若有【待核实：资产网格右键菜单组件名】）；② Electron 原生 `Menu` 弹出 |
| 推荐 | **① 自绘浮层**（GlassCard 同款 token、Esc 层栈接管关闭、点击外部关闭） |
| 理由 | 原生 Menu 破坏「零系统默认控件」的产品纪律；自绘菜单与 Esc 层栈、暗色主题、圆角 token 一致 |

**A9 · 「删除」是否进首版（高危项，单独批注）**

| 项 | 内容 |
|---|---|
| 推荐 | **不进首版**。若用户坚持要（选方案二），必须做回收站化：`shell.trashItem()` 移入系统回收站（Electron 原生 API【查证：Electron 标准 API】），**绝不做永久删除**；且删除入口只放右键菜单，不放 Delete 键直达（见 A12 说明） |
| 理由 | 删除是不可逆操作（即使回收站化，用户心智里「软件删的文件」责任在软件）；写操作还牵动 `pinnedDirGuard` 的只读边界重设计（删除目标同样要走 pin 根前缀校验）。首版价值在「看」，不在「动」 |

### 3.4 选择与多选

**A10 →（编号调整说明：选择域为 A10）· 选择模型**

| 项 | 内容 |
|---|---|
| 现状 | 无选中态（行只有 hover 背景）【查证 `PinnedFolderBrowser.tsx:253`】 |
| 可选 | ① 单击选中（单选）；② 单选 + Ctrl 点选/Shift 范围选；③ ② + 空白处框选（rubber band，对标 idbox 资产网格已有语言【待核实：资产网格框选实现】） |
| 推荐 | **② 单击选中 + Ctrl/Shift 多选**；框选**首版不做**（不做项 §7） |
| 理由 | 多选是右键菜单「批量操作」的前置语义（即使首版无批量动作，选中数也要在计数区显示「已选 3 项」）；框选的命中计算在列表/图标两套视图下各做一套，成本不小且首版没有消费多选的批量动作。底部计数条显示选中数（对标资源管理器状态栏） |

### 3.5 排序

**A11 · 排序键与方向**

| 项 | 内容 |
|---|---|
| 现状 | 主进程固定：目录在前、名称升序【查证 `pinnedDirGuard.ts:132-135`】 |
| 可选 | ① 列表头点击排序（名称/大小/时间/类型四列可点）；② 顶行排序菜单（下拉选键+方向）；③ ①+② 都要 |
| 推荐 | **① 列表头点击**为列表视图的排序入口（升↔降↔还原循环或升/降切换），图标视图用**顶行排序菜单**（图标视图无列头）；目录恒在前（不可通过排序打乱，这是资源管理器默认行为且对浏览友好） |
| 理由 | 排序改为渲染层做（主进程已返回 size/mtimeMs 全量字段【查证 `pinnedDirGuard.ts:36-45`】），零 IPC 改动；「目录恒在前」保住浏览语义。「类型」列首版列表里没有独立列——**推荐列表加第四列「类型」**（显示扩展名大写，如 `PSD`），既补齐资源管理器的列语义，又给排序键一个落点【推断，待批注确认】 |

### 3.8 性能与边界

**A14 · 边界场景处理**

| 场景 | 现状 | 增量要求 |
|---|---|---|
| 单层 >2000 条 | 静默截断（超限视为异常目录）【查证 `pinnedDirGuard.ts:26-33,135`】 | **必须改为明示**：列表末尾单行提示「已显示前 2000 项（共 N 项）」——主进程需回传总数或截断标志【待核实：IPC 返回结构是否可加 `truncated` 字段】 |
| 目录消失/无权限 | 单行错误 + 回首页按钮【查证 `PinnedFolderBrowser.tsx:221-227`】 | 保留；历史栈回退到上一有效层也应可用 |
| 深层目录（层级很深） | 面包屑逐级截断显示（max-w 280/200px + truncate）【查证 `PinnedFolderBrowser.tsx:199-200`】 | 保持；面包屑超宽时优先保留根节点与当前层（中间层折叠为「…」可点下拉）【推断】 |
| 目录内容被外部修改 | 列目录时快照，无刷新 | 右键空白处「刷新」（A7）+ 工具行刷新按钮；不做文件监听（不做项 §7） |
| 快速连点竞态 | `cancelled` 挡过期响应【查证 `PinnedFolderBrowser.tsx:107-136`】 | 保持机制，历史栈跳转同样纳入竞态防护 |

## 四、明确不做（首版）

| # | 不做项 | 理由 |
|---|---|---|
| 1 | 真实图片缩略图 | 解码/缓存/失效管线是独立工程量，先立骨架（A5） |
| 2 | 框选（rubber band） | 无消费批量动作，两套视图各做一套命中计算成本高（A10） |
| 3 | 路径输入框 / 绝对路径展示 | 违背绝对路径不进渲染层的安全叙事（A2） |
| 4 | 左侧栏（常用位置/目录树） | 场景不需要，首页钉选卡已是「常用位置」（A3） |
| 5 | 跨 pin 搜索 / 目录内搜索 | 搜索是独立能力域，另有 search-center 已建体系，不混入 |
| 6 | 网络路径 / 映射盘特殊处理 | 现有 statSync 在慢介质上已由加载态兜住【查证 `pinnedDirGuard.ts:29-31`】，不做专项优化 |
| 7 | 回收站浏览 | 独立能力域 |
| 8 | 文件监听（fs watch 自动刷新） | 事件风暴风险，手动刷新够用（A14） |
| 9 | Delete 键 / 永久删除 | 见 A9 |

## 五、范围方案对比表（供用户拍板）

| 维度 | 方案一：只读浏览版（推荐） | 方案二：可操作版 |
|---|---|---|
| 范围 | 历史栈导航 + 列表/图标视图 + 三套右键菜单（打开/显示/刷新）+ 单击与 Ctrl/Shift 多选 + 列表头/菜单排序 + 键盘全家桶 + 2000 截断明示 | 方案一全部 + 新建文件夹 + 重命名 + 删除（回收站化） |
| 用户三条原话覆盖 | ✅ 返回明了 ✅ 视图切换 ✅ 右键菜单（「重命名/删除」除外） | 全覆盖且含写操作 |
| IPC 增量 | 1 条：`fs:listDir` 返回结构加 `truncated/total`（或复用现有，改契约）【待核实】 | 方案一 + 2~3 条新写通道：`fs:createDir` / `fs:renameEntry` / `fs:trashEntry`，每条都要过 pin 根前缀校验 |
| 安全边界 | **零放宽**：只读边界原样（`pinnedDirGuard` 不出现写 API 的纪律保持【查证 `pinnedDirGuard.ts:17`】） | 只读边界被打破，需要守卫模块分层重构（读守卫/写守卫）+ 新增单测覆盖写路径注入面 |
| 风险 | 低——纯展示层与既有 IPC 小改 | 高——删除误操作、重命名竞态（目标已存在）、写权限缺失场景、回收站失败回滚；且 ardot UI 稿要一并画写操作态（命名输入框、冲突提示） |
| 工期感受 | 一个批次可收口 | 约为方案一的 1.6~2 倍【推断】 |
| 后续演进 | 方案二可作为独立增量无缝叠加 | — |

**推荐理由**：用户三条原话（返回/视图/右键）在方案一内全部解决；「我们要实现的就是文件资源管理器」的核心是**交互模型对齐**而非**写能力对齐**。写操作建议等 ardot UI 稿画完、用户看过交互后再决定是否追加为第二批。

## 六、验收要点（方案一口径，摘要）

1. 下钻 ≥3 层后：← 一路退回根、→ 可重做前进、Backspace 与 ← 等价、「回首页」独立可达；
2. 列表/图标两视图可切换，偏好按 pin 持久化，重开同一 pin 恢复上次视图与排序；
3. 文件夹/文件/空白处三套右键菜单项与 §3.3 表一致，Esc/点外部均可关闭，无系统原生菜单闪现；
4. Ctrl 多选与 Shift 范围选正确，底部计数显示「已选 N 项」；
5. 列表头四列（名称/大小/修改时间/类型）点击排序生效，目录恒在前；
6. >2000 条目录出现截断明示行；错误态在历史栈回退下可恢复；
7. 全程无绝对路径出现在 UI/日志/设置（沿用既有纪律）。
