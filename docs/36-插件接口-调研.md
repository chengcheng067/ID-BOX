## 2. 现状盘点：为什么必须新增一条「主进程侧查询通道」

### 2.1 三层与进程边界（【查证】）

| 层 | 持有什么 | 对外可见面 |
| --- | --- | --- |
| `renderer` | `assets[]`（Zustand）、**Dexie/IndexedDB（元数据唯一权威）** | 只能经 `preload` 白名单 |
| `preload` | `contextBridge.exposeInMainWorld('modvault', api)` | `window.modvault.*`，**只有本应用渲染进程能用** |
| `main` | `settings.json`、`fs` / `7z` / 缩略图、`vault://` 协议、`ipcMain.handle` | 只接 IPC；**拿不到 Dexie** |

证据：`src/preload/index.ts:480`、`src/shared/ipc.ts:1-5`、`docs/25:2111-2115`、`docs/16:44-51`、`:78-87`。

### 2.2 关键结论（原文判据② `:2111-2115` + 判据③ `:2117-2120`）

1. **【沿用原文】** 渲染层数据都在 **Dexie（Chromium IndexedDB）**，主进程读不到；唯一对外能力是 `window.modvault.*`，那是 IPC，**只有应用自己的渲染进程能用**（`docs/25:2112-2113`）。
   → **外部程序读库，必须新增一条主进程侧的查询通道**：原文列举 **本地 HTTP / 命名管道 / CLI**（`docs/25:2114`）；或让插件直读 IndexedDB —— **不推荐：库 schema 会变，插件必然跟着碎**（`docs/25:2115`，同 J2）。
2. **【沿用原文 · MVP 主线】** `Asset.folder` 是**绝对路径**，这是天然优势；插件真正想要的只是「给我一个绝对路径 / 一组绝对路径」，**元数据是次要的**（`docs/25:2117-2118`）。所以 MVP 可能极简到 **只暴露「搜词 → 返回绝对路径列表」**：**材质给贴图文件路径、模型给 `.skp` / `.max` 路径**（`docs/25:2119-2120`）。→ **这条是 §5 MVP ≤5 端点方案的主线**（见 §5.0 与 E2），它比暴露完整 schema 稳得多。
3. **【查证·风险】** 但绝对路径**不是稳定契约**：`docs/16:100` 明写「`Asset.folder` 的一致性**没有任何保证者**，只有约定」；改分类 / 改名 / 移库 / `rescan` 都可能让旧路径失效或旧记录被「删旧建新」（`docs/16:93-95`、`:114-125`）。→ **插件不得长期缓存路径，每次取用应重新解析**（写入 §5.3 的接口语义）。
4. **【查证】** 主进程已有只读扫盘能力（`rescanLibrary(settings.libraryDir)`，`src/main/index.ts:1529`）且「分类层级以磁盘为权威」（`docs/16:108`、`:131`）—— 这是「不依赖 Dexie 也能列出资产」的现成地基，但**拿不到 `tags/note/styles` 等只在索引里的元数据**（`docs/16:108`）。

### 2.3 可复用的既有地基（不必从零造）

| --- | --- | --- |

### 2.4 破坏性通道的现有防护思路（对外接口必须继承）

【查证】`src/main/ipcGuard.ts` 的守卫哲学（`:1-45`、`:116-139`、`:186-234`）：

- **渲染层是「同源但不可信」的** —— 这条对**外部插件同样成立，且更甚**：外部进程比渲染层更不可信。
- `isWithinRoot(root, target)`：**deny by default**；要求绝对路径（`C:\` / UNC / POSIX 根），拒相对路径；归一化后消 `..` 穿越；**无条件小写**（Windows 大小写不敏感）；前缀必须带分隔符（`C:\lib` 不匹配 `C:\lib2`）；**永不抛异常**。
- `guardTrashPaths` 还有三类额外禁令（库根本身 / 大类目录 / `.trash`·`.staging`）—— 说明「只读接口」与「可写接口」要分开设计，写接口必须更窄。
- `src/main/index.ts:1146-1188` 把 `openPath` / `reveal` / `trashPaths` 三条破坏性通道逐一套上守卫；`drag:start` 也用 `isWithinRoot` 校验（`:1561`）；`protocol.ts:117` 对三个目录一视同仁做越界 403。

> **结论（【推断】但强建议）**：未来任何对外接口，**出参只返回库内绝对路径且经 `isWithinRoot` 复核**；入参一律当 `unknown` 处理、永不抛；**只读端点与写入端点分开设鉴权等级**。这不是新发明，是把 `ipcGuard.ts` 的既有纪律外推一层。

### 4.2 逐项对比表（原文三选一为主）

> 安全性结论多为**【推断】**（基于通用安全机制推理，非本仓库实测）；「实现成本」沿用 `docs/13:24` 的 **小(S) / 中(M) / 大(L)** 量级思想，**只给档位、不给天数**。

| 维度 | ① `HTTP + JSON` | ② `命名管道` | ③ `file://` 清单 + 文件监视 |
| --- | --- | --- | --- |
| **未授权本地调用** | 🔴 端口开着，**同机任何进程**都能连；绑 `127.0.0.1` 只挡外部网段，挡不住本机恶意程序。**必须有 token**【推断】 | 🟢 管道可设 ACL / 仅当前用户会话，比 TCP 端口收敛【推断，ACL 细节待核实】 | 🟢 **无监听端口**，攻击面最小；但任何能写交换目录的程序可伪造请求，需目录权限 + 清单签名【推断】 |
| **CSRF / 浏览器侧** | 🔴 本机浏览器里**任意网页**可对本机端口发简单请求；**DNS rebinding** 可绕过 `127.0.0.1` 绑定【推断】。防护：校验 `Host`/`Origin`、token 放**自定义头**（不放 Cookie）、CORS 默认拒绝、只认 `application/json` | 🟢 浏览器连不上命名管道【推断】 | 🟢 浏览器无法直接写本地约定目录，CSRF 面几乎为零【推断】 |
| **token 泄露** | 🟡 token 需落到插件配置/文件里才能被 DCC 读到 → **任何能读该用户目录的程序可读**；且进 URL/日志易泄【推断】。缓解：高熵、可一键轮换、只绑 loopback | 🟢 可无 token（靠 ACL）；若要 token 同 ① 的落盘问题【推断】 | 🟢 可完全无 token（靠目录权限）；若加签名，密钥同样要落盘【推断】 |
| **端口占用** | 🔴 **固定端口会被别的程序占用 / 被防火墙拦**；随机端口则插件要先发现端口【推断】；已有单实例锁 → 多实例谁监听要明确（§2.1） | 🟢 无 TCP 端口；但**管道名冲突**是同类问题【推断】 | 🟢 **零服务、无任何端口**【沿用原文 `:2132`】 |
| **跨平台（当前仅 Windows）** | 🟢 HTTP/TCP 跨平台最自然；当前仅 Windows（`README.md:474`），未来若跨平台**这一项迁移成本最低**【推断】 | 🔴 **Windows 命名管道是平台能力**；macOS/Linux 要换 Unix domain socket，等于另写一套【推断】—— 与「仅 Windows」现状一致，但堵死未来跨平台 | 🟢 目录 + watcher 跨平台通用；`chokidar` 本身跨平台【查证，`package.json:22`】 |
| **双向/实时性** | 🟢 请求-响应同步，插件能「搜了立刻拿结果」 | 🟢 全双工、低延迟 | 🟡 **异步、要等导出**（原文 `:2132`），延迟高，不适合「在 DCC 里搜了立刻插入」 |
| **可调试性 / 跨语言** | 🟢 curl/浏览器直接调，JSON 跨语言（三个 DCC 都能发 HTTP） | 🔴 需要管道客户端，各语言支持不一（Ruby / MAXScript / Rhino Python 侧要各写一套）【推断】 | 🟡 看文件好排查，但无请求语义、要自定义清单格式 |
| **实现成本** | **小~中**：主进程起 http server + 复用现有扫盘/守卫；插件侧三个 DCC 都有 HTTP 客户端（§3） | **中~大**：主进程管道服务 + **每个 DCC 各写一套管道客户端**；且 Windows 专属 | **小**：复用 `chokidar` + 既有监控目录导入；但要定义清单文件格式、并发与幂等 |
| **与「本地优先、数据敏感」偏好** | 🟡 需要用户显式「允许插件访问」开关才安心；路径清单只在 loopback 出、绝不联网/上云（J1） | 🟢 贴合「不外露端口」的直觉，但平台绑定 | 🟢 **最贴合「零服务、本地优先」直觉**（对应原文把用户偏好算进来的要求） |

### 4.3 鉴权模型（回答原文 **D1**：要不要 token → **要**）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 结论 | **要 token**，且配一个**默认关闭**的「允许插件访问」总开关 | 直接回答 `docs/25:2130`；本地 HTTP 端口开着，同机任何程序都能读路径清单（J1） |
| 绑定 | **只绑 `127.0.0.1`（IPv4 loopback）**，不绑 `0.0.0.0` | 挡外部网段；路径清单绝不出本机 |
| 开关 | 设置页一个默认关闭的总开关 + 显式「生成 / 轮换 token」按钮 | 用户「数据敏感」偏好（`docs/25:2132`）；默认关 = 不开端口 |
| token | 高熵随机（如 128bit+），**放自定义请求头**（如 `X-IDBOX-Token`），**绝不放 Cookie / URL query** | 避免浏览器自动携带与 CSRF、避免进日志【推断】 |
| 请求校验 | 校验 `Host` 必须是 `127.0.0.1:<port>`、拒绝非预期 `Origin`、CORS 默认拒绝、只收 `application/json`、拒绝非白名单方法 | 缓解 DNS rebinding / CSRF【推断】 |
| 生命周期 | 应用退出即关服务；应用未启动 → 插件调 `/health` 失败并提示「请先启动 ID BOX」 | 随主进程生命周期 |
| 轮换/撤销 | 设置页一键轮换，旧 token 立即失效 | 泄露后可止损 |
| 分发 | **【待核实/待拍板】** token 怎么到插件手里：① 设置页「复制连接串」由用户粘贴进插件配置 ② 写入 `%APPDATA%/idbox/` 下受限文件由插件读 —— 见 Q3 | 两者都有落盘泄露面【推断】 |

### 4.4 「取用」语义（回答原文 **D3**，`docs/25:2133-2134`）

### 4.5 协议形态推荐（回答原文 **D2**）

- **主形态建议 ① `HTTP + JSON`（localhost + token）**：三个必答 DCC 都有现成 / 可用的 HTTP 客户端（§3：SU `Net::HTTP`、Max `dotNet`、Rhino Python 标准库【推断待核实】），请求-响应同步、易调试、跨语言、未来跨平台成本最低；风险（本机端口 / CSRF / token 泄露）**可用 §4.3 的开关 + 校验收敛**，且这些防护是 `ipcGuard.ts` 既有纪律的外推（§2.4）。
- **③ `file://` 清单 + 文件监视作为「零服务兜底 / 降级路径」保留**：它已有 `chokidar` 与监控目录导入地基（§2.3），**最贴合用户「本地优先、数据敏感」的偏好**，但「零服务，但要等导出」（原文 `:2132`）带来的异步延迟不适合「在 DCC 里搜了立刻插入」的主体验。
- **② 命名管道不建议第一批**：原文说它「更安全、Windows 原生」—— 安全性确实更收敛，但**每个 DCC 要各写一套管道客户端**、且 Windows 专属，与「未来可能跨平台」冲突【推断】；当前项目仅 Windows，这条不构成否决，只是排期靠后。
- **「本地优先、数据敏感」怎么算进来**（`docs/25:2132` 要求）：默认关闭总开关、只绑 loopback、路径清单绝不上云 / 不联网、可一键停用与轮换 token、不引入账号或服务端（`docs/13:138-146` F-07/F-08 一票否决）、零服务形态作为兜底。

### 5.1 五个端点

#### E1 · 健康检查 `GET /health`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/health` |
| 参数 | 无（**免 token**，供插件探测「ID BOX 是否在运行 / 端口是否对」） |
| 返回 | `200 { ok:true, data:{ appVersion, apiVersion:"1", libraryReady:boolean, readOnly:boolean } }` |
| 失败语义 | 连接被拒 / 超时 = **ID BOX 未启动或开关关闭**，插件提示「请先启动 ID BOX 并开启插件访问」；`libraryReady:false` = 库目录未配置/不可读，插件禁用取用按钮（不报错） |
| 幂等性 | **幂等**（纯读，无副作用） |
| 备注 | `appVersion` 可复用既有 `app:getVersion`（`src/shared/ipc.ts:153`）；`readOnly` 表示当前是否允许 E4 |

#### E2 · 搜词 → 返回绝对路径列表 `GET /assets`（**原文主线端点**）

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/assets` |
| 参数 | `q?: string`（关键词，匹配资产名/路径）、`kind?: model\|texture\|cad\|hdri\|material`、`ext?: string`（如 `skp` / `max` / `jpg`）、`limit?: number`（默认 50，上限 200）、`offset?: number` |
| 返回 | `200 { ok:true, data:{ total, items: AssetBrief[] } }`；**`AssetBrief = { id, name, kind, category1, category2, primaryExt, absPath, files:[{ rel, absPath, ext, kind }], verifiedAt }`** —— **直接给绝对路径**：模型给 `.skp` / `.max`、材质给贴图文件路径（`docs/25:2119-2120`）；出参逐条经库根校验，越界条目不返回 |
| 失败语义 | `400 INVALID_PARAM`（`limit` 越界 / `kind` 非法枚举）；`401 UNAUTHORIZED`（token 缺失/错）；`403 OUT_OF_ROOT`（某条路径越界 → 该条剔除并在 `data.omitted` 计数，**绝不把越界路径写进响应**）；`503 LIBRARY_UNAVAILABLE`（库目录不可读 / 取数源不可用）；`q` 为空 = 返回全部（按 `limit` 分页） |
| 幂等性 | **幂等**（纯读；同一时刻重复调用结果一致，库内容变化后结果自然变化）。**每次搜索都是一次「现取」**，天然满足 §5.3「不缓存路径」 |
| 备注 | **对齐原文主线**：`docs/25:2119` 的「搜词 → 返回绝对路径列表」就是本端点，元数据（tags / note / styles）刻意不给，避免暴露 schema（J2）。E3 是它的「按 id 精确版 / 失效后刷新」补充，不是替代 |

#### E3 · 按 id 取 / 刷新落盘路径 `GET /assets/{id}/path`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/assets/{id}/path` |
| 参数 | 路径参数 `id`（E2 返回的 `id`）；query `role?: primary\|textures\|all`（缺省 `all`） |
| 返回 | `200 { ok:true, data:{ id, folder, verifiedAt, primaryFile, files: [{ rel, absPath, ext, kind }] } }`；用途：插件已持有 `id`（上次搜到的结果 / DCC 工程里记了 assetId）时**重新解析**路径，或插入模型前做最后一次校验 |
| 失败语义 | `404 NOT_FOUND`（`id` 不存在 / 已被 rescan 删旧建新）；`410 GONE`（记录还在但**磁盘路径已失效** —— 对应 `docs/16:124`「索引有/盘无」）；`403 OUT_OF_ROOT`（守卫拒绝，**绝不返回**）；`503 LIBRARY_UNAVAILABLE` |
| 幂等性 | **幂等**（纯读）；但**返回值不是稳定契约** —— 改分类 / 改名 / 移库 / rescan 后可能变 `410`，**插件必须每次现取、不得缓存**（§2.2 第 3 条、§5.3） |
| 备注 | 这是「给路径让 DCC 自己 import」（§4.4 方案 A / 原文 D3）在「精确取单个资产」时的落点 |

#### E4 · 触发导入 `POST /import`（**唯一写端点**）

| 项 | 内容 |
| --- | --- |

### 5.2 硬约束：主进程侧「谁能读库」（**必须拍板 Q1**）

【查证】服务若跑在**主进程**，而 `Dexie` 在**渲染进程**（`docs/25:2112`、`docs/16:141`），则 E2/E3/E5 的取数只有三条路：

| 方案 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 主进程只读扫盘** | 复用 `rescanLibrary` 的深度遍历（`src/main/index.ts:1529`），按「磁盘是分类权威」（`docs/16:108`）产出 `id/name/kind/路径` | 不依赖窗口存活、不改 IPC 面、纯只读最安全；**正好够 E2 的「搜词 → 绝对路径列表」** | **拿不到 `tags/note/styles/别名`**（只在 Dexie）；搜索只能靠文件名/路径；`rescan` 的「删旧建新」语义（`docs/16:114-125`）要小心别在接口里触发 |
| **B. 新增一条 IPC 让渲染层回传** | 主进程收到 HTTP 请求 → 新增 `plugin:query` 通道问渲染层 → 渲染层查 Dexie 回传 | 元数据完整、复用既有查询逻辑 | **依赖窗口存活**（最小化/窗口关闭时是否仍可用待核实）；新增通道要同时改 `shared/ipc.ts` + `preload/index.ts` + `main/index.ts` 三处（`src/shared/ipc.ts:1-5` 的既有纪律） |
| **C. 主进程直接读 IndexedDB 文件** | 解析 Chromium LevelDB | —— | **明确不做**：`docs/25:2115` 已否定（schema 会碎），格式私有、风险最高 |

> **建议（【推断】，待 Q1 拍板）**：MVP 走 **A**（只读扫盘，最贴合「只给路径」的极简契约），把 B 作为「将来要按标签/风格搜索」时的升级路径。**理由**：J2（不暴露 schema）+ J3（只读优先）+ 不新增 IPC 面；代价是「搜词」只能匹配文件名/路径 —— 这与 `docs/25:2119` 的 MVP 设想一致。

### 5.3 路径安全与「路径非稳定契约」（写入接口语义）

- **【查证→推断】** 出参 `absPath` 必须逐条做 `isWithinRoot`-等价校验（§2.4），越界条目剔除 / 返回 `403` 且**绝不把越界路径写进响应**（对齐 `src/main/protocol.ts:117-119` 的 403 纪律）。
- **【查证】** `Asset.folder` 无一致性保证者（`docs/16:100`）；改分类 / 改名 / 移库 / rescan 都会让旧路径失效（`:93-95`、`:114-125`）→ E2 / E3 约定「**每次现取、不缓存**」，并把 `410 GONE` 作为一等失败语义。**E2 每次搜索本身就是一次现取**，与原文「搜词 → 返回绝对路径列表」的极简主线天然兼容。
- **【推断】** 插件侧拿到路径后应**立刻读取/插入**，不做长期引用；若 DCC 工程文件里要记录来源，建议记 `assetId` + `apiVersion` 而非绝对路径，路径用时再用 E3 解析。

### 5.4 明确不进 MVP 的能力

封面/缩略图字节流（若将来要给，优先复用 `vault://` 而非在 HTTP 里传图）、标签/风格/评分等元数据筛选、按内容哈希判重（`docs/27:85-94` 明确本轮不做）、交互式重复裁决弹窗（跨进程未解，见 E4）、批量回写分类、远程/局域网访问（J1 / `docs/13:138-146` F-07/F-08 一票否决）、云同步。
