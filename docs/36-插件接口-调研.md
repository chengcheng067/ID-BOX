| J1 | **本地优先、数据敏感**：任何形态都不能把「用户素材库的绝对路径清单」泄露给未授权的本机程序或浏览器网页 | `README.md:212`、`:284-289`；`docs/25:2130`、`:2132` |

## 2. 现状盘点：为什么必须新增一条「主进程侧查询通道」

### 2.1 三层与进程边界（【查证】）

| 层 | 持有什么 | 对外可见面 |
| --- | --- | --- |
| `renderer` | `assets[]`（Zustand）、**Dexie/IndexedDB（元数据唯一权威）** | 只能经 `preload` 白名单 |
| `preload` | `contextBridge.exposeInMainWorld('modvault', api)` | `window.modvault.*`，**只有本应用渲染进程能用** |
| `main` | `settings.json`、`fs` / `7z` / 缩略图、`vault://` 协议、`ipcMain.handle` | 只接 IPC；**拿不到 Dexie** |

证据：`src/preload/index.ts:480`、`src/shared/ipc.ts:1-5`、`docs/25:2111-2115`、`docs/16:44-51`、`:78-87`。

### 2.2 关键结论

1. **【查证】** `window.modvault.*` 是 IPC，不是外部接口（`docs/25:2113`）。外部进程要读库，必须新增一条 **主进程侧的查询通道**，或让外部直接读 IndexedDB —— 后者被明确否定：「库 schema 会变，插件必然跟着碎」（`docs/25:2115`）。
2. **【查证】** `Asset.folder` 是**绝对路径**，插件真正想要的只是「一组绝对路径」（`docs/25:2117-2120`）。这是 MVP 能做极简的天然优势。
3. **【查证·风险】** 但绝对路径**不是稳定契约**：`docs/16:100` 明写「`Asset.folder` 的一致性**没有任何保证者**，只有约定」；改分类 / 改名 / 移库 / `rescan` 都可能让旧路径失效或旧记录被「删旧建新」（`docs/16:93-95`、`:114-125`）。→ **插件不得长期缓存路径，每次取用应重新解析**（写入 §5.3 的接口语义）。
4. **【查证】** 主进程已有只读扫盘能力（`rescanLibrary(settings.libraryDir)`，`src/main/index.ts:1529`）且「分类层级以磁盘为权威」（`docs/16:108`、`:131`）—— 这是「不依赖 Dexie 也能列出资产」的现成地基，但**拿不到 `tags/note/styles` 等只在索引里的元数据**（`docs/16:108`）。

### 2.3 可复用的既有地基（不必从零造）

| 既有能力 | 位置 | 对插件接口的意义 |
| --- | --- | --- |
| 拖出到 DCC（`drag:start`） | `src/shared/ipc.ts:42-48`；`src/main/index.ts:1552-1561` | 已验证「把库内绝对文件路径交给外部建模软件」这条路走得通 |
| 路径根守卫 `isWithinRoot` | `src/main/ipcGuard.ts:128-139`；`shared/vault.ts` 同名实现 | **对外接口的路径出参必须照抄这套校验**（见 §2.4） |
| `vault://` CORS / 越界校验 | `src/main/protocol.ts:84-130` | 若将来要让 DCC 侧读缩略图，可复用；也说明本仓库已有「自定义协议 + 白名单 host + 越界 403」的经验 |
| `openExternal` 仅 `http/https` 白名单 | `src/shared/ipc.ts:160-165` | 深链/外链形态的既有「协议白名单」纪律 |
| 导入判重 + 批次串行锁 | `docs/27:19-41`（D01/D18/D19/D22） | `POST /import` 的幂等与失败语义直接对齐它 |
| `chokidar` + 监控目录自动导入 | `package.json:22`；`docs/27:37` | 「约定目录 + watcher」形态**已有运行地基** |

### 2.4 破坏性通道的现有防护思路（对外接口必须继承）

【查证】`src/main/ipcGuard.ts` 的守卫哲学（`:1-45`、`:116-139`、`:186-234`）：

- **渲染层是「同源但不可信」的** —— 这条对**外部插件同样成立，且更甚**：外部进程比渲染层更不可信。
- `isWithinRoot(root, target)`：**deny by default**；要求绝对路径（`C:\` / UNC / POSIX 根），拒相对路径；归一化后消 `..` 穿越；**无条件小写**（Windows 大小写不敏感）；前缀必须带分隔符（`C:\lib` 不匹配 `C:\lib2`）；**永不抛异常**。
- `guardTrashPaths` 还有三类额外禁令（库根本身 / 大类目录 / `.trash`·`.staging`）—— 说明「只读接口」与「可写接口」要分开设计，写接口必须更窄。
- `src/main/index.ts:1146-1188` 把 `openPath` / `reveal` / `trashPaths` 三条破坏性通道逐一套上守卫；`drag:start` 也用 `isWithinRoot` 校验（`:1561`）；`protocol.ts:117` 对三个目录一视同仁做越界 403。

> **结论（【推断】但强建议）**：未来任何对外接口，**出参只返回库内绝对路径且经 `isWithinRoot` 复核**；入参一律当 `unknown` 处理、永不抛；**只读端点与写入端点分开设鉴权等级**。这不是新发明，是把 `ipcGuard.ts` 的既有纪律外推一层。

## 4. 协议形态取舍与鉴权风险

> 本节回答 `docs/25:2129-2134` 的三个设计问题之「协议形态」与「鉴权」，以及「取用语义」。
> **四种形态**：① 本地 HTTP/REST（localhost + token）② 自定义 URL scheme / 深链 ③ 约定目录 + 文件监视（watcher）④ 命名管道。
> 安全性四项按任务要求逐项过：**未授权本地调用 / CSRF / token 泄露 / 端口占用**；再加**跨平台（当前仅 Windows）**与**实现成本**。

### 4.1 四种形态定义（【推断】为主，附查证点）

| 形态 | 怎么工作 | 本仓库相关地基 |
| --- | --- | --- |
| ① localhost HTTP/REST | 主进程 `http.createServer` 绑 `127.0.0.1:<port>`，JSON over HTTP，插件带 token 调端点 | 主进程是 Node 20，可起服务【推断】；`rescanLibrary` 可作数据源（§2.2） |
| ② URL scheme / 深链 | 注册 `idbox://` 之类 scheme，DCC 拼 `idbox://search?q=...` 唤起 ID BOX 并把参数带进来；结果靠「回写文件 / 剪贴板 / 再次深链」返回 | **【查证】** 本仓库已有 `registerSchemesAsPrivileged` + `protocol.handle` 实战（`src/main/protocol.ts:35-75`）；**`app.setAsDefaultProtocolClient` / Windows 下 `second-instance` 事件取 URL【待核实】**（见 §4.6） |
| ③ 约定目录 + watcher | 双方约定一个交换目录：插件写 `request.json`，ID BOX 用 watcher 读到后写 `response.json`；零监听端口 | **【查证】** `chokidar ^4.0.3` 已装（`package.json:22`）、已有「监控目录自动导入」（`docs/27:37`） |
| ④ 命名管道 | 主进程 `net.createServer` 监听 `\\.\pipe\idbox`，插件连管道做请求/响应 | **【推断】** Node `net` 在 Windows 支持命名管道路径；未核实（§4.6） |

### 4.2 逐项对比表（核心决策依据）

> 安全性结论多为**【推断】**（基于通用安全机制推理，非本仓库实测）；「实现成本」沿用 `docs/13:24` 的 **小(S) / 中(M) / 大(L)** 量级思想，**只给档位、不给天数**。

| 维度 | ① localhost HTTP + token | ② URL scheme / 深链 | ③ 约定目录 + watcher | ④ 命名管道 |
| --- | --- | --- | --- | --- |
| **未授权本地调用** | 🔴 端口开着，**同机任何进程**都能连；绑 `127.0.0.1` 只能挡外部网段，挡不住本机恶意程序。**必须有 token**【推断】 | 🔴 **任何本机程序/网页**都能拼 `idbox://` 唤起；scheme 本身**无鉴权**，参数可被伪造【推断】 | 🟢 **无监听端口**，攻击面最小；但任何能写交换目录的程序可伪造请求，需目录权限 + 请求签名【推断】 | 🟢 管道可设 ACL / 仅当前用户会话，比 TCP 端口收敛【推断，待核实 ACL 细节】 |
| **CSRF / 浏览器侧** | 🔴 本机浏览器里**任意网页**可对本机端口发简单请求（`<img>`/`form`/`fetch`）；**DNS rebinding** 可绕过 `127.0.0.1` 绑定【推断】。防护：校验 `Host`/`Origin`、token 放**自定义头**（不放 Cookie，避免自动携带）、CORS 默认拒绝、只认 `Content-Type: application/json` | 🔴 恶意网页可直接 `<a href="idbox://...">` 触发唤起，等于**无鉴权的远程触发面**【推断】 | 🟢 浏览器无法直接写本地约定目录，CSRF 面几乎为零【推断】 | 🟢 浏览器连不上命名管道【推断】 |
| **token 泄露** | 🟡 token 需落到插件配置/文件里才能被 DCC 读到 → **任何能读该用户目录的程序可读**【推断】；且 token 若进 URL/日志易泄。缓解：随机高熵、可一键轮换、只绑 loopback、短时握手 | 🟡 深链参数会出现在**命令行/浏览器历史/日志**里，塞 token 反而更容易泄【推断】 | 🟢 可完全无 token（靠目录权限）；若加签名，密钥同样要落盘【推断】 | 🟢 可无 token（靠管道 ACL）；若要 token 同 ① 的落盘问题【推断】 |
| **端口占用** | 🔴 **固定端口会被别的程序占用 / 被防火墙拦**；随机端口则插件要先发现端口（写端口文件 / 探测 `/health`）【推断】；已有单实例锁 → 多实例谁监听要明确（§2.1） | 🟢 无端口（OS scheme 注册表）【推断】 | 🟢 无端口 | 🟢 无端口；但**管道名冲突**是同类问题【推断】 |
| **跨平台（当前仅 Windows）** | 🟢 HTTP/TCP 跨平台最自然；当前仅 Windows（`README.md:474`），未来若跨平台**这一项迁移成本最低**【推断】 | 🟡 scheme 注册方式各 OS 不同（Windows 注册表 / macOS `open-url` / Linux desktop 文件）【推断，待核实】 | 🟢 目录 + watcher 跨平台通用；`chokidar` 本身跨平台【查证，`package.json:22`】 | 🔴 **Windows 命名管道是平台能力**；macOS/Linux 要换 Unix domain socket，等于另写一套【推断】—— 与「仅 Windows」现状一致，但堵死未来跨平台 |
| **双向/实时性** | 🟢 请求-响应同步，插件能「搜了立刻拿结果」 | 🔴 **天生单向**（DCC→ID BOX）；要把结果送回 DCC 得再配一条回路（回写文件 / 剪贴板 / 反向深链），链路最绕【推断】 | 🟡 异步轮询，**要等导出/落盘**，延迟高（`docs/25:2132` 已点出「零服务，但要等导出」） | 🟢 全双工、低延迟 |
| **可调试性 / 跨语言** | 🟢 curl/浏览器直接调，JSON 跨语言（三个 DCC 都能发 HTTP） | 🟡 靠日志与唤起链路，难调试 | 🟡 看文件，好排查但无请求语义 | 🔴 需要管道客户端，各语言支持不一（Ruby/MAXScript 侧要自己实现）【推断】 |
| **实现成本** | **小~中**：主进程起 http server + 复用现有扫盘/守卫；插件侧各 DCC 都有 HTTP 客户端（§3） | **中**：scheme 注册 + 参数解析 + 结果回送回路；DCC 侧拼 URL 简单但取结果麻烦 | **小**：复用 `chokidar` + 既有监控目录导入；但要定义请求/响应文件格式与并发/幂等 | **中~大**：主进程管道服务 + **每个 DCC 各写一套管道客户端**；且 Windows 专属 |
| **与 J1（本地优先·数据敏感）** | 🟡 需要用户显式「允许插件访问」开关才安心 | 🟡 唤起即暴露存在性 | 🟢 最贴合「零服务」直觉 | 🟢 贴合，但平台绑定 |
| **与 J2（稳定契约）** | 🟢 端点即契约，版本化容易 | 🔴 参数即契约，难版本化 | 🟡 文件 schema 即契约，会演化 | 🟢 同 HTTP |

### 4.3 鉴权模型（若选 ①，【推断】的设计草案，非实现）

| 项 | 建议 | 理由 |
| --- | --- | --- |
| 绑定 | **只绑 `127.0.0.1`（IPv4 loopback）**，不绑 `0.0.0.0` | 挡外部网段（J1） |
| 开关 | 设置页一个**默认关闭**的「允许插件访问」总开关 + 显式「生成/轮换 token」按钮 | 用户数据敏感偏好（`docs/25:2132`）；默认关 = 不开端口 |
| token | 高熵随机（如 128bit+），**放自定义请求头**（如 `X-IDBOX-Token`），**绝不放 Cookie / URL query** | 避免浏览器自动携带与 CSRF、避免进日志【推断】 |
| 请求校验 | 校验 `Host` 必须是 `127.0.0.1:<port>`、拒绝非预期 `Origin`、CORS 默认拒绝、只收 `application/json`、拒绝非 `GET`/白名单 `POST` | 缓解 DNS rebinding / CSRF【推断】 |
| 生命周期 | 应用退出即关服务；应用未启动 → 插件调 `/health` 失败并给「请先启动 ID BOX」 | 随主进程生命周期 |
| 轮换/撤销 | 设置页一键轮换，旧 token 立即失效；插件侧需重新粘贴 | 泄露后可止损 |
| 分发 | **【待核实/待拍板】** token 怎么到插件手里：① 设置页「复制连接串」由用户粘贴进插件配置 ② 写入 `%APPDATA%/idbox/` 下受限文件由插件读 —— 见 Q3 | 两者都有落盘泄露面【推断】 |

### 4.4 「取用」语义（`docs/25:2133-2134`）

| 方案 | 描述 | 取舍 |
| --- | --- | --- |
| **A. 给路径，DCC 自己 import**（建议 MVP） | ID BOX 只返回绝对路径；插件调 `definitions.load` / `mergeMAXFile` / `bpy.ops.wm.append` | 简单、耦合轻、跨三个 DCC 统一；**写操作完全不进接口**。**【推断】** 与 `docs/25:2119` 的「只暴露搜词 → 返回绝对路径列表」一致 |
| **B. ID BOX 主动 push** | ID BOX 通过某种通道把素材「送进」正在运行的 DCC | 能做「拖出到 SU 那种体验」，但要 DCC 侧常驻监听器 + 跨进程唤起，**耦合重**【推断】；`docs/25:2134` 已点明 |

> **需拍板 · Q4**：MVP 是否锁定「方案 A（只给路径）」？建议默认 **是**，把 B 留到「插件内主动搜」跑顺之后再评估。

### 4.5 建议（**建议，不代替拍板**）

- **主形态建议 ① localhost HTTP + token**：三个 DCC 都有可用的 HTTP 客户端（§3），请求-响应同步、可调试、跨语言、未来跨平台成本最低；风险（本机端口 / CSRF / token 泄露）**可用 §4.3 的开关 + 校验收敛**，且这些防护思路是 `ipcGuard.ts` 既有纪律的外推（§2.4）。
- **③ 约定目录 + watcher 建议作为「零服务兜底/降级路径」保留**：它已有 `chokidar` 与监控目录导入地基（§2.3），安全性最好、最贴合「本地优先」，但异步、要等落盘，不适合「在 DCC 里搜了立刻插入」的主体验。
- **② 深链不建议做主通道**：天生单向、参数无鉴权、结果回送链路最绕；**可作为「从 DCC 一键唤起 ID BOX 并定位到某资产」的辅助入口**另案评估【推断】。
- **④ 命名管道不建议第一批**：每个 DCC 要各写一套管道客户端，且 Windows 专属，与「未来可能跨平台」冲突【推断】。

### 4.6 本节待核实项与核实方式

| 待核实项 | 核实方式 |

## 5. MVP 接口清单（≤5 个端点）

> 对齐 `docs/25:2143`「建议 ≤5 个端点」与 `docs/25:2119`「只暴露搜词 → 返回绝对路径列表」。
> **全部是设计草案，本轮不实现**；方法/参数/返回/失败语义/幂等性逐项给全。

### 5.0 统一约定（【推断】的设计草案）

| 项 | 约定 |
| --- | --- |
| 基址 | `http://127.0.0.1:<port>/v1`（`<port>` 由 ID BOX 启动时选定并写入发现文件；**端口发现方式属 Q2/Q3**） |
| 鉴权 | 除 `/health` 外，所有端点须带 `X-IDBOX-Token`；token 未配置 / 开关关闭 → 服务不监听（§4.3） |
| 内容类型 | 请求 `application/json`（`GET` 用 query）；响应 `application/json; charset=utf-8` |
| 统一错误体 | `{ "ok": false, "error": { "code": "...", "message": "..." } }`；**HTTP 状态码 + `code` 双轨**，`code` 供插件分支 |
| 统一成功体 | `{ "ok": true, "data": ... }` |
| 路径出参 | **只返回库根内的绝对路径**，逐条经 `isWithinRoot`-等价校验（§2.4）；返回 `folder` 时附带 `verifiedAt` 时间戳 |
| 只读优先 | E1/E2/E3/E5 全只读；**唯一写端点 E4 单独设更严校验**（见 §5.1 E4） |
| 失败不抛 | 对齐本仓库 IPC 纪律（`src/shared/ipc.ts:157-158`「永不 reject」、`src/main/ipcGuard.ts:100-114`「永不抛」）：接口失败一律结构化返回，不抛裸异常 |

### 5.1 五个端点

#### E1 · 健康检查 `GET /health`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/health` |
| 参数 | 无（**免 token**，供插件做「ID BOX 是否在运行 / 端口是否对」的探测） |
| 返回 | `200 { ok:true, data:{ appVersion, apiVersion:"1", libraryReady:boolean, readOnly:boolean } }` |
| 失败语义 | 连接被拒 / 超时 = **ID BOX 未启动或开关关闭**，插件提示「请先启动 ID BOX 并开启插件访问」；`libraryReady:false` = 库目录未配置/不可读，插件应禁用取用按钮（不报错） |
| 幂等性 | **幂等**（纯读，无副作用） |
| 备注 | `appVersion` 可复用既有 `app:getVersion`（`src/shared/ipc.ts:153`）；`readOnly` 表示当前是否允许 E4 |

#### E2 · 列出/搜索可导入资产 `GET /assets`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/assets` |
| 参数 | `q?: string`（关键词，匹配资产名/路径）、`kind?: model\|texture\|cad\|hdri\|material`（对齐大类口径）、`ext?: string`（如 `skp` / `max` / `jpg`）、`limit?: number`（默认 50，上限 200）、`offset?: number` |
| 返回 | `200 { ok:true, data:{ total, items: AssetBrief[] } }`；`AssetBrief = { id, name, kind, category1, category2, primaryExt }` —— **刻意不含绝对路径**（路径单独走 E3，见下方「为什么拆开」） |
| 失败语义 | `400 INVALID_PARAM`（`limit` 越界 / `kind` 非法枚举）；`401 UNAUTHORIZED`（token 缺失/错）；`503 LIBRARY_UNAVAILABLE`（库目录不可读 / 取数源不可用）；`q` 为空 = 返回全部（按 `limit` 分页） |
| 幂等性 | **幂等**（纯读；同一时刻重复调用结果一致，但库内容变化后结果自然变化） |
| 备注 | **为什么 E2 不直接给路径**：把「列表」与「取路径」拆开，才能让「取路径」这一步每次都重新校验 `isWithinRoot` 且强制插件不缓存路径（§2.2 第 3 条）。数据源约束见 §5.2 |

#### E3 · 取资产落盘路径 `GET /assets/{id}/path`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/assets/{id}/path` |
| 参数 | 路径参数 `id`（E2 返回的 `id`）；query `role?: primary\|textures\|all`（缺省 `all`） |
| 返回 | `200 { ok:true, data:{ id, folder, verifiedAt, primaryFile, files: [{ rel, absPath, ext, kind }] } }`；**`absPath` 逐条经库根校验**，材质类给贴图文件路径、模型类给 `.skp`/`.max` 路径（对齐 `docs/25:2119-2120`） |
| 失败语义 | `404 NOT_FOUND`（`id` 不存在 / 已被 rescan 删旧建新）；`410 GONE`（记录还在但**磁盘路径已失效**——对应 `docs/16:124`「索引有/盘无」）；`403 OUT_OF_ROOT`（路径越界，守卫拒绝，**绝不返回**）；`503 LIBRARY_UNAVAILABLE` |
| 幂等性 | **幂等**（纯读）；但**返回值不是稳定契约** —— 改分类/改名/移库/rescan 后可能变 `410`，**插件必须每次现取、不得缓存**（§2.2） |
| 备注 | 这是「给路径让 DCC 自己 import」（§4.4 方案 A）的落点。若选方案 A，E3 是 MVP 的核心端点 |

#### E4 · 触发导入 `POST /import`（**唯一写端点**）

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `POST /v1/import` |
| 参数 | body `{ paths: string[], requestId?: string, classifyHint?: { category1?, category2? } }`；`paths` = 插件侧要送进库的**源文件绝对路径**（例如 DCC 里当前用的贴图/模型另存路径） |
| 返回 | `202 { ok:true, data:{ batchId, accepted, results: [{ src, status:"done"\|"skipped"\|"failed", assetId?, reason? }] } }`（异步批次语义对齐既有 `import:event` / `import:batchDone`，`src/shared/ipc.ts:7-8`、`:171-172`） |
| 失败语义 | `400 INVALID_PATH`（非绝对路径 / 文件不存在 / 非法类型）；`403 OUT_OF_ROOT`（**入参路径越界** —— 但注意：源文件在库外是**正常业务**，故这里的守卫应是「允许读的源」白名单而非「必须在库内」，与 `ipcGuard.ts` 的库内校验语义不同，属 **【待核实/待拍板】**，见下方风险）；`409 CONFLICT`（重复资产需用户裁决 —— 对齐 `docs/27` 的 `ImportConflictAsk`，但**跨进程弹窗怎么呈现是未解问题**）；`409 DUPLICATE_REQUEST`（同一 `requestId` 重复提交）；`423 BUSY`（已有导入批次在跑，对齐 `docs/27:36` 批次串行锁 D18）；`503 IMPORT_UNAVAILABLE` |
| 幂等性 | **条件幂等**：带 `requestId` 时，相同 `requestId` 重复调用返回首次结果、不重复落盘（对齐 `docs/27:36` 串行锁 + `docs/27:19-21` 判重键 `zhimoId`/`dedupeKey`）；不带 `requestId` **不保证幂等**，重复调用可能产生 `-2` 副本（`docs/27:32` D14） |
| 备注 / 风险 | **这是本清单里最该谨慎的一个端点**：① 判重快照 `ctx` 目前由**渲染层**在调用 `importPaths` 时传入（`docs/27:40` D22、`src/preload/index.ts:63-70`），而服务跑在**主进程**（读不到 Dexie）→ **主进程侧要触发完整导入链，必须先解决取数/回传问题**（§5.2），否则只能退化成「不判重的旧行为」（`docs/27:39` D21）；② 重复弹窗（`docs/27:24-27` D06-D08）是**进程内 UI**，跨进程插件触发时怎么让用户裁决 **【待核实/待拍板】** → 建议 **MVP 阶段 E4 固定走「跳过重复 + 不弹窗」**（对齐 `docs/27:37` D19 watcher 自动导入「不问」的口径），把交互式裁决留到后续。**③ 因此 E4 建议列为「最后开、且可先不开」的端点**。 |

#### E5 · 查询分类词表 `GET /taxonomy`

| 项 | 内容 |
| --- | --- |
| 方法/路径 | `GET /v1/taxonomy` |
| 参数 | `kind?: model\|texture\|cad`（缺省返回全部大类的精简结构） |
| 返回 | `200 { ok:true, data:{ version, kinds: [{ kind, level1: [{ name, level2: [string] }] }] } }`；**只读快照**，不含自定义词条以外的运行时状态 |
| 失败语义 | `400 INVALID_PARAM`（非法 `kind`）；`401 UNAUTHORIZED`；`503 TAXONOMY_UNAVAILABLE` |
| 幂等性 | **幂等**（纯读快照） |
| 备注 | 词表唯一真相源是 `src/shared/taxonomy.ts`（`README.md:278`）、历次修订见 `docs/06`；**插件拿词表只用于展示/回写分类提示，不得反过来改本地词表**（词表纪律：`README.md:78`、`:295-299`）。回写分类若要做，须走 Q7 |

### 5.2 硬约束：主进程侧「谁能读库」（**必须拍板 Q1**）

【查证】服务若跑在**主进程**，而 `Dexie` 在**渲染进程**（`docs/25:2112`、`docs/16:141`），则 E2/E3/E5 的取数只有三条路：

| 方案 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 主进程只读扫盘** | 复用 `rescanLibrary` 的深度遍历（`src/main/index.ts:1529`），按「磁盘是分类权威」（`docs/16:108`）产出 `id/name/kind/路径` | 不依赖窗口存活、不改 IPC 面、纯只读最安全 | **拿不到 `tags/note/styles/别名`**（只在 Dexie）；搜索只能靠文件名/路径；`rescan` 的「删旧建新」语义（`docs/16:114-125`）要小心别在接口里触发 |
| **B. 新增一条 IPC 让渲染层回传** | 主进程收到 HTTP 请求 → 新增 `plugin:query` 通道问渲染层 → 渲染层查 Dexie 回传 | 元数据完整、复用既有查询逻辑 | **依赖窗口存活**（应用最小化/窗口关闭时是否仍可用待核实）；新增通道要同时改 `shared/ipc.ts` + `preload/index.ts` + `main/index.ts` 三处（`src/shared/ipc.ts:1-5` 的既有纪律）；与单实例/窗口生命周期耦合 |
| **C. 主进程直接读 IndexedDB 文件** | 解析 Chromium LevelDB | —— | **明确不做**：`docs/25:2115` 已否定「直接读 IndexedDB」（schema 会碎），且格式私有、风险最高 |

> **建议（【推断】，待 Q1 拍板）**：MVP 走 **A**（只读扫盘，最贴合「只给路径」的极简契约），把 B 作为「将来要按标签/风格搜索」时的升级路径。**理由**：J2（不暴露 schema）+ J3（只读优先）+ 不新增 IPC 面。代价是「搜词」只能匹配文件名/路径 —— 这与 `docs/25:2119` 的 MVP 设想一致。

### 5.3 路径安全与「路径非稳定契约」（写入接口语义）

- **【查证→推断】** 出参 `absPath` 必须逐条做 `isWithinRoot`-等价校验（§2.4），越界返回 `403` 且**绝不把路径写进响应**（对齐 `src/main/protocol.ts:117-119` 的 403 纪律）。
- **【查证】** `Asset.folder` 无一致性保证者（`docs/16:100`）；改分类/改名/移库/rescan 都会让旧路径失效（`:93-95`、`:114-125`）→ E3 约定「**每次现取、不缓存**」，并把 `410 GONE` 作为一等失败语义。
- **【推断】** 插件侧拿到路径后应**立刻读取/插入**，不做长期引用；若 DCC 工程文件里要记录来源，建议记 `assetId` + `apiVersion` 而非绝对路径，路径用时再用 E3 解析。

### 5.4 明确不进 MVP 的能力

封面/缩略图字节流（若将来要给，优先复用 `vault://` 而非在 HTTP 里传图）、标签/风格/评分等元数据筛选、按内容哈希判重（`docs/27:85-94` 明确本轮不做）、交互式重复裁决弹窗（跨进程未解，见 E4）、批量回写分类、远程/局域网访问（J1 / `docs/13:138-146` F-07/F-08 一票否决）、云同步。

## 6. 先做 SketchUp：落地路径与工作量

> 工作量口径：沿用 `docs/13:24` 的 **小(S)/中(M)/大(L)** 量级思想，**只给「小 / 中 / 大」档位，不给精确天数**（按要求）。档位含义：**小**≈纯脚本/纯配置、不动主进程；**中**≈要动主进程或新增一条通道；**大**≈新机制/跨进程写路径/多版本矩阵。这是**量级**，不是工时承诺。
> 阶段顺序与任务要求一致：**P1 Ruby 扩展骨架 → P2 与 ID BOX 建立通信 → P3 拖入/插入模型 → P4 回写分类或来源标记**。

### P1 · Ruby 扩展骨架

| 项 | 内容 |
| --- | --- |
| 目标 | 一个能在目标 SketchUp 里安装、出现在 Extensions 菜单/工具栏、点开有面板（哪怕只有一个搜索框和列表）的 Ruby 扩展 |
| 前置依赖 | §3.1 的**待核实项先清掉**（扩展注册类名 / Plugins 目录 / 目标 SU 版本）；确认 SU Ruby API **主线程**约束（`ruby.sketchup.com/index.html`） |
| 工作量 | **小** |
| 主要产出 | `.rb` 骨架 + 注册文件 + `UI::Command`/`UI::Toolbar`/`UI::HtmlDialog` 面板（`UI.html` 已查证）+ 「未连上 ID BOX」的降级文案 |
| 风险 | SU 版本矩阵（库内存在 `sketchup 2014` 记录，`docs/25:174`）；4.x 与老版本 API 差异【待核实】 |
| 验收口径 | 在目标 SketchUp 里能启用/停用扩展、面板能打开关闭、不报错；**此阶段不连 ID BOX** |

### P2 · 与 ID BOX 建立通信

| 项 | 内容 |
| --- | --- |
| 目标 | 扩展用 `Net::HTTP` 调 E1 `/health` 与 E2 `/assets`，把列表渲染进面板；能处理「ID BOX 没开 / 开关没开 / token 错」三种失败 |
| 前置依赖 | **P1** + **§4 的协议形态拍板（Q2）** + **§5.2 取数方案拍板（Q1）** + **Q3 token 分发方式**；主进程侧起服务（属 ID BOX 侧改动，本轮不实现） |
| 工作量 | **中**（ID BOX 侧要新增「主进程查询通道」，是全新对外面；SU 侧本身仍是小） |
| 主要产出 | 连接设置（host/port/token 从配置读）、`/health` 探测、搜索框 → 列表、统一错误提示 |
| 风险 | 端口发现 / token 落盘泄露（§4.3）；CSRF/DNS rebinding 防护要在 ID BOX 侧落地（§4.3）；**这是第一次把主进程暴露给外部进程**，必须继承 `ipcGuard.ts` 的 deny-by-default 纪律（§2.4） |
| 验收口径 | ID BOX 关闭时插件给清晰提示；开启后能在 SU 面板里搜到库内资产名；用错 token 得到 `401` 而非崩 |

### P3 · 拖入 / 插入模型（**MVP 建议止于此**）

| 项 | 内容 |
| --- | --- |
| 目标 | 选中列表项 → E3 取绝对路径 → `definitions.load(path)` 载入为组件 → `place_component` / `add_instance` 插入当前模型；贴图同理（材质 API 待核实） |
| 前置依赖 | **P2** + §3.1 三个**待核实**项（`Model#import` 边界、`place_component`/`add_instance` 官方签名、`Material#texture=`）；**取用语义拍板 Q4（建议方案 A：只给路径）** |
| 工作量 | **中**（SU 侧插入逻辑 + 主线程调度 + 失败回滚；ID BOX 侧若只加 E3 只读端点则是小~中） |
| 主要产出 | 「插入为组件 / 应用贴图」两个动作 + 插入失败（版本不兼容、文件被移动 → E3 的 `410 GONE`）的可读提示 |
| 风险 | ① **路径非稳定契约**（§5.3）：用户在 ID BOX 里改了分类/移库后插入失败；② SU 要求**主线程**改模型，`Net::HTTP` 结果必须切回主线程（§3.1，【查证】）；③ `.skp` 版本高于当前 SU 时载入失败【待核实】；④ 若真要做「从面板拖进视口」，drop 接管 API 待核实（§3.1），**MVP 用「点按钮插入」替代拖拽** |
| 验收口径 | 库内一个 `.skp` 能被插入当前模型且可 Undo；库内一张贴图能被应用到选中面（材质 API 核实后）；路径失效时给 `410` 友好提示而非静默白模 |

### P4 · 回写分类或来源标记

| 项 | 内容 |
| --- | --- |
| 目标 | 插件把「这条素材被哪个 DCC 工程取用过」或「建议分类」回写进 ID BOX（例如写入资产 `note` / 自定义来源标记，或调 E5 词表做分类提示） |
| 前置依赖 | **P3** + **Q7 拍板（要不要开写端点、写什么字段、字段命名/落库口径）** + 解决「主进程读不到 Dexie」的**写入回传**问题（比 §5.2 的只读更难：`docs/16:145-151` 显示现有写路径都是「main 改盘 → renderer 写库」的手工补偿，跨进程写会引入新的崩溃窗口） |
| 工作量 | **大** |
| 主要产出 | 一个受控的写端点（或写文件 + watcher 回灌）+ 字段口径 + 幂等键 |
| 风险 | ① **写路径无事务**（`docs/16:12-18`「地基评级 B−：没有事务性、没有失败恢复」）—— 跨进程写会放大 `docs/16:93` 的双写分叉风险；② 分类词表纪律（`README.md:78`、`:295-299`）不允许插件自造词条；③ 与 `docs/27` 导入判重/覆盖语义可能冲突；④ 隐私：来源标记会记录用户的工程文件路径（J1） |
| 验收口径 | 回写后 ID BOX 里能看到标记、重启不丢、重复回写不产生副本；**任何失败都不破坏既有资产记录** |

### 6.5 阶段依赖与建议停点

```
P1（小，独立可验收）
 └─ P2（中）← 依赖 Q1/Q2/Q3 拍板 + ID BOX 侧新增查询通道
     └─ P3（中，MVP 建议止于此）← 依赖 Q4 + §3.1 待核实项
         └─ P4（大）← 依赖 Q7 + 写路径事务问题（建议单独立项，不塞进 MVP）
```

> **建议**：MVP **做到 P3 就停**，P4 单独立项。理由：P4 触碰「主进程↔渲染层双写无事务」这个 `docs/16` 已标红的地基问题，且与「只读优先」（J3）冲突 —— 不该在插件接口的第一版里同时解决两件事。**用户 `docs/25:2101` 的原话是「只做调研，之后再做」，本轮连 P1 都不做**（§7）。
