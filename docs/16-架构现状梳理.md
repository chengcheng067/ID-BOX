## 0. 地基评级与三句话结论

> ### 地基评级：**B−**（能用、边界干净，但**没有事务性、没有失败恢复**）
>
> **① 分层扎实**：`shared` 零 `node:`/`electron`、`renderer` 零 `main` 依赖、全仓 0 个 `any`。
> **② 薄弱点不在组织，在写路径**：磁盘由 main 改、索引由 renderer 改，只靠 IPC 返回值对齐，两侧都没有日志。
> **③ 最危险的是正常操作**：导入队列里点「更改库目录」会**自动重扫**（`ImportQueue.tsx:20-28`），空目录一扫描 → 全库索引 `bulkDelete` → 元数据永久丢失。

**一句话**：这是一套"能跑、能测、边界干净"的实现，缺的不是抽象，是**写路径的原子性与恢复能力**。

## 4. Q3：磁盘是唯一真相，还是索引是唯一真相？

### 4.1 一句话结论

**都不是。分层真相**：**分类层级以磁盘为权威（rescan 覆盖索引），元数据以索引为权威（磁盘没有 tags/note/styles），`kind` 以文件内容为权威（`primaryKind`）**。三套权威之间没有事务，靠 rescan 单向对账；因此"能自愈"仅限**路径未变**的场景。

### 4.2 三条写路径的时序

| 路径 | 磁盘（main） | 索引（renderer/Dexie） | 顺序 | 中断后果 |
| --- | --- | --- | --- | --- |
| **导入**（`importer.ts:154-391`） | 解压到 `.staging` → 移入 `<大类>/<一级>/<二级>/<名>` | 收到 `status:'done'` 事件后 `db.assets.put`（`store.ts:466`） | 盘先、索引后（异步事件） | 盘有、索引无 → **下次 rescan 自动补回**（新 UUID、元数据本来就空）。**可自愈** |
| **改分类/改名**（`store.ts:595-652`、`989-1011`） | `assignCategory` 逐个 `fs.rename` | 循环结束后**一次性** `bulkPut`（`:649`） | 盘先、索引后（**批量尾部**） | 中途死 → 前 N 个盘已搬、索引仍指旧路径 → rescan 视为 gone **删除**（tags/note/styles 丢）。**不可自愈** |
| **材质合并**（`main/materialMerge.ts:392-528` + `store.ts:864-972`） | 逐资产 rename + manifest 逐项落盘 | 全部完成后**单事务** `put`（`store.ts:928-930`） | 盘先、索引后（**全量尾部**） | 中途死 → 同上；但 **manifest 有 assetId + prevRelFolder + DB 备份快照**，理论上可人工/半自动复原（**目前无恢复入口**，见 §5-dead#10） |
| （补）**重扫**（`rescan.ts:120-245`） | 只读 | 以 `folder` 为键 merge；匹配不上的本地记录 `bulkDelete`（`store.ts:1048-1050`） | 索引单向覆盖 | 它是"对账器"，但**没有差异确认**，直接把"索引有、磁盘无"判死刑 |

### 4.3 四象限（谁会出现在哪）

| 情形 | 会不会发生 | 现状表现 | 自愈 |
| --- | --- | --- | --- |
| 盘有 / 索引无 | ✅ 会（导入事件丢失、用户在资源管理器拷入资产、索引被清后） | UI 不可见 | ✅ rescan 补回（**新 UUID、元数据空白**） |
| 索引有 / 盘无 | ✅ 会（用户在资源管理器删/改名目录） | **卡片还在、封面 404**、拖出/双击报错；`init()` 不做存在性校验（`store.ts:423-428`） | ❌ 只能手动 rescan（删记录） |
| 两边都有但路径不同（改名/移库） | ✅ 会（最危险） | 旧记录残留 + 新记录空白 | ❌ rescan = 删旧建新，**元数据丢** |
| 两边一致 | 常态 | 正常 | — |

### 4.4 关键代码证据

- `store.ts:1015-1017` 注释明写合并键是 `folder`，**"不能用 id"**；`1048-1050` 直接 `bulkDelete(gone)`。
- `store.ts:1038` 注释「分类以磁盘目录名为准（rescan 的权威语义）」——索引在分类维度上自愿放弃权威。
- `rescan.ts:120-131` 不校验大类目录名、不校验库身份，只按深度遍历。
- `SettingsDialog.tsx:374` 对用户的描述是「外部改动过（**改名、移动、删除**）的资产会同步更新」——**行为上实为"删旧建新"**，文案与实现不符（这是最容易被用户当成"数据丢了"的交互）。

## 5. Q4：Dexie 放在渲染进程，付了什么代价

### 5.1 一句话结论

代价不是性能（**Dexie 的索引一个都没用上**：全仓 0 处 `.where()/.orderBy()`，只有 `db.assets.toArray()` 全量读 + 内存过滤），而是**写者不在数据所在的进程**——于是出现 10 处"main 改完磁盘、把结果回传给 renderer 再写库"的手工补偿，每一处都是一个崩溃窗口。

### 5.2 "main 想改索引但改不了"的完整清单

| # | 场景 | main 侧产出 | renderer 侧落库 | 窗口期风险 |
| --- | --- | --- | --- | --- |
| 1 | 导入 | `Asset`（含新 UUID）经 `import:event` 推送 | `store.ts:466` `db.assets.put` | 事件丢失 → 盘有索引无（可 rescan 补） |
| 2 | 改分类 | `{folder,name,relFolder,category1/2,renamed}` | `store.ts:649` `bulkPut` | 🔴 批量尾部一次性写 |
| 3 | 改名 | 新 `folder` | `store.ts:989-1011` 重算 `relFolder` + `put` | 🟡 单条窗口小 |
| 4 | 重扫 | `Asset[]`（新 UUID）+ `ignored[]` | `store.ts:1049-1050` `bulkDelete`+`bulkPut` | 🔴 两个独立事务，中间死 = 索引半删 |
| 5 | 遗留布局迁移 | `{ok:[{id,to,relFolder}], failed}` | `store.ts:806-814` `bulkPut` | 🟡 与 #2 同族 |
| 6 | 材质大类合并 | `{moves:[{assetId,to,relFolderTo,renamed}]}` + manifest | `store.ts:928-930` 单事务 `put` | 🔴 全量尾部；但有 manifest/备份 |
| 7 | 封面图写盘 | `{rel}` | `store.setCover` → `put` | 🟢 孤儿文件可清 |
| 8 | 缩略图生成 | `{filename}` | `ensureMissingThumbs`/`setCover` → `put` | 🟢 可重生成 |
| 9 | 球图落盘 | `{filename}` | `renderBallThumbFor` → `put` | 🟢 可重生成 |
| 10 | **合并回滚** | `{ok, failed}`（`main/index.ts:586`、`materialMerge.ts:556`） | **无调用方**（`grep rollbackMaterialMerge src/renderer` → 空） | ⛔ 死通道：磁盘能回滚，**索引不能** |

### 5.3 可靠性评估

| 维度 | 现状 | 评价 |
| --- | --- | --- |
| 原子性 | 只有材质合并的 DB 写入用了 `db.transaction`（`store.ts:928`）；其余是 `put`/`bulkPut` 裸调用 | 部分有 |
| 写失败处理 | `commitAsset` 是 `void db.assets.put(...)`（`store.ts:330`）——**没有 `.catch`**；配额满/DB 被锁 → 未处理 rejection，内存已更新、磁盘没写 | ❌ 静默分叉 |
| 恢复 | 无 journal、无"待提交"标记、无启动对账；manifest 有数据但无消费方 | ❌ |
| 可测试性 | store 测试必须同时桩 `window.modvault` + `db`（`storeFlow.test.ts:25-45`），事务语义本身测不到 | 中 |
| 扩展性 | 单窗口单写者假设；多窗口/多实例无协调 | ❌ |

### 5.4 替代方案对比

| 方案 | 改动面 | 收益 | 风险/成本 | 建议 |
| --- | --- | --- | --- | --- |
| **A. 保持 Dexie + 写前日志（journal）+ 启动对账** | `store.ts` 新增 ~150 行；`db.ts` 加 1 张 `journal` 表（v4）；main 的迁移/改分类结果先写 journal 再执行 | 把"崩溃窗口"从"全量尾部"缩到"单条 + 可重放"；恢复能力从 0 到 1 | 小，纯增量 | ✅ **先做这个** |
| **B. 索引迁到 main（better-sqlite3）** | IPC 全面改造（40 个接口里 ~15 个改语义）、Dexie→SQLite 迁移、打包体积 +（原生模块）、renderer 改订阅 | 单写者 + 真事务 + 查询下推 + 多窗口天然安全；`Asset.files` 不必全量进内存 | 大（约 3-5 天 + 打包风险），且**当前没有查询性能需求**（无 `.where`） | ⏳ 等"多窗口/团队库/万级资产"任一成立再做 |
| **C. 独立 index worker/子进程** | 中 | 隔离 IO | 仍然是两写者，没解决根因 | ❌ 不推荐 |

**判据**：如果下一步要做 F-07 局域网共享 / F-08 云同步 / 多窗口，**必须**先做 B；如果继续单机单窗口，A 足够，B 属于过度设计。

## 6. Q5：`store.ts` 1,521 行怎么切

### 6.1 一句话结论

它不是"一坨"，是**10 个职责清楚但住在一个文件里的模块**；拆分是**纯机械移动 + `store.ts` 变 re-export 壳**，零 API 变更、零组件改动，收益是"以后每次改功能只碰 1 个 ≤300 行的文件"（这个项目没有 git，冲突成本比常规项目更高）。

### 6.2 职责分块（按当前行号实测）

| # | 块 | 行号 | 行数 | 关键耦合点 |
| --- | --- | --- | --- | --- |
| B1 | 导入 + 模块常量 + 视图类型 | 1-192 | 192 | 无（纯声明） |
| B2 | `VaultState` 接口（状态 + 全部 action 签名） | 193-318 | 126 | 所有块的类型契约 |
| B3 | 基础设施：`upsert` / `commitAsset` / `regenThumbSweep` / 合并探测去重 / `bootstrapMigrations` | 319-403 | 85 | **被 B5-B9 全部引用** |
| B4 | 初始 state + `init()` + 导入事件订阅 | 404-495 | 92 | 调 B3、B8、B9、B10 |
| B5 | 导入 | 496-515 | 20 | — |
| B6 | 删除四件套（确认/宽限/撤销/提交） | 516-594 | 79 | `commitDelete` 调 IPC + Dexie |
| B7 | 分类指派 + 拖拽撤销 + AI 归类 | 595-787、1147-1248 | 193 + 102 | 调 `regenThumbSweep`、`db.bulkPut`；AI 复用 `assignCategory` |
| B8 | 迁移（遗留布局 + 材质合并 + 探测） | 788-863、864-972 | 76 + 109 | 调 `planLegacyMoves`、`db.transaction`、`maybeAutoMigrate` |

| B10 | 设置 + 派生选择器 + 迁移调度 + 缩略图/球图队列 | 1129-1146、1274-1305、1296-1521 | 18 + 32 + 226 | 模块级单例（`ballQueue` 等） |

### 6.3 拆分方案（目标：单文件 ≤ 320 行，API 零变更）

```
src/renderer/store/
├ index.ts        # create<VaultState>() 组合各 slice + re-export 全部公共符号（~40 行）
├ types.ts        # B1 + B2：状态/action 契约、视图类型（~320 行，纯类型）
├ runtime.ts      # 模块级单例：thumbAttempted / ballQueue / ballAttempted / mergeProbeHandled / aiClassifyRunning（~40 行）
├ commit.ts       # upsert / commitAsset / regenThumbSweep（B3 的一半，~60 行）
├ init.ts         # B4 + importPaths（~115 行）
├ delete.ts       # B6（~80 行）
├ assign.ts       # B7 的指派 + 撤销（~195 行）
├ ai.ts           # B7 的 AI 归类（~105 行，依赖 get().assignCategory）
├ migrate.ts      # B8（~190 行）
├ assets.ts       # B9（~180 行）
├ settings.ts     # B10 的设置（~20 行）
└ thumbs.ts       # B10 的缩略图 + 球图队列 + 迁移调度（~230 行）
```

**保持 API 不变的三个技巧**：

1. `src/renderer/store.ts` 保留为一行 `export * from './store/index'` —— **13 个组件、6 个测试文件的 import 全部不用改**（`grep -rl "from '../store'" src/renderer` → 13；`grep -rl "renderer/store" tests` → 6。这是本项目做重构的唯一安全姿势：没有 git，改 import 就是大面积冲突）。
2. slice 之间**不互相 import**，只通过 `get().action()` 调用（Zustand 原生支持），避免循环依赖。需要跨块调用的仅 3 对：AI→assign、init→thumbs/migrate、rescan→migrate。
3. 模块级单例集中到 `runtime.ts`，并在 `init()` 里显式 `resetRuntime()`（顺带修一个现存问题：`thumbAttempted` 全仓只在 `add`，从不清空 → 同一会话内缩略图失败一次就永远不重试）。

### 6.4 拆 vs 不拆

| 维度 | 不拆（现状） | 拆 |
| --- | --- | --- |
| 单次改动半径 | 平均落在 1,521 行的文件里；多人并行必冲突（docs/14 §7 已把"store.ts 最易撞车"写进派单提醒） | ≤320 行/文件，冲突面按职责隔离 |
| 定位成本 | 需要先读 120 行 import+类型 | 文件名即职责 |
| 测试 | 现状可测（桩两个边界），拆分后不变 | 不变（这是关键：**拆分不改善测试**，只改善可维护性） |
| 风险 | 0 | 纯移动 + 1 行 re-export；687 条测试是安全网；预计 0.5 天 |
| 收益量级 | — | **中**（不解决任何一个 §9 风险，纯粹为后续 10 个功能候选降摩擦） |

**裁定：值得拆，但不该排在最前面**——它不降低任何现有风险，属于"做下一个功能之前顺手做"的重构。

## 9. Q8：三个最可能先塌的地方

排序依据：**发生概率 × 后果严重度**（不是"代码丑"）。

| 排名 | 塌点 | 概率 | 后果 | 评分 |
| --- | --- | --- | --- | --- |
| **①** | **切换库目录 → 自动重扫 = 全库索引与元数据永久丢失** | **中高**（UI 主动引导） | **极高**（tags/note/styles/封面/调参全没，且无备份） | 🔴🔴🔴 |
| **②** | **双实例并存 → 并发迁移/导入 + IndexedDB 锁 + settings 互相覆盖** | 中 | 高（索引错乱/半迁移/启动白屏） | 🔴🔴 |
| **③** | **跨进程写路径中断 → 索引/磁盘分叉 → 下次 rescan 把分叉"修复"成元数据丢失** | 低中 | 高（批量资产的元数据一次性丢） | 🔴🔴 |

### ① 切库 + 重扫（最该先修）

**判据（代码）**：
- `ImportQueue.tsx:20-28`：`chooseLibrary()` 成功后**无条件** `saveSettings({})` + `rescan()`；注释写「重建索引」。
- `SettingsDialog.tsx:416` 库目录说明：「更改后点「导入」页的「重新扫描」即可索引新目录」——**主动教用户做这个动作**。
- `store.ts:1017-1050`：rescan 以 `folder` 精确匹配；新库为空 → 所有旧记录进 `gone` → `bulkDelete`。
- `SettingsDialog.tsx:355`：重扫按钮只在 `materialMergeBusy` 时禁用，**与库目录是否变化无关**。
- 全仓**没有任何**"索引里的 folder 是否属于当前 libraryDir"的校验（grep `libraryDir` 在 renderer 只命中 1 处迁移计划）。

**触发序列（两条，全部是正常操作）**：

- **路径 A（自动，最危险）**：导入一个大包 → 磁盘空间不足报错（`ImportQueue` 底部出现「更改库目录」）→ 点它并选新盘 → `changeLibrary()` **立刻** `rescan()` 新目录（`ImportQueue.tsx:20-28`）→ 新盘为空 → 全库 `bulkDelete` → 旧库文件还在，**tags/note/styles/renderParams/手动封面永久丢失**（`backups` 表没有为 rescan 做快照）。
- **路径 B（手动，被文案引导）**：设置 → 库目录「更改…」→ 选新盘（此时索引还在，但所有封面 404）→ 按设置页文案去点「重新扫描」（`SettingsDialog.tsx:416`）→ 与 A 同样的全删。

**同族变体**：`settings.json` 损坏 → `loadSettings` 回退 `DEFAULT_SETTINGS` + 重新探测默认库（`settings.ts:258-267`）→ 库路径悄悄变成另一个盘 → 用户看到"资产在但封面全裂"，此时点重扫同样全删。而 `saveSettings` 是**非原子写**（`settings.ts:270-273`，直接 `writeFile`，无 tmp/rename、无 `.bak`），每次改设置都在赌。

### ② 双实例

**判据**：`main/index.ts:224` `app.requestSingleInstanceLock()` **丢弃返回值**——Electron 的语义是「拿不到锁应自行 `app.quit()`」，不检查就等于没锁。`second-instance` 只是把已有窗口聚焦，**不会终止第二个进程**。

**触发序列**：首次启动慢（解压/杀软扫描）→ 用户再双击一次图标 → 第二个进程照常 `loadSettings` / `createWindow` / `serveVault` / `restartWatcher`：
- 两个进程共享同一 `userData` → IndexedDB 同源双开：后开的渲染进程可能打不开 DB → `store.init()` reject（`store.ts:423` 无 catch）→ **永久停在"正在加载素材库…"**（`App.tsx:167-168`）；
- 两个进程都能调 `materialMerge`（互斥标志在 `materialMerge.ts:346` 是**进程内**变量）；
- 两个进程各自 `saveSettings(settings)` 整包覆盖 → 后写者赢，**设置静默回退**。

### ③ 写路径中断（无 journal）

**判据**：
- `store.ts:595-652`：批量指派是 `for` 循环逐条 IPC + 逐条缩略图，**循环结束才 `bulkPut`**；
- `store.ts:330` `commitAsset` 是 `void db.assets.put()`，**无 catch**；`ensureMissingThumbs`（`:1518`）同样；
- `rescan` 的 `bulkDelete` + `bulkPut` 是**两个独立事务**（`:1049-1050`）；
- 材质合并虽有 manifest 与备份，但**没有启动时消费 manifest 的恢复逻辑**（`rollbackMaterialMerge` 只有 main/preload，renderer 无调用方）。

**触发序列**：选中 80 个资产 → 拖拽归类到「石材/水磨石」→ 搬到第 40 个时断电/强杀 → 40 个目录已在 `材质/石材/水磨石`，Dexie 里 80 条仍指旧路径 → 下次启动 UI 显示旧分类（且封面 404）→ 用户点「重新扫描」（文案说"会同步更新"）→ 40 条旧记录被当 gone 删除、40 条新记录以空元数据重建 → **tags/note/styles 丢一半，且不可恢复**。

## 11. 我认为最该先修的一条

> ### **C1：库安全三件套 —— 把"切库/重扫"从"删数据"改成"可确认、可回滚、可恢复"**
>
> 理由不是它最"架构"，而是它的**性价比极端不对称**：全部改动 ≤ 120 行、不引入新依赖、不改变任何正常路径的行为，却能一次性堵掉**唯一一个"两次正常点击就永久丢元数据"**的通道。

**三个改动点（可独立验收）**：

| # | 改动 | 位置 | 判据 |
| --- | --- | --- | --- |
| 1.1 | rescan 前**先算差异**：若 `匹配数 == 0` 且 `本地资产数 > 0` → 拒绝执行并要求显式确认（"当前库目录下没有找到任何资产，是否确定用空索引替换？"） | `store.ts:1013` rescan 入口 | 空目录 + 有索引 → 提示框，不 `bulkDelete` |
| 1.2 | rescan **删除前**把将被删的记录写进 `db.backups`（`id: rescan-<ts>`），并在设置页给"恢复上次重扫前索引"入口 | `store.ts:1048` 前 | 删 80 条 → backups 有快照；恢复后 tags 回来 |
| 1.3 | 切库时**禁止自动 rescan**：`ImportQueue.changeLibrary` 改为"只切目录 + 提示去重扫"；`SettingsDialog` 文案同步改；重扫按钮在"库目录 ≠ 索引所属目录"时显示警告 | `ImportQueue.tsx:20-28`、`SettingsDialog.tsx:355-375` | 切库后索引不变、无删除；文案不再教用户直接重扫 |

**验收标准（QA 可直接照做）**：
1. 建一个 80 资产的库（带 tags/note/styles）→ 设置里改库目录到空目录 → **回到主界面，80 个资产仍在**、无删除、有"库目录已变更，请确认后再重扫"提示；
2. 强行点重扫 → 弹确认框；取消 → 无变化；确认 → 删除前 `backups` 多一条；点"恢复"→ 80 条记录与标签全部回来；
3. 正常库（索引与磁盘一致）点重扫 → **行为与现在完全一致**（零回归）。

**为什么不是 C2**：C2（journal）解决的是"崩溃分叉"，概率低、需要设计重放；C1 解决的是"正常操作丢数据"，概率高、且改动是防御性的。**先把人祸堵住，再防天灾。**
