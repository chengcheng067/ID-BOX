**不一致的 5 条（本设计要解决的核心样本）**：

|---|---|---|---|

| 建筑设计/规划设计 | **工装空间** > 居住区规划 | 同上 | 同上 |

**面包屑为空的 4 条**：`上海汤臣一品复式豪宅_767㎡_JPG平面图`、`李玮珉-深圳汉京九榕台990㎡别墅户型样板房`、`最新整理设计师专用CAD平立面图库`、`CAD平立面图库大全` —— 详情页**不保证有面包屑**。

> **⚠️ 本设计修正了团队假设的一处**
>
> 任务书假设「`居住区规划` 是面包屑的**二级**，和真值 `规划设计` 属于"完全不同的一级+二级"」。我按 `docs/34 §6.3` 的旧词表清单核对了本地词表：`居住区规划` **不在** `CAD_LEVEL2_MAP` 的任何一组里，也**不在** `CAD_LEVEL3_ALIAS` 的 377 条里（`grep "term: '居住区规划'"` = 0 命中）。
>
> 结论：这 2 条样本的正确形态不是"两个都解析出来、比对不一致"，而是 **S2 只能解析到一级 `工装空间`、二级为空**（详见 §3.3 的解析算法与 §7.3 的原型实测）。这直接影响 `conflict` 的定义：它是 `(工装空间, 未分类)` vs `(建筑设计, 规划设计)` —— **一级不同**的冲突，不是纯粹二级冲突。设计必须能表达这种"一边只有一级"的冲突，故 §2.2 的 `conflict` 判据写成"两个可比部分都非空且至少一项不等"。

## §2 核心机制：三源 → 置信度 → 决策

### 2.1 三个来源的定义与可用性

| 源 | 内容 | 采集时机 | 纯函数来源 |
|---|---|---|---|
| **S1** 标题语义 | `classifyAssetName(name, fileNames, kind)` → `{category1, category2}`；附 `matchedTerm` / `matchedLevel`（`autoClassify` 返回） | **T0 导入落盘时**就有 | `src/shared/classifyAsset.ts:82` |
| **S2** 站方面包屑 | `breadcrumb_data` → 按 `href` 父链还原 → 映射到本地 (一级, 二级) | T1 批次结束后才有 | 新 `shared/classifyCrossCheck.ts`（见 §2.4） |
| **S3** 站方末级名 | `classifyBaseName`（站方最深节点**名字**，不含路径）→ `mapZhimoCategory(name, kind)` | T1 批次结束后才有（**与 S2 同一次 HTTP GET**） | `src/shared/zhimoTaxonomyMap.ts:1118` |

**三个源的信息含量不是等价的**：

- S2 带**路径**（一级 + 二级都能还原），S3 只有**末级名字**（`docs/34 §6.3`："界面只给末级名称，不给路径"）。
- 所以 **S2 是校验主力，S3 是旁证**。S3 有值时若与 S2 不一致，不判 conflict，只在 UI 里多展示一行"站方另一说：X"（R-03）。
- 例外：S2 空（面包屑缺失，实测 20 条里 4 条 = 20%）时，S3 是站方唯一的声音 → 此时 S3 可以顶替 S2 的位置参与判定。**这一点写进 §2.2 的 `s2Of()` 定义**，不做成隐式回退。

### 2.2 置信度状态机

```
                    ┌──────────────────────────────────────────┐
                    │ 输入：S1（必有，可能双未分类）             │
                    │      S2'（= S2 或 S3 顶替，可能为 null）   │
                    │      S3（可能为 null，仅展示用）           │
                    └───────────────────┬──────────────────────┘
                                        │
              ┌─────────────────────────┴──────────────────────────┐
              │                                                    │
      S1 = 双未分类?                                        S1 有值
              │                                                    │
      ┌───────┴────────┐                          ┌────────────────┴───────────────┐
      │                │                          │                                │
  S2' 有值        S2' 为 null              S2' 为 null                     S2' 有值
      │                │                          │                                │
 medium-s2          none                  ┌───────┴───────┐            ┌───────────┴────────────┐
 落 S2'            进队列                 │               │            │                        │
                 reason=                一级相同?      一级不同      完全一致                有差异
                 unclassified              │               │            │                        │
                                     ┌─────┴─────┐    conflict      high                  ┌──────┴──────┐
                                     │           │   （R-06 不适用，                       │             │
                              S1 二级为空   S1 二级有值  因为一级就不同）          S1 二级为空   S1 二级有值
                                     │           │                                    │             │
                                  high        conflict                            high(补二级)   conflict
                                (用 S2 补二级)  （R-05 不消歧）                     （R-06）
```

**形式化判据**（实现即按这个写，`decideClassify` 的全部逻辑）：

```ts
// s2 归一化：S2 有面包屑就用面包屑；面包屑解析不出 → 用 S3 顶替（两者同一次 GET，零额外成本）
const s2 = s2FromBreadcrumb(breadcrumb, kind) ?? s2FromBaseName(classifyBaseName, kind)

if (s1Empty && !s2)                → 'none'          // 双未分类 + 站方什么都没给
if (s1Empty && s2)                 → 'medium-s2'     // 站方单方结论
if (!s1Empty && !s2)               → 'medium-s1'     // 我方单方结论（**必须标记未验证**）
if (!s1Empty && s2) {
  if (s1.c1 !== s2.c1)             → 'conflict'      // 一级不同 = 硬冲突，不消歧
  if (s1.c2 === UNCLASSIFIED)      → 'high'          // R-06：S1 只到一级且一级对 → 用 S2 补二级
  if (s1.c2 === s2.c2)             → 'high'
  else                             → 'conflict'      // 一级同、二级不同
}
```

**四个关键设计点**：

1. **`medium-s2` 也算"没验证"**，不是"可信"。理由对称：S2 单独出现时没人校验它，而面包屑只有 55% 与列表页一致。
2. **`conflict` 的判据里 `s1.c2 === UNCLASSIFIED` 优先于"二级不等"** —— 否则"只到一级"会被误判成冲突，把 10 条本来对的资产推进队列。
3. **`s2FromBaseName` 顶替只在面包屑完全解析不出时触发**，且必须过 `isLevel1AllowedForKind` 闸门（防 §1.4 那个 `办公空间 → 工装/办公空间` 的错）。
4. **`medium-*` 不产生 `candidates`**（只有一个答案，没得选）；只有 `conflict` 才给候选。

### 2.3 决策结构

```ts

/** 单源的结论（S1 用 ClassifyOutcome + matched 信息；S2 用本地化后的两级 + 原文路径） */
interface ClassifySourceS1 {
  category1: string
  category2: string
  /** `autoClassify` 的命中词与命中层级；一级回退命中时 matchedTerm 是那个一级词 */
  matchedTerm?: string
  matchedLevel?: 'l2' | 'l3-alias' | 'material-l2' | 'cad-l2' | 'cad-l3'
}

interface ClassifySourceS2 {
  level1: string
  level2: string          // 解析不出二级时 = UNCLASSIFIED
  /** 面包屑原文（按 level 升序），供 UI 展示"站方原话" */
  raw: readonly string[]
  /** true = 面包屑缺失，本条由 S3 顶替（UI 要如实说"站方没给路径"） */

  /** 落点。`conflict` / `none` 时是"当前**不动**的建议值"（见 §5），不是"已定案" */
  category1: string
  category2: string
  confidence: ClassifyConfidence
  sources: { s1?: ClassifySourceS1; s2?: ClassifySourceS2; s3?: string }
  /** 仅 `conflict`：去重后最多 3 条，顺序 = [S1, S2, 其余] */

}
```

`candidates` 的生成纪律（`buildCandidates(s1, s2)`）：

- 只用 `s1` 与 `s2` 两个落点（S3 不产生候选：它给不出二级）；

- 上限 3 条，实际永远 ≤ 2 条 —— 上限是给将来"AI 补分类"留的口（`docs/15 §7` 的 AI 通道若接进来，会是第三个 `from`）。

## §3 站方 → 本地映射

### 3.1 CAD：恒等优先（R-07）

**为什么恒等能成立**：本地 CAD 词表本身就是照抄站方的（`CAD_LEVEL1_LIST` 10 项来自 `cad_tree.json` 原序，`CAD_LEVEL2_MAP` 10 键 / 102 项同源，`taxonomy.ts:60` / `:362`）。

**我实测的覆盖率**（1091 条真值的 55 个 (一级, 二级) 组合）：

```
pairs 55  rows in-map 1091 / 1091  100.0%
不在 CAD_LEVEL2_MAP 的真值二级：（空）
```

→ **只要面包屑的二级名命中了本地 `CAD_LEVEL2_MAP`，落点就是确定的**，不需要别名表。

**解析算法 `s2FromBreadcrumb()`（CAD 分支）**：

```
输入：crumbs（已按 level 升序/任意序）、kind='cad'

① 按 level **降序**遍历（最深的先试）：
   对每条 level >= 2 的条目 c：
     p = 按 href 前缀在 crumbs 里查父条目（不用数组下标！见下方 ⚠️）
     p 不存在 → 跳过本条
     rawL1 = p.name
     l1 = CAD_LEVEL1_LIST 含 rawL1 ? rawL1 : cadStationAliasL1(rawL1, c.name)
     l1 为 null → 跳过本条
     CAD_LEVEL2_MAP[l1] 含 c.name → **返回 { level1: canonical(l1, c.name), level2: c.name, raw }**
     （canonical() = CAD_LEVEL2_CANONICAL_PARENT[c.name] ?? l1，处理 5 组重名二级）

② 都没命中 → 试三级归并表：取最深条目，在 CAD_LEVEL3_ALIAS 里按 term 全等查
   命中 → 返回 { level1: canonical(hit.level1, hit.level2), level2: hit.level2 }

③ 还没命中 → 一级兜底：取 level === 1 的条目
   CAD_LEVEL1_LIST 含 name → 返回 { level1: name, level2: UNCLASSIFIED }
   否则走 cadStationAliasL1(name, null) → 仍不行 → 返回 null

④ 全落空 → null（= 面包屑给了，但本地词表里一个都对不上 → 视为"站方没说"）
```

**⚠️ 为什么必须按 `href` 查父，不能用数组下标**：`tests/zhimoCover.test.ts:309-316` 有一条实测用例 —— 3 条面包屑 `[软装陈设(f765), 墙饰墙绘(f765s806), 挂画(f765s1035)]`，`level` 是 `[1, 2, 2]`：**第 3 条的父是第 1 条，不是第 2 条**。用 `crumbs[i-1]` 当父会把 `挂画` 挂到 `墙饰墙绘` 下。`ZhimoBreadcrumbItem.href` 里带的正是完整父链（`f765s1035`），必须用它。

**⚠️ 5 组重名二级必须有 canonical 父级**：`景观图库`(CAD图库/园林景观)、`景观节点详图`(节点详图/园林景观)、`结构节点图`(节点详图/结构设计)、`建筑节点`(节点详图/建筑设计)、`电气工程节点`(节点详图/机电工程)。本地已有 `CAD_LEVEL2_CANONICAL_PARENT`（`taxonomy.ts:421-427`），直接复用，**不要新建第二张表**。

**闸门**：函数返回前一律 `isLevel1AllowedForKind('cad', level1)`，false → 整个 S2 视为 `null`。

- 返回单对象 → 采用；
- 返回 `ARR(1)` → **解包该唯一元素**（`1168792999` 就是这情形：`家具/沙发`）；
- 返回 `ARR(n>1)` → S2 = null（不猜）；
- 返回 `null` → 走一级兜底（若最深名本身是本地一级）→ 还不行则 S2 = null。

### 3.4 `hdri` / `other`：没有站方源（**不假装有**，R-06 的反面）

| kind | S2 | S3 | 所以可能的置信度 |
|---|---|---|---|
| `hdri` | **永远 null** | `classifyBaseName` 理论上可能有（站方详情页字段不区分 kind），但 `mapZhimoCategory(name, 'hdri')` **无 hdri 频道词表** → 即便有名字也大概率 `null` | `medium-s1` 或 `none`（**`conflict` 永不出现**） |
| `other` | 同上 | 同上 | 同上 |

**这不是"设计不完整"，是"数据里没有"**。写进文档的理由：
- `isZhimoCoverKind()`（`renderer/logic/zhimoCover.ts:64`）只认 `model | cad` —— 说明连**封面抓取**都不覆盖 hdri/other，站方数据链条本来就没打通；
- `isLevel1AllowedForKind()`（`taxonomy.ts:1117-1119`）对 `hdri`/`other` **恒返回 false**（`CHANNEL_LEVEL1` 里没有这两册）→ S1 对它们**永远双未分类**（我实测确认：`classifyAssetName(x, undefined, 'hdri')` 与 `'other'` 对 6 个样本全部返回 `未分类/未分类`）。

→ 所以 `hdri` / `other` 的真实状态是 **`none`（双未分类）**，而且**不会有 S2/S3 来救**。它们只能靠 AI 补分类（`docs/15 §7`）或用户手动。**设计里如实写成 `none`，不要为统一而虚构一个 S2。**

### 3.5 映射闸门（统一兜底）

无论哪个 kind，`s2FromBreadcrumb` / `s2FromBaseName` 返回前都必须过：

```ts
import { isLevel1AllowedForKind, UNCLASSIFIED } from './taxonomy'
if (!isLevel1AllowedForKind(kind, level1)) return null   // 一级不在本 kind 的容器词表 → 整个 S2 作废
if (level1 === UNCLASSIFIED) return null                  // 不允许 S2 给出"未分类/未分类"这种空结论
```

**这条闸门的必要性有一处实证**：§1.4 里 `mapZhimoCategory('办公空间', 'cad')` 返回 `工装/办公空间`（SU 一级）。若不设闸门，CAD 资产的 S2 会变成 `工装/办公空间`，然后和 S1 的 `工装空间/办公空间` 判成 **conflict（一级不同）** —— 一个纯粹因为映射表串台而造成的假冲突。闸门把它压成 `null`（走恒等路径，§3.1 优先且不会走到这里）。

### 4.1 两种 reason（R-10）

```ts
export type ReviewReason = 'unclassified' | 'conflict'

/**
 * 该资产是否需要用户裁定。
 *
 * ⚠️ 与 `isUnclassified()`（`logic/triageFlow.ts:57`）的关系：
 * - `'unclassified'` 的判据**就是** `isUnclassified()` —— 双未分类。**一个字节不改**。
 * - `'conflict'` 是新判据：`classifyReview.reason === 'conflict'`（有分类但来源冲突）。
 *   它**不是**未分类，所以不能塞进 `shouldTriage()`（那会破坏"进整理模式 = 处理未分类"
 *   的肌肉记忆，并且 `assignCategory` 对"已在目标分类"的资产判 skipped → 表现为"按了没反应"，
 *   见 `triageFlow.ts` 的 `isUnclassified` 注释第 3 段）。
 */
export function reviewReasonOf(asset: Asset): ReviewReason | null
```

判据表（**唯一实现点**，组件里不许再写）：

| 输入状态 | `reviewReasonOf` | 说明 |
|---|---|---|
| `classifyReview?.reason === 'conflict'` | `'conflict'` | **优先判断**：一个 conflict 资产即使二级恰好是 `未分类`，也归 conflict（理由：它已经有人工/自动的落点在争议中，不是"从没分过"） |
| `isUnclassified(asset)` | `'unclassified'` | 语义与现在**完全一致** |
| 其它 | `null` | 不在队列里 |

**顺序不可交换**的理由：conflict 且 `category2 === 未分类`（R-06 不适用的一级冲突，如 §3.3 那 2 条 `工装空间/未分类` vs `建筑设计/规划设计`）→ 若先判 `isUnclassified` 会因为 `category2 === 未分类` 但 `category1 !== 未分类` 而返回 false，然后落到 `null` —— **这条资产就凭空从两个队列里都消失了**。这是最容易漏的一条，必须写成测试。

### 4.2 与现有 `TriageOverlay` 的关系

**复用浮层，不复用待办集函数**：

| 层 | 现状 | 本设计 |
|---|---|---|
| 纯逻辑 `triageFlow.ts` | `isUnclassified` / `buildTriageQueue` / `startTriage` / `stepTriage` / `skipCurrent` / `advanceAfterAssign` / `reconcileTriage` / `decideTriageKey` | **一行不改**。新增 `buildReviewQueue(ordered, reason)` 放在**新文件** `renderer/logic/reviewFlow.ts`，内部 `filter(a => reviewReasonOf(a) === reason)`。`buildTriageQueue(ordered)` 保持 `= buildReviewQueue(ordered, 'unclassified')` 的等价语义（用测试钉住等价性，不用实现合并 —— 合并会让 `triageFlow.ts` 的注释体系失焦） |
| 游标 | `TriageCursor`（ids / currentId / skipped） | **原样复用**。`startTriage(queue)` / `stepTriage` / `skipCurrent` / `advanceAfterAssign` / `reconcileTriage` 都只认 `Asset[]`，与 reason 无关 |
| store | `triageActive: boolean` + `openTriage()` / `closeTriage()` | 扩成 `triageMode: 'unclassified' \| 'conflict' \| null`。**`triageActive` 保留为派生 getter**（`triageActive = triageMode !== null`），避免 12 个既有读点全改。`openTriage()` 签名不变（= `openTriage('unclassified')`），新增 `openReview('conflict')` |

| 差异点 | — | `conflict` 模式下右栏多一块「来源对比」：S1 / S2 / S3 三行 + 候选按钮。选中候选即预填 `level1/level2`，`Enter` 走**同一个** `assignCategory` |

**为什么必须复用而不是另起一个浮层**：`TriageOverlay` 的 509 行里，真正与"未分类"耦合的只有 4 处（队列来源、标题文案、收尾文案、右栏内容）。另起一个会把这 4 处之外的 30+ 条纪律（Esc 栈、`reconcileTriage` 接位、`busy` 防连按、`panelOpen` 让路、选中态跟随）**复制一遍**，必然漂移。

### 4.3 三个入口（按优先级）

#### 入口 ①（必须）：侧栏「待确认」节点

**位置**：`src/renderer/components/Sidebar.tsx` 的「整理」组（`:591` 的注释块之后，与「收藏」`:606` / 「重复资产」`:620` 并列），**新增一行「待确认」**：

```
整理
  收藏       12
  重复资产    3
  待确认      7     ← 新增；0 时禁用 + opacity-40（与「重复资产」同款，见 Sidebar.tsx:622-625）
```

- **计数**：`assets.filter(a => !isDeletedAsset(a) && reviewReasonOf(a) === 'conflict').length`
  - ⚠️ **全库口径**（不套筛选），与「未分类」那个数字同源（`docs/25` 的口径表里 ① 号），否则用户点进去看到的数量和徽标对不上；
  - **只数 `conflict`，不数 `unclassified`**：后者已有「未分类」节点 + 「整理」按钮，混在一起会让两个数字互相污染；

#### 入口 ②（必须）：批次级汇总弹窗（R-11）

**触发点**：`window.modvault.onImportBatchDone()`（`store.ts:2492`）里，`scheduleZhimoPipeline()` **之后**挂一次 `scheduleReviewSummary()`。

**形态**（不新增弹窗组件，用既有 `enqueueNotice` + `notice`）：

```
本批 12 个素材，其中 3 个分类存疑 → 点侧栏「待确认」处理
```

- **为什么不做 modal 弹窗**：用户原话是"弹窗提示"，但 `docs/27` 建立的批次汇总模式就是 `enqueueNotice`（`store.ts:290`），它已经解决了"多条汇总互不吞并"（队列 + 4.5s 依次展示）。在这里另起一个 modal 会有两个真问题：
  1. **模态阻断**：用户批量导入 50 个包后可能立刻去干别的，一个必须点掉的 modal 是打扰；
  2. **Esc 层级**：`store.ts` 已有 `useEscLayer` 栈（`closeQuickLook` / `TriageOverlay` / `CategoryPicker` / 冲突询问弹窗都在栈上），再加一层要重新排优先级。
- **为什么绝不可能逐包弹**：`import:batchDone` 是**批次级**事件（`types.ts:653` 的契约："抓取是后置任务，不在导入链路里"），逐包弹需要改成 `import:event` 里弹 —— 那会变成"拖 50 个包弹 50 次"。**这一点写进 `scheduleReviewSummary()` 的函数头注释**，并加源码守卫（§9.3 S-03）。
- **⚠️ 时序约束**：`conflict` 只有 T1（抓完详情页）之后才知道，而 `onImportBatchDone` 在 T0 结束时立刻触发。所以 `scheduleReviewSummary()` 必须**等知末流水线跑完**：

```ts
function scheduleZhimoPipeline(): void {
  setTimeout(() => {
    void (async () => {
      const state = useVault.getState()
      if (zhimoAutoCategoryEnabled(state.settings)) {
        await state.runZhimoCategoryReclass().catch(() => undefined)
      }
      await useVault.getState().runZhimoCovers().catch(() => undefined)
      // ★ 新增：流水线**跑完**才汇总（此时 conflict 才存在）
      reportReviewSummary()
    })()
  }, 0)
}
```

`reportReviewSummary()` 统计"本批新增的 conflict 数"，**不用全库数**：
- 全库数 = 用户历史上积压的，每次导入都报一遍会变成噪音；
- 本批数：在 `runZhimoCategoryReclass` 的 `summary` 里加一个 `conflicts` 计数（§7.1 的文件清单），或者用一个模块级 `conflictsInBatch: number`（消费型，`flush*` 同款，`store.ts:315` 的 `flushSkippedSummary` 是现成范式）。

#### 入口 ③（可选，本批做）：卡片角「存疑」标记

**位置**：`src/renderer/components/AssetGrid.tsx:2433` 的右上角竖列 `absolute right-2 top-2 z-10 flex flex-col items-end gap-1` 里，`SelectBox` 之后、`Flags` 之前插入一个徽标。

- **样式**：复用 `.badge`（中性灰 tint），文字 `存疑`，**不新造颜色**（`docs/32` 的纪律：徽标只用既有 `badge` / `badge-accent`）；
- **点击**：`stopPropagation` + `openReview()`（打开浮层并跳到这张）。⚠️ 不能只"筛到这张" —— 用户点它的意图是"处理这个存疑"，不是"看它"；
- **只在 `reviewReasonOf(a) === 'conflict'` 时渲染**，不渲染 `unclassified`（未分类已有明显的视觉表达：分类为空 + 侧栏计数）；
- **回收站里不渲染**（`!trashMode`，与 `GripHandle` 同一条纪律，`AssetGrid.tsx:2477`）。

**优先级排序（我的裁定）**：① 侧栏节点 > ② 批次汇总 > ③ 卡片标记。
理由：① 是**持久入口**（用户任何时候都能找到），② 是**发现入口**（告诉用户"有东西要处理"），③ 是**定位入口**（在网格里指出是哪张）。缺 ① 则队列没有归宿，缺 ② 则用户不知道有队列，缺 ③ 不影响功能完整性。**三个都做，但若排期紧可以砍 ③。**

## §5 落库时机与搬目录裁定

### 5.1 三阶段

| 阶段 | 触发 | 手上有什么 | 该做什么 | 谁来做 |
|---|---|---|---|---|
| **T0 导入落盘** | 每次 `importOne` | **只有 S1** | 按 S1 落盘（与现在**完全一致**，`importer.ts:766-780` 不动）；额外写 `classifyReview: { confidence: 'medium-s1' 或 'none', reason: s1 双未分类 ? 'unclassified' : undefined }` | `main/importer.ts`（三处 `fresh` 构造：`:993` / `:1308` / `:1602`） |
| **T1 批次结束** | `import:batchDone` → `scheduleZhimoPipeline` | S2 / S3 可拿（一次详情页 GET，零额外请求） | 逐条 `decideClassify` → 更新 `classifyReview`；`high` 且需搬则**搬**；`conflict` 进队列；`medium-*` 只标记 | `renderer/store.ts` 的 `runZhimoCategoryReclass` 扩展（或新函数 `runClassifyVerify`） |
| **T2 用户整理** | 用户在浮层确认 | 用户裁定 | `assignCategory` 搬目录 + 清 `classifyReview`（写 `decidedAt` + `confidence: 'high'`，`reason` 删掉） | `TriageOverlay`（`conflict` 模式） |

**T0 为什么必须现在就写 `classifyReview`**：不写的话，T1 抓完详情页只看到"这资产有分类"，无法区分"这个分类是 S1 猜的（可能错）"还是"用户手工指的（不要动）"。**这个区分是整个机制的前提**，且它只能在 T0 写（T1 时已被覆盖）。

**T0 写什么**（精确）：
- S1 双未分类 → `{ confidence: 'none' }`（`reason` 不写：`unclassified` 是**派生值**，见 R-13）；
- S1 有值 → `{ confidence: 'medium-s1' }`（"未经站方验证"）；
- **不给 `sources` 存 S1 明细**：`s1` 是可重算的（`classifyAssetName(name, files, kind)` 是纯函数），存进库只会随词表升级而腐坏。**这是 R-13"字段最小化"的第二个理由**（第一个理由是减少漏点）。

### 5.2 T1 要不要搬目录 —— 裁定：**有条件地搬，只搬 `high` 且改动有意义的那批**（R-12）

**三条门槛（AND，缺一不搬）**：

| # | 门槛 | 理由 |
|---|---|---|
| ① | `confidence === 'high'` | `medium-*` 的落点没被第二源验证过；`conflict`/`none` 根本没有可信落点。**搬了等于把猜测写成目录事实** |
| ② | `decideClassify` 给出的落点 ≠ **当前磁盘分类** | 相同则 `assignCategory` 会判 `skipped`（`store.ts:3128-3131`），但仍会走 IPC + `regenThumbSweep`，纯浪费 |
| ③ | **不是 `coverSource === 'manual'` 之外的用户改动过的分类** —— 精确说：`classifyReview` 存在且 `confidence !== 'high'` 且 `decidedAt` 不存在 | 用户手工归类的资产 `classifyReview` 已被清掉（T2）；如果还有残留标记，说明**是自动/导入给的**，可以搬 |

**为什么不全搬（含 `medium-*`）**：
- 单价成本：`assignCategory` 每条 = 1 次 IPC（`main` 侧 `moveAssetCategory`）+ 1 次 `regenThumbSweep`（重生成缩略图）+ 1 次 `bulkPut`。§1.5 测算每 1000 条 CAD 有 ~460 条 `medium-s2`（S1 空、只有站方）—— 那是 460 次目录移动 + 460 次缩略图重算，在万条库上是分钟级的卡顿；
- 收益不对称：`medium-s2` 的落点是**站方单方结论**，而站方单方结论的可信度上限是 55%（§1.1）—— 用 460 次目录移动换一个 55% 正确率的落点，不如只标记；
- **可逆性**：搬了有 `zhimo-reclass-` 备份可撤销（`store.ts:4741`），但"撤销"是**消费型**的（一次撤销撤全部），用户没法只撤某一条搬错的。

**为什么也不能"全不搬"**：
- `high` 是**两源独立一致**，误判率显著低于单源。§1.5 的 oracle 实验里 464 条 `high` 全部判对（因为 oracle 的 S2 = 真值）；
- 真实场景下 `high` 的比例不会这么高，但"两源一致"本身就是强证据 —— 与 `docs/34 §9.2` 的"`工装平面图` 75% 精确率是强判据"同一条思路；
- 不搬的话，用户导入后必须先手动跑一次整理才能享受分类准确性的提升，**装上没效果**（与 `settings.zhimoAutoCategory` 的产品口径"默认开 = 装上就有效果"冲突）。

**实施的工程约束**：
- 必须**复用** `runZhimoReclassQueue`（`zhimoReclass.ts:323`）的三种节流（小并发 2 / 250ms 间隔 / 每 50 条停 2s）+ `shouldStop`；
- 必须**先备份**（`backupReclassMoves(records, ZHIMO_RECLASS_BACKUP_PREFIX)`，`store.ts:4711`），**早于任何移动**；
- 必须**按分类对分组**（`groupByCategoryPair`，`zhimoReclass.ts:229`）—— 一次 `assignCategory` 只接受一个分类对；
- **候选筛选必须复用现有 `isZhimoReclassCandidate`**（`zhimoReclass.ts:84`）再叠加"达标"条件：非软删 + 有 `zhimoId`。**不要新写一份软删判断**（那是第二套真相）。

### 5.3 T1 落地后的 `classifyReview` 形态

```ts
// high 且已搬（或无需搬）
{ confidence: 'high', reason: undefined, sources: { s2: {...} }, decidedAt: Date.now() }
// 注：high 的不写 reason → reviewReasonOf 返回 null → 不进队列

// conflict（进队列）
{ confidence: 'conflict', reason: 'conflict', sources: { s1: {...}, s2: {...}, s3: '办公室' } }
// 注：**必须持久化 sources** —— 否则下次启动浮层里"为什么存疑"就没了，
//     用户面对一个空白的对比面板只能重抓详情页（而站方可能已改）。

// medium-s2（只标记）
{ confidence: 'medium-s2', sources: { s2: {...} } }

// none（= 未分类，靠 reviewReasonOf 的 isUnclassified 分支进队列，不靠 reason）
{ confidence: 'none' }
```

**`sources` 存不存的裁定**：
- `s1` **不存**（可重算，且会随词表升级腐坏）；
- `s2` **存**（不可重算：站方随时可能改面包屑，重抓拿到的是"今天的站方"而不是"当时的站方"；而用户要看的就是"当时为什么判成 conflict"）；
- `s3` **存**（同理，且只有一个字符串，成本可忽略）；
- 总计：`~120 字节/条`（`s2.raw` 是 2~3 个名字）→ 1 万条 = 1.2MB。**可接受**，且只在 `medium-*` / `conflict` 上写（`high` 不写 `s1`、只写 `s2` 的 `raw` 可选省略）。

## §6 数据层变更（R-13 / R-14 / R-15）

### 6.1 新增字段（**只加一个**）

```ts
// src/shared/types.ts，放在 zhimoId 之后（`Asset` 里"知末相关"字段聚在一起）
/**
 * 分类可信度与待确认原因（2026-10 三源交叉验证，docs/35）。
 *
 * 为什么是**一个嵌套对象**而不是 4 个平铺字段（`pendingVerify` / `classifyConfidence` /
 * `classifySources` / `reviewReason`）：本项目的字段保全有**三处**必须同步
 * （`rescan` 白名单 / `applyOverwriteInherit` / `mergeDuplicateGroup`），
 * 每多一个字段就多三个漏点。2026-10 的 rescan 事故（143 条里 127 条的 renderParams 被抹）
 * 就是"新字段忘了归类"的直接后果 —— 嵌套成 1 个字段，漏点从 12 个降到 3 个。
 *
 * `undefined` = 尚未经交叉验证（老记录 / 未抓过详情页）→ 行为与改造前完全一致。
 * **非索引字段**：不参与筛选、不进 `.where()` → 不需要升 Dexie 版本（同 materialMeta / renderParams）。
 */
classifyReview?: ClassifyReview

/** 见上。字段全部可选：任一缺失都不影响既有功能。 */
export interface ClassifyReview {
  /** 上一次判定的置信度（§2.3）。`undefined` = 没有判定过 */
  confidence?: ClassifyConfidence
  /** **只有 `conflict` 才写**。`unclassified` 是派生值（走 isUnclassified），不落库 */
  reason?: 'conflict'
  /**
   * 判定依据。**只存不可重算的部分**：
   * - `s1` 不存（`classifyAssetName` 纯函数可重算，且随词表升级会腐坏）；
   * - `s2` / `s3` 存（站方随时会改，重抓拿到的是"今天的站方"）。
   */
  sources?: {
    s2?: { level1: string; level2: string; raw: string[]; fromBaseName: boolean }
    s3?: string
  }
  /** 用户/自动**定案**的时间戳；有值 = 已定案 → `reviewReasonOf` 返回 null */
  decidedAt?: number
}
```

**`pendingVerify` 为什么不落库**（R-13）：
- 它 = `classifyReview?.reason === 'conflict'`，**一个表达式就能算出来**；
- 落库的代价是"两处真相"—— `reason` 改了忘了改 `pendingVerify` 就是永久不一致；
- 它与 `docs/25` 里"未分类有三种口径"的教训同型：**同一语义只能有一个存储点**。

**`confidence` 为什么**要**存**：它不能从 `category1/category2` 反推（`high` 与 `medium-s1` 可能落同一个分类对），而 T2 的清标记、`medium-s2` 的搬目录策略都要读它。

### 6.2 Dexie 不升版本（R-15）

**依据（三条，均可复核）**：

1. `ASSETS_V5_STORE_SCHEMA`（`db.ts:34-35`）是**索引串**，只列要建索引的字段。`classifyReview` 不参与任何筛选；
2. 项目里**没有任何 `.where()` 走非 `id` 键的筛选**（`db.ts:181` 的注释写明"favorite 不建索引——项目里 0 处 `.where()`，标记筛选全量在内存过滤"）→ 新增字段连"加索引更快"的动机都没有；

### 6.3 rescan 保全（R-14 的第一处）

`store.ts:3826-3858` 的 rescan 合并是**以 `local` 为底、只覆盖显式列出的磁盘权威字段**（`...local` 打底）。所以 `classifyReview` **天然就被保留了** —— 但**必须显式归类**，否则 `tests/rescanMergePreserve.test.ts` 的编译期穷举会红：

```ts
// tests/rescanMergePreserve.test.ts:75 的 LOCAL_PRESERVED 追加一行
const LOCAL_PRESERVED = [
  'id', 'source', 'mojibake', 'styles', 'renderParams', 'renderShape',
  'deletedAt', 'trashRel', 'aliasOverride', 'tags', 'note',
  'favorite', 'rating', 'colorTag', 'importedAt', 'updatedAt',
  'classifyReview'   // ← 新增：分类判定依据，rescan 无权改写

```

**为什么它属于 `LOCAL_PRESERVED` 而不是 `DISK_AUTHORITATIVE`**：rescan 从磁盘读的是目录名（`s.category1/s.category2`），**磁盘上没有"置信度"这种东西**。把 `classifyReview` 归到磁盘权威，等于让 rescan 把它写成 undefined —— 那正是 2026-10 事故的形态（新字段被占位默认值覆盖）。

**⚠️ 有一条边界要说清**：rescan 会覆盖 `category1/category2`（磁盘权威）。若用户在 T2 手工改了分类（目录已搬），rescan 读到的是新目录 → 分类正确。但若 `classifyReview.confidence === 'high'` 且 `decidedAt` 已写，`reviewReasonOf` 返回 null，不会因 rescan 重新进队列。**这是对的**：用户已经裁定过的，不该被重扫重新翻出来。

### 6.4 另外两处保全（R-14 的其余两处）

**(a) `applyOverwriteInherit`（`importer.ts:631-649`）** —— 覆盖导入时"旧记录的用户元数据"要继承过来：

```ts
function applyOverwriteInherit(fresh: Asset, existing: ImportDedupeEntry): Asset {
  const meta = existing.meta
  return {
    ...fresh,
    // ...既有字段...
    // 分类判定依据：旧记录有就继承（同 zhimoId 的"本地优先"口径 —— 抓过一次的站方结论，
    // 新包解不出同样的东西，丢了就得重抓）
    classifyReview: fresh.classifyReview ?? meta.classifyReview
  }
}
```

⚠️ 但 `ImportConflictInherit`（`types.ts:441-455`）里**没有** `classifyReview`，需要加。它是 `shared` 类型 → 主进程与渲染层的判重快照共用，加字段是类型安全的（两端同时看到）。

**(b) `mergeDuplicateGroup`（`recordHygiene.ts:148`）** —— 同 folder 重复记录合并，"只补空、不覆盖"：

```ts
if (merged.classifyReview === undefined) {
  const withReview = others.find((a) => a.classifyReview !== undefined)
  if (withReview) merged.classifyReview = withReview.classifyReview
}
```

**优先级要不要挑"更好的那个"（如 `high` 优于 `conflict`）？** **不要。** 与 `mergeDuplicateGroup` 的既有纪律一致（"只补空、绝不覆盖"）—— 拿"别条的值"覆盖幸存者的判定依据，是在没有依据的情况下替用户改结论。默认 `compareSurvivor`（`recordHygiene.ts`）已经按"用户字段多 > updatedAt > id"排序，幸存者本来就该赢。

## §10 待明确事项（3 条，每条给建议答案）

### Q-1：`medium-s2`（站方单方结论）要不要在 UI 上"提示用户确认"？

**背景**：§1.5 测算 42.2%（460/1091）的资产将是 `medium-s2`。如果它们也弹提示/进队列，队列会变成 ~600 条的量级，用户会直接放弃。

**我的建议：不要。`medium-s2` 只标记、不进队列、不弹窗。**
理由：① 它至少有站方一个来源，比 `none`（什么都没有）强；② 队列的价值是"处理不确定性"，600 条无差别队列等于没有队列；③ 若用户想看，可以在设置页的「按站方分类重排」汇总里看到 `unverified N` 这个数字（T-14），**按需主动进入**而不是被动打扰。
**需要你拍板的点**：`medium-s2` 的落点是否**也**要在卡片上加一个极淡的视觉标记（比如徽标不加，但 hover tooltip 写"分类来自知末，未经本地语义验证"）。我倾向**加 tooltip、不加徽标**。

### Q-2：`hdri` / `other` 没有任何 S2/S3 源，要不要给它们单独做一套"待确认"？

**背景**：§3.4 —— 这两个 kind 的 S1 恒为双未分类（`isLevel1AllowedForKind` 对它们恒 false），且站方无频道词表。它们**永远**是 `none` + `unclassified`，现在的「整理」队列**已经在处理它们**。

**我的建议：不单独做。它们就走现有的 `unclassified` 队列（一屏一张 + 手动选分类）。**
理由：交叉验证对它们**没有输入可验**，做一套专门的 UI 只是换皮。用户原话"模型，hdr，材质同理"的正确读法是"这套机制对四个大类通用**（在有站方源的前提下）**"，而不是"hdr 也要有三源交叉"—— 三源在 hdr 上物理不存在。
**需要你拍板的点**：若你希望 hdr 有分类能力，正解是**接 AI 辅助分类**（`docs/15 §7`，`settings.aiClassify` 已有完整链路），而不是在这套三源机制里硬塞一个假源。要不要把"AI 对 hdri/other 补分类"单独立一项后续（不进本批）？

### Q-3：T1 的 `high` 搬目录，用户能不能**事后**知道"这次自动搬了多少、搬错了怎么只撤那一条"？

**背景**：§5.2 裁定了"搬 `high`"，但 `zhimo-reclass-` 备份是**消费型 + 全量撤销**（`store.ts:4741` 的 `undoLastReclassify(prefix)` 会把那一批全搬回去）。如果 200 条 `high` 里只有 3 条搬错，用户没法只撤 3 条 —— 只能全撤再手工重做。

**我的建议：本批不做逐条撤销，但必须在汇总里把数字说清。**
具体：设置页汇总块（T-14）显示「自动确认 N（其中因站方验证一致 M）」+ 侧栏「待确认」的数字；用户若发现搬错，正解是**把它拖回原分类**（`assignCategoryWithUndo` 已有 5 秒撤销条，`store.ts:3206`），而不是走批量撤销。
**需要你拍板的点**：要不要给 `zhimo-reclass-` 备份加一个"按 id 撤销"的入口？（技术上可行：`undoLastReclassify` 改成接受 `ids?: string[]`，只搬回指定的那些。但它会引入"备份被部分消费"的状态，撤销一次之后备份还在不在、能不能再撤第二次 —— 这些交互要重新设计。）**我建议本批不做，挂账到下一批**，因为它不是本需求（三源交叉验证）的一部分。
