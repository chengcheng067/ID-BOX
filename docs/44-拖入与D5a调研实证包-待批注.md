## TL;DR

**调研结果比「找到现成代码抄」更省事，也更反直觉**：行业里**没有**「从插件 HTML 面板拖一条线到 SU 视口、松手就落位」的成熟实现；3D Warehouse、Enscape、官方材质范例这些成熟做法全是「选中 → 回调把 id 给 Ruby → Ruby 调放置工具/油漆桶 → 用户在视口里点一下落位」。而**这一整套我们插件已经有了**（`Inserter.insert` 的 `place_component`）。所以「拖入」真正缺的不是插入/落位，只是**触发方式**，以及一个关于「要不要为真·拖拽付出代价」的产品判断。

**GitHub 上确实没有开箱即用的拖放桥**，但官方给了纯 Ruby、零网络、零原生件的接收端 API（`Sketchup::Importer` / `Materials#load`）；可复用的不是「拖放代码」，是这些官方接口。

⚠️ 最关键的一条边界：**接收端 ≠ 发出端**。官方 API 定义「SU 收到一个文件/路径之后干什么」，不负责产生「从我们面板把资产拖出去」的那个 OS 级拖放对象；后者正是官方 issue #506 被卡住的 CEF 路径，GitHub 上没找到现成实现。

## 2. 对「从 0 自己做会有很大问题」的直接回答

`【查证】` 成熟软件的做法（R-2 §5 竞品对照）：

| 软件 | 真实做法 | 是不是「松手即落位」 |
| --- | --- | --- |
| 3D Warehouse / SU 自带组件面板 | 选中 → `Click in the drawing area to place the component`；SU 以 Move 工具挂上组件 | 否，视口内还要点一下 |
| Enscape 资产库 | 从 SU 工具栏开**独立窗口**，选中后组件跟随鼠标，`until ... you have clicked in the SketchUp viewport`，SU 里是白色简化占位符 | 否 |
| 官方论坛材质范例 | HTML `onclick` → `sketchup.paint(name)` → Ruby `materials.load(.skm)` + `materials.current=` + `Sketchup.send_action('selectPaintTool:')` | 否，切油漆桶后刷面 |
| V-Ray / Chaos Cosmos | 官方文案 `drag into scene / drag onto surface`，实际文档写 `拖到 central panel / Add to Scene` | 公开实现细节未找到 |
| D5 | 主业是 LiveSync 把 SU 模型**送出去**渲染；D5 Works 文案称「drag straight into SketchUp scene」 | 公开实现细节未找到 |
| 可搭鸭 Okducky | **本地包里查不到任何拖模型/材质进 SU 的实现**（见 §3 复核） | 不适用 |
| 溜云库 / 青云库 | **独立 Windows 桌面客户端**（不是 SU 内 HtmlDialog）：「下载模型后无需解压，可直接拖入 MAX/SU」「一键拖拽素材至 MAX/SU」+「**青模自动出现在第三方软件顶部菜单**」 | 文案层「拖入」，机制未公开 |

⇒ **所有竞品「拖进 SU」的底层机制均未找到公开实现细节**，逐条标 `【待核实】`，没有编造。R-2 明确区分了「把 SU 模型送出去渲染」与「把外部资产送进 SU 视口」，这两件事常被混为一谈。

### 2.1 一条可能改变取舍的新线索（`【推断】`，不是结论）

R-2 v1.1 §5 第 6 条 + §6.3 拼出了一个我们之前没摆到一起的事实：

| 事实 | 证据 |
| --- | --- |
| **主程序侧早就有「OS 级拖出」能力** | `src/main/index.ts:1673` `event.sender.startDrag({ file: abs, icon })` —— Electron `webContents.startDrag`，把库内**绝对文件路径**交给 OS 级原生拖放（U-12 官方原文「Initiates a native drag operation」） |
| **SU 侧有官方「拖文件进建模窗口」的接收端** | 论坛 168256：SU ≥ 2019.2 「drag and drop ALL supported file types directly into your modeling window」，由 `Sketchup::Importer` 接管、`load_file` 收绝对路径 |
| **同类产品正是「外部客户端 + DCC 侧插件」形态** | 溜云库 / 青云库的「第三方软件顶部菜单插件」文案（U-19），R-2 判 `【推断】`「暗示外部客户端 + DCC 侧插件的进程间联动，与本项目 Electron 主程序 + SU 插件形态相近」，**无实现细节佐证** |

⇒ `【推断】` **「从 ID BOX 主程序窗口拖到 SU 视口」可能根本不需要碰 CEF 面板发出端那个死结**：发出端用主程序已有的 `startDrag`，接收端用 SU 自己的拖放处理，SU 插件只做菜单/落位/索引这一侧。这恰好绕开 #506 与「插件禁原生件」两条硬约束。但要注意：① SU 官方文档记的是「松手 → 组件挂 Move 光标 → 视口内再点一下」，**仍不是松手即落位**；② SU 不能以管理员运行（`docs/38:110`，UIPI 跨完整性级别会拦）；③ 溜云库那条只是宣传文案，**没有任何实现细节**，不能当成「竞品验证过」的证据。

⇒ 这条线索只登记，不替产品下结论；核实方式是真机最小探针（V14：注册最小 `Sketchup::Importer` + 从资源管理器拖 `.skp` 进建模窗口观察 `load_file`）。它扩展了 §7 第 1 条的可选形态，**不是新的待拍板问题**。

⇒ 本项目现状（`【查证】`，带行号）：`INSERTABLE_KINDS = %w[model]`（`lib/core.rb:64`）、`CALLBACK_NAMES` 仅 `ready/refreshIndex/insertRecord`（`lib/panel_callback.rb:47`）、`panel.html:1083` 只有 click 事件委托、无 drag 事件；`lib/loader.rb:392` 已用 `definitions.load`、`:441-443` 已用 `place_component`、`:388` 已有 `start_operation`。**落位结果等价，差的是触发方式。**

⇒ 还差四层：① HTML 拖放事件层 ② 拖放→Ruby 回调层 ③ 材质层 ④ 系统级 OLE 发起层。后两层受硬约束限制：插件是纯 Ruby + 本地 HTML，**没有 Electron/Node/`webContents`**，且 `docs/39:169-170` + `lib/core.rb:12-19` 写死零网络 / 零原生件（`禁 .so/.dll`、只用 stdlib `json`）⇒ **主程序 `src/main/index.ts:1673` 的 `startDrag({file, icon})` 不能照搬进 SU 插件**。

## 5. D5a 入库的硬事实（R-1，给 V1.0 用）

- `1.d5mesh` 文本段仅 **17,802 B（0.3%）**，其余 **99.7%（约 5.96 MB）是紧密 float 数组**；全包 `glTF/FBX/PLY/STL/OBJ/RIFF/DDS/KTX/Basis` 签名计数全 0 ⇒ **网格主体是 D5 私有二进制，不可解析**，读顶点/UV/材质索引需 D5 官方规范或 SDK `【待核实】`。
- `info.json` = 28 条 `instanceIdArray` + `productID`（32 位 hex，可作去重/溯源候选），**无资产名、无分类**。`d5material.xml` = 25 个 `<Material_2>`，其中 6 个含 `<diffuse_map>`，且是**导出机的绝对路径**（GUID 临时目录）。
- 6 张贴图是**并列的 6 个材质 diffuse**，**没有「主 diffuse / 资产主图」**；实看是编织平铺纹理、黄色丝绒平铺纹理、**一张二维码推广件**，都不是「休闲椅」的渲染成品图。包内**没有任何内嵌预览图**（PNG magic 1 + JPEG magic 5 = 恰好 6 张贴图）。
- ⇒ 若走「解包成目录」，现有 `pickCover`（`classify.ts:391-420`）会落到 **⑤ largest = 1.56 MB 编织纹理特写**，`coverSource='largest'`，**视觉上认不出是椅子**。且 `walkFiles` 会把 6 张贴图全收进 `files[]`，`primaryKind` 按 `KIND_PRIORITY` 把整包判成 **`texture`**、落「材质」目录；`textures/` 子目录里的图**不会**被重扫当成独立图片资产。
- **当前把 `.d5a` 拖进 ID BOX 会报错而非跳过**：`src/main/extractor.ts:61` `SUPPORTED_EXTS = new Set(['.zip','.rar','.7z'])` → `:287-288` 抛 `unsupported`「只支持 zip / rar / 7z」；`detectZipContent`（:79）只服务已过白名单的 `.rar/.7z`，**不会**让 `.d5a` 因内容是 ZIP 而绕过。
- 插件侧会卡在两处：`INSERTABLE_KINDS`（`core.rb:64`，非 model 不给插入）与 `model.definitions.load`（`loader.rb:392`，对 `.d5mesh` 私有二进制必然失败）。
- 新增一种资产格式的最小改动面可参照 cad 引入提交 `b59de52`（**16 个文件**）；现有 `AssetKind` 只有 6 种（`types.ts:19`）。
