## 1. TL;DR（5 条）

1. **偏离2 按字面不成立、按内容口径成立**：渲染层没有任何 Node 能力（`README.md:285`、`src/preload/index.ts` 全文无 `node:fs`），它写不了文件。定案为「**渲染层生成内容 + 主进程执行落盘**」——这正是既有先例 `IPC.indexBackup`（`src/shared/ipc.ts:78`、`src/main/index.ts:1832-1849`）的形状。
2. **写入侧天然单写者，不需要跨进程文件锁**：写盘必须只在拿到单实例锁后的 `bootstrap()` 内发生（`src/main/index.ts:890`、`:976-981`），第二实例「不读写 userData」（`:886-888`）。插件是**纯读方**，主进程是**唯一写方**——文件锁这条 PRD 假设可以取消。
3. **半写文件靠三件事防**：固定文件名 + 写 tmp 再 rename（`src/main/settings.ts:217-220`、`src/main/hdrDecode.ts:716-719`）＋ 串行写队列（`src/main/settings.ts:286`）＋ 写入顺序约定「先 `index.json`、后 `manifest.json`（manifest 存 index 的 SHA256）」。插件只读两个固定名，忽略一切 `*.tmp*`。
4. **规模判据已实测**：按 PRD §4 字段子集，单条记录紧凑 JSON 平均 **564 B**（`files` 只留 `rel/ext`）／**795 B**（含逐条 `generatedAt`），143 条样本实测 10/23（`.workbuddy/memory/2026-11-04.md:26` 是当前库统计：138 个四层资产目录 / 17.98 GB）⇒ **V1.0 全量单文件（≈78–110 KB）足够，不做增量、不分页**。判据写死为「记录数 ≤ 2000 且文件 ≤ 2 MB → 全量」；17.98 GB 是**素材载荷**，与索引无关。
5. **错误码共用一张表、不另立**：插件只能观测「文件状态」，写入侧失败的可观测形态必然落进 `IDBOX-101`／`IDBOX-102`；写入侧失败改用数据字段（`manifest.state` / `lastError`）承载。V1.0 定义 6 条（101–106），预留 107–110 四个编号但不定义，总数不超 10。

## 2. 偏离2 定案：快照文件由谁写

### 2.1 结论

| 层 | 职责 | 依据 |
| --- | --- | --- |
| **渲染层** | **生成内容**（读 Dexie → 按 §3.2 字段子集序列化 → 把字符串交出去） | 元数据唯一权威（`docs/16:108`「元数据以索引为权威」）；词表唯一真相源 `README.md:283` |
| **主进程** | **执行 IO**（目录、原子写、串行化、SHA256、manifest） | 渲染层拿不到 Node 能力（`README.md:285`），只能走 preload 白名单（`src/preload/index.ts:480`）；既有先例 `src/main/index.ts:1832-1849` 正是「渲染层传 JSON、主进程落盘（渲染进程无权写任意路径）」 |

⇒ PRD `docs/38 §6.1 偏离2` 里「建议由渲染层写」这一句：**按字面（渲染层直接 `fs.writeFile`）不成立，按内容口径成立**。主进程「只负责目录、原子写与文件锁」中的**文件锁这一项建议取消**——单实例锁已经保证只有一个进程能碰 userData（`src/main/index.ts:886-888`、`:976-981`），加跨进程文件锁是多余的复杂度，且它治不了真正的并发写问题（固定 tmp 名 + 无串行化，见 `src/main/settings.ts:225-238` 的实测现场：`rename` 抛 ENOENT、以及更隐蔽的「内容互相覆盖」）。**修法是串行写队列，不是随机 tmp 名**（同文件 `:237` 明确「换成随机 tmp 名只能消掉 ENOENT，治不了覆盖/乱序」）。

### 2.2 落盘位置（沿用 D1，不推翻）

`<userData>/plugin/` = `%APPDATA%\idbox\plugin\`，即 `userDataDir()`（`src/main/paths.ts:15-18`）下新增一个子目录；与 `thumbsDir()`（`paths.ts:20-22`）、`logDir()`（`logger.ts:78-81`）同级同风格——**既有落盘全在 `<userData>`**，这是项目纪律，不另立第二套根。

两个文件名固定：`manifest.json`、`index.json`。固定名是硬要求：插件不能猜路径（用户原话见 `docs/38:107`），带时间戳的文件名会让插件无从定位（`kindMigrate.ts:227` 那种时间戳文件名在这里**不适用**）。

新增设置开关（如 `pluginIndexEnabled`）必须按 `SettingsSchema` 的**单项降级**纪律：`.optional().catch(false)`（`src/main/settings.ts:74`、`:80`、`:91`——一个脏值只让这一项回落，绝不拖垮整份 settings.json，否则 `libraryDir` 一起丢、库会「消失」）。当前 schema（`settings.ts:54-60`）**没有任何插件相关键，需新增**。

### 2.3 写盘触发点（本文建议，待 §6 拍板）

| 触发点 | 位置 | 说明 |
| --- | --- | --- |
| **启动写一次** | `bootstrap()` 内、`settings` 到手之后（`src/main/index.ts:916`，`createWindow()` `:932` 之后） | 必须在 `bootstrap()` 内、受单实例锁保护；写在 `whenReady` 而非模块顶层，否则第二实例也会写 |
| **索引变更后** | `importBatchDone`（`src/shared/ipc.ts:172`）、`rescan`（`src/shared/ipc.ts:1529`、`src/renderer/store.ts:1582`，回写见 `store.ts:4554`）、分类指派提交、软删/还原提交、面板「手动刷新」 | 只算「会改变 §3.2 字段」的事件 |
| **不入触发集** | 缩略图涓流（`store.ts:593` 的单轮上限） | `thumbRel` 只在 `thumbStatus === 'ready'` 时写（`types.ts:99`、`:309-311`）；涓流会形成持续小流，不该触发写盘。建议「涓流结束后按下一轮 debounce 补写一次」 |
| **节流** | debounce quiet 窗口 **1.5 s** + max-wait 上限 **5 s**（连续变更流下仍保证最迟 5 s 落盘一次） | 与 `src/main/watcher.ts:40` 的 `stabilityThreshold: 3000` 同量级但更短；插件 3 s 轮询 ⇒ 端到端最坏延迟约 6–8 s，仍在 PRD D1 的 10 s 提示线内 |
| **定时兜底** | 建议**不设** | debounce + max-wait 已覆盖；PRD 的「新鲜度靠 10 秒提示条 + 手动刷新」承担剩余风险 |

**失败纪律**：写盘失败**不阻断主流程**（照抄 `src/main/kindMigrate.ts:256-261`「仅 `onWarn`、不阻断」），但**不照抄它的非原子写**（`kindMigrate.ts:254` 直接 `writeFile`，无 tmp+rename）。且**绝不写空内容掩盖失败**：渲染层取不到内容时保留上一份有效快照，把失败记进 `manifest.lastError`，读者看到的是「旧但完整 + 明确的错误状态」，而不是空文件。

## 3. 两个文件的格式规范

通用：UTF-8、**无 BOM**、LF、顶层为对象（不是数组）、JSON 值不做 pretty-print（单行紧凑，插件解析更快；体积见 §3.3）。所有路径字符串统一 posix 分隔符 `/`（照 `AssetFile.rel` 口径，`src/shared/types.ts:273-291`）。时间一律 ISO8601 UTC（沿用 `src/main/logger.ts:199` 与 `src/main/kindMigrate.ts:248` 的 `toISOString()` 口径）。

### 3.1 `manifest.json`（发现文件，E1 落点）

| 字段 | 类型 | 必填 | 可空 | 口径 |
| --- | --- | --- | --- | --- |
| `apiVersion` | string | ✅ | — | `"1"`，只增不删（`docs/36 Q10` / `docs/36:513`） |
| `appVersion` | string | ✅ | — | ID BOX 版本（`app.getVersion()` 口径，`src/main/index.ts:937`） |
| `generatedAt` | string | ✅ | — | 本次 manifest 落盘时刻，ISO8601 UTC |
| `libraryRoot` | string | ✅ | — | 绝对路径，即 `settings.libraryDir`（`src/main/index.ts:943`）；插件靠它现算绝对路径（E3 并入 E2，`docs/38 §4`） |
| `pluginIndexEnabled` | boolean | ✅ | — | 开关状态。插件读不到文件或此值为 false → `IDBOX-101`（PRD P0-2 文案「请在 ID BOX 设置里开启插件索引导出」） |
| `state` | string | ✅ | — | `"ok"` \| `"error"`。写入侧状态的**唯一承载方式**（见 §5） |
| `lastError` | object \| null | ✅ | ✅null | `{ code, message, at }`；`code` 用 §5 码表的码；`state === "ok"` 时为 null |
| `indexSha256` | string | ✅ | — | **`index.json` 落盘字节的 SHA256**（小写 64 hex，无 BOM）。命名写明是 index 的哈希，不叫 `sha256`（manifest 无法含自身哈希） |
| `indexBytes` | number | ✅ | — | 字节数，用于快速判定 |
| `indexCount` | number | ✅ | — | 记录条数 |
| `thumbsRoot` | string | ✅ | — | `thumbsDir()`（`src/main/paths.ts:20-22`）—— PRD §6.1 偏离3 要求 manifest 暴露它，插件直接读本地缩略图 |
| `freshnessHintSeconds` | number | ✅ | — | 建议 `10`，与 PRD D1（`docs/38:166`）一致；插件读它做提示条，不硬编码 |

写入顺序（**硬约定**）：① 生成 index 内容 → ② 写 tmp、rename 成 `index.json` → ③ 计算 SHA256 → ④ 写 tmp、rename 成 `manifest.json`。读者永远只看到「完整的旧文件」或「完整的新文件」；两个 rename 之间的窗口是**唯一不一致窗口**，插件的处置见 §3.4。

### 3.2 `index.json`（资产快照，E2 落点）

信封 + 记录数组：

```json
{
  "apiVersion": "1",
  "generatedAt": "2026-11-04T10:00:00.000Z",
  "libraryRoot": "E:/ModVault/Library",
  "count": 138,
  "records": [
    { "id": "…uuid…", "name": "…", "kind": "texture", "category1": "材质", "category2": "贴图",
      "source": "知末网", "zhimoId": null, "relFolder": "材质/贴图/…",
      "mainFile": "…cover.png", "files": [{ "rel": "…", "ext": "png" }],
      "thumbRel": "…png", "suMajor": null }
  ]
}
```

记录字段（按 PRD §4 的清单逐条定型）：

| 字段 | 类型 | 必填 | 可空 | 口径与出处 |
| --- | --- | --- | --- | --- |
| `id` | string | ✅ | — | UUID 主键，**永不因改名/改库/改大类而变**（`src/shared/types.ts:294-295`，`docs/01 P0-7`）——插件侧唯一锚点 |
| `name` | string | ✅ | — | **原样 `Asset.name`**（`types.ts:296`）。面板展示时自行套 `displayName()`（`src/shared/naming.ts:114`）。不在快照里预先折叠，避免与词表口径耦合 |
| `kind` | string | ✅ | — | 六值：`model\|texture\|hdri\|material\|cad\|other`（`src/shared/types.ts:19`）。⚠️ **新发现：PRD §7 的 `idbox_kind` 值枚举缺 `other`**（`docs/38:151`），须补齐；本文按 `types.ts` 为准 |
| `category1` | string | ✅ | ✅null | 单段词表词；未分类 = `未分类`（`src/shared/taxonomy.ts:19`，判据 `:1170`） |
| `category2` | string | ✅ | ✅null | 同上 |
| `source` | string | ✅ | ✅null | 与 `Asset.source` 对齐（`types.ts:299`） |
| `zhimoId` | string \| null | ✅ | ✅null | `types.ts:391` 显式可 null ⇒ 快照里写 `null`（不省略），便于插件区分「无」与「未提供」 |
| `relFolder` | string | ✅ | — | posix 相对库根（`types.ts:303`）；配合 `manifest.libraryRoot` 现算绝对路径 |
| `mainFile` | string \| null | ✅ | ✅null | **派生值，不是 `Asset` 字段**（`grep mainFile src/` 无命中）。由 `pickPrimaryFile()`（`src/shared/classify.ts:436`）按 P0-14 优先级派生（`classify.ts:423`：`.skp > .max > .fbx > .obj > .3ds > 首个模型文件 > 首个 CAD 文件 > files[0]`；`PRIMARY_MODEL_EXTS` `classify.ts:302`）。CAD 必须显式收进来，否则 `files[0]` 只是目录遍历顺序 |
| `files` | array | ✅ | — | **每项只两键**：`rel`（相对资产文件夹、统一 `/`，`types.ts:273-291`）、`ext`（小写）。`name`/`size`/`kind`/`w`/`h` 不进快照（J2「不暴露 schema」，`docs/38:32`） |
| `thumbRel` | string \| null | ✅ | ✅null | **仅当 `thumbStatus === 'ready'`** 时写（`types.ts:99`、`:309-311`）；相对 `manifest.thumbsRoot` |
| `suMajor` | number \| null | ✅ | ✅null | `types.ts:317`；用于插入前版本预警（`IDBOX-104`）。实测样本缺失率高：76/143 = 53% ⇒ 必须可空，插件不得假定有值 |

**与 PRD §4 的一处架构偏差**：`generatedAt` 从「逐条字段」改为「**信封级一次**」。逐条写约 +231 B/条（实测：含逐条 `generatedAt` 795 B/条 vs 只留 `rel/ext` 且信封级 564 B/条）。逐条时间戳改用 P1 可增字段 `updatedAt`（`types.ts:414-415`），符合「只增不删」。

**软删记录不入快照**：判据照现有视图 —— `store.ts:556` `assets.filter((a) => !isDeletedAsset(a))`（判据来自 `store.ts:40`）。回收区是库内概念，插件无删除视图，写进去会污染搜索结果。

**不含字段（显式声明）**：`tags` / `note` / `styles`（J2，`docs/38 §4`；`docs/16:108` 元数据以索引为权威但这类自由字段属 schema 风险面）。

### 3.3 规模与增量策略

实测（`_probe_db/assets-full.json`，143 条，10/23 抓的旧样本，非当前工作树；按 PRD §4 字段子集计算）：

| 口径 | 平均/条 | 138 条全量 |
| --- | --- | --- |
| 信封级 `generatedAt` + `files` 只留 `rel/ext`（本文规范） | **564.2 B** | **≈ 78 KB** |
| 含逐条 `generatedAt` | 795.2 B | ≈ 110 KB |
| 全字段原始记录（含 `tags/note/size/w/h` 等） | 1041.2 B | ≈ 144 KB |

其他实测分布：平均每条 `files` 4.12 项；`relFolder` 最长 66、`name` 最长 55；软删 13/143；`suMajor` 缺 76/143。

**判据（写死）**：
- `记录数 ≤ 2000` **且** `文件 ≤ 2 MB` ⇒ **全量单文件 `index.json`**（V1.0 走这条，当前库离阈值差一个数量级）。
- 超过 ⇒ 按大类分册（`plugin/index/<category1>.json` + manifest 列分册清单）或 NDJSON 流式；**这是 V1.0 之后的事，本轮不设计增量协议**。
- 不做增量/分页的理由：全量 78 KB 的读取代价远低于增量协议的复杂度（增量需要 `since` 语义、删除墓碑、版本对账——正是 J2 要避免的「插件跟着 schema 碎」，`docs/25:2203`）。
- ⚠️ **17.98 GB 是素材载荷，不是索引载荷**（`.workbuddy/memory/2026-11-04.md:26`：138 个四层资产目录 / 17.98 GB / thumbs 229 文件 28 MB）。不能拿 GB 当分册判据。

### 3.4 插件读前如何避免读到半写文件

1. 只读两个固定名：`manifest.json`、`index.json`。**忽略任何 `*.tmp*`**；插件目录下除这两个文件外不应有其他内容，出现即跳过。
2. 读 `manifest.json` → 校验 `apiVersion === "1"`（未知版本 → `IDBOX-101` 的「版本不匹配」分支）。
3. 读 `index.json` → 重算 SHA256 → 与 `manifest.indexSha256` 比对。
4. **不一致的处理**：因为两个 rename 之间存在唯一不一致窗口，一次不一致**先当作"正在写"**：下一轮轮询重试；**连续 3 轮仍不一致才报 `IDBOX-102`**。这条把「半写」和「读到窗口」分开，避免误报。
5. 文件缺失 / 不可读 / JSON 解析失败 → `IDBOX-101`（含「未开导出」，靠 `pluginIndexEnabled`）。
6. 写入侧失败的可观测形态只有两种，都落在既有码里：文件不存在 = 101；文件存在但校验/解析失败 = 102。因此不需要为写入侧另立码（§5）。
7. **Windows 上 rename 失败不止跨盘**（`src/main/fsutil.ts:61-63`、`:98-100`：目标已存在且非空 → `EPERM/EEXIST/ENOTEMPTY`；被占用 → `EBUSY/EACCES`）。这里的好处是：`rename` 失败时**原文件保持不动** ⇒ 插件仍看到一份完整可用的旧快照，降级是优雅的。要求插件**开-读-关，不跨轮持有文件句柄**（否则它自己就是那个"被占用"的原因），主进程侧则不做盲目重试、把失败记进 `manifest.lastError`。

### 3.5 插件侧文件监视的对应约定

SketchUp Ruby **没有跨进程 IPC，也没有可靠的文件系统 watcher**【推断】⇒ **只能轮询**。建议 **3 s** 轮询一次（与 `src/main/watcher.ts:40` 的 `stabilityThreshold: 3000, pollInterval: 500` 同量级），且：
- 只在面板打开时轮询；面板关闭即停止（不占 CPU、不常驻）。
- 轮询的是 `manifest.json` 的 `generatedAt`，变了才读 `index.json`（省 SHA256 重算）。
- 面板显示「索引更新于 X 秒前」，> `manifest.freshnessHintSeconds`（默认 10 s）给提示条 + 手动刷新（PRD D1，`docs/38:166`）。手动刷新 = 强制下一轮立即重读，**不能触发主进程写盘**（插件无任何写权限、无 IPC）。

## 4. 插件包规范

### 4.1 硬约束（写死）

### 4.2 目录约定（`.rbz` 内 = 恰好两项）

`.rbz` 是「改名的 ZIP」【查证】，官方要求包内**恰好两项**：一个根 `.rb`（只做扩展注册、含扩展元数据）+ 一个**与根 `.rb` 同名（去掉 `.rb`）的支持目录**（其余全部内容都在这里）【查证：`ruby.sketchup.com/file.extension_requirements.html`】。照此：

```
idbox_panel-1.0.0.rbz                ← 分发物，ZIP 归档，恰好两项
  idbox_panel.rb                     ← 根注册文件（registrar）：仅注册扩展 + 元数据（名称/作者/版本/版权），不含逻辑、不加载其它文件；文件名必须纯 ASCII
  idbox_panel/                       ← 支持目录（与根 .rb 同名）
    main.rb                          ← 实际逻辑入口，靠 SketchupExtension.new(..., "idbox_panel/main") 指向这里
    panel.html                       ← 本地 HTML 面板（UI::HtmlDialog，docs/36:128 已查证该类存在）
    lib/                             ← 纯 ASCII 文件名，纯 ASCII 内容标识
    native/<platform>/<rubyVer>/     ← V1.0 不产出任何文件，只立目录约定（见下）
```

- **安装后落点**：SketchUp 把 `.rbz` 解到当前用户 Plugins 目录，运行时看到的就是「根 `.rb` + 同名目录」。Plugins 目录含 Windows 用户名，不可控（见 §4.4）。
- **注册类名与插件目录确切路径【待核实】**（`docs/36:128` 明确标注未一手核实），本文不写死。官方模板用的是 `SketchupExtension.new(...)` + `Sketchup.register_extension(EXTENSION, true)`【查证】，但确切类名与新旧名仍按 `docs/36:128` 保持【待核实】。
- **包内取文件用 `Sketchup.require "idbox_panel/xxx"`（不带 `.rb`）而非 `require` / `require_relative`**【查证】；所有代码包在单一唯一命名模块内、不用全局变量【查证】——这两条是 `.rbz` 共享运行环境的硬要求，不是风格建议。
- **按 Ruby 运行时分叉目录**：照 `docs/37:56` 立 `native/<platform>/<rubyVer>/` 约定（可搭鸭按 2.7 / 3.2 / 3.4 分叉，串不匹配报 `RVL-103`）。**V1.0 无原生件，这条只是"将来需要时照此立目录"的约定，不产出文件**（`docs/38 §6` 第 2 行）。
- Ruby 语法下限：门槛 SU 2021+（`docs/38 §2.4`、`docs/37:75-80`）⇒ 按 Ruby 2.7 兼容写法，不用 3.x 才有的语法。
- 编码：包内所有文件 UTF-8、**无 BOM**；`.rb` 首行不加 magic comment 依赖（见 §4.4）。

### 4.3 分发 / 安装 / 运行 三层区分（v1.1 新增，回应"后缀是 .rbz"口径）

| 层 | 是什么 | 谁执行 | 与既有硬约束的关系 |
| --- | --- | --- | --- |
| **分发** | `idbox_panel-x.y.z.rbz`（ZIP 归档，恰好两项，见 §4.2） | ID BOX 打包产出 | 与 §4.1 第 1 条一致；明文源码打进包内，不加密 |
| **安装** | 把 `.rbz` 装进 SketchUp | **用户经「扩展 → 安装扩展 / Extension Manager」选 `.rbz` 完成**【查证：help.sketchup.com 安装流程】 | 解压属于**安装动作**，不属于插件运行时行为 → 与 §4.1 第 6 条「插件不解压、不读压缩包」**不冲突** |
| **运行** | Plugins 目录里的根 `.rb` + 同名支持目录 | SketchUp 加载 | 插件运行时仍只读、零网络、零原生件、不解压 |

**"一键安装"能不能自动化 ——【推断】+【待核实】**：Ruby API 侧没有可靠的"从外部脚本安装 `.rbz`"的公开接口【推断】。所以 D3 的"一键安装"只有两种可定义形态：

1. **仅导出 `.rbz`**，用户在 SU 的扩展管理器里选它安装（走官方路径，会被扩展管理器登记、可启停）；
2. **ID BOX 把 `.rbz` 内容（根 `.rb` + 支持目录）直接复制到 Plugins 目录**——技术上最直接，但这条**可能不会被扩展管理器登记**（没有走注册流程，可能只是"脚本"而非"扩展"，启停与元数据显示会缺失）**【待核实】**，且它意味着 **ID BOX 侧要具备解压能力**（Node 侧可行，属应用侧而非插件侧）。

D3 尚未拍板，这条口径并入 D3（见 `docs/38 §8.2`）。

### 4.4 Windows 非 ASCII 路径（风险约定）

- **实证部分【查证】**：可搭鸭把文件搬到纯 ASCII 缓存根 `C:/okducky/runtime` 再 `load`（`docs/37:92`），这条路径的存在说明 **SketchUp 在 Windows 上加载非 ASCII 路径的本地扩展会出问题**。
- **场景差异【推断】**：我们插件读的是 JSON 里的**数据路径**（素材路径常态含中文是正常业务），不是加载自身原生件；插件自身文件在 SU Plugins 目录下，**该目录含 Windows 用户名、不可控**。这条区别是【推断】，必须真机核实（核实方式：在用户名含中文的机器上，从 Plugins 目录 `load` 一个明文 `.rb`，看是否成功）。
- **处理口径（本文定，三条）**：
  1. 插件**自身文件名纯 ASCII**（`idbox_panel.rb` / `panel.html`），不依赖任何含中文的子目录；
  2. 读 JSON **显式指定 UTF-8**：Ruby 的 `Encoding.default_external` 在 Windows 上不一定是 UTF-8【待核实】，因此读时显式 `mode: 'r:UTF-8'`（等价口径），并对读到的字符串做 `force_encoding('UTF-8')` 校验；写侧（主进程）已保证 UTF-8 无 BOM；
  3. **安装时检测当前用户名非 ASCII，给一次明确提示**（例如「当前用户目录含非 ASCII 字符，若插件加载异常请将 ID BOX 用户改用纯 ASCII 路径」）——这是**提示，不是错误码**，不占用 §5 的码表。是否额外立一个 ASCII 备用发现根（如 `C:\idbox\plugin`）见 §6 第 2 条。

## 5. 错误码归属

**结论：共用同一张码表，不另立一组。V1.0 定义 6 条（`IDBOX-101..106`），显式预留 107–110 四个编号但不定义，总数 ≤ 10。**

理由（三条）：

1. **插件是纯读方，它只能观测"文件状态"。** 写入侧失败的可观测形态只有两种，且都已经在既有表里：文件缺失/未开导出 = `IDBOX-101`；文件存在但解析/校验失败（含半写）= `IDBOX-102`。写入侧另立一组码，会产生「只有 ID BOX 自己看得懂、无法在面板显示」的码，直接违反 P0-5（失败语义可读）与 P0-6（可诊断）。
2. **写入侧失败改用数据字段承载，不用码承载**：`manifest.state = "error"` + `manifest.lastError = { code, message, at }`。`code` 复用同一张表（写入侧失败若可归入 101/102 就归入），面板显示时读的是字段、不是新码。这样「写入侧」与「插件侧」在用户面前是同一语言。
3. **不扩张码表数量**：预留编号不算定义。建议预留区间用途只写口径、不写条目：107–110 留给未来「Ruby 运行时不匹配（借 `RVL-103` 的形态，`docs/37:56`）／JSON 库缺失／插件目录不可写（P1-4 双向通道时才有意义）／自身路径非 ASCII（§4.4 真机核实后若确证会失败才需要）」。在真机核实之前**不定义这四条**——避免把【推断】当契约。

保留 PRD §6.2 的六条原文语义不动：101 发现文件缺失 ｜ 102 JSON 解析/校验失败（含半写） ｜ 103 路径失效（快照与盘不符，等价 `410 GONE`）｜ 104 `.skp` 版本高于当前 SU（用 `suMajor`）｜ 105 路径越界被拒 ｜ 106 SU 版本低于门槛。三件套形态照 `docs/37:57`（错误码 + 结构化日志 + 用户可见诊断页），日志落 ID BOX 既有日志面（`src/main/logger.ts:78-81`）。
