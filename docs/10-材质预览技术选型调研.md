## 1. 问题 A：材质球预览怎么实现

### 1.1 先独立评估用户提的三个方向

用户原话提了「内置一个小体积虚幻引擎 / Unity / GitHub 上有没有开源渲染器」。逐一独立评估（不先入为主）：

**① Unity（WebGL 导出）——不推荐。**
- 体积：Unity 6000.0.23f1 默认空项目 WebGL 构建 **9.7MB**，极限优化后 **2.2MB**（Playgama 实测）；Unity 6 空项目 BiRP 构建 7.7MB，剥离后 2.3MB（visionarylab 实测 gist）。带真实贴图/着色器的典型场景 **30-100MB**。体积本身在 500MB 预算内不是问题，**问题是工作流**：要用 Unity Editor 建工程、写 C#、走 IL2CPP 构建链，每次改预览逻辑都要在编辑器里构建产出物再塞进 Electron。团队 C# 能力有限，这是高权重否决项。
- License：Personal 免费（年收入/融资 <20 万美元），Pro $2,040/年/席；2023 年 Runtime Fee 争议后政策已修订取消（generalistprogrammer 2025 对比文）。Personal 版有启动画面（Unity 6 免费版可关，据 visionarylab gist）。
- 结论：为一个「把几张贴图贴到球上」的需求引入完整游戏引擎，投入产出比最差。

**② Unreal Engine——不推荐（且比 Unity 更差）。**
- UE 自 4.24 起**移除了原生 HTML5 导出**，UE5 的浏览器交付只剩 Pixel Streaming（UE 5.7 重写为 Pixel Streaming 2）：游戏跑在带 GPU 的服务器上，WebRTC 视频流推给浏览器，**每个用户需要一个 UE 实例**（cinevva 2026 引擎对比）。这与「完全本地离线单机」直接冲突——要么本地常驻一个 UE 实例+信令服务器，要么违背离线约束。
- UE 5.4+ 有实验性 WebGPU RHI、UE 5.8 有 HTML5 打包路径，但属演进中的实验功能（多个中文博客源，可信度低，标注【待核实】），首包下载体积大、对浏览器 GPU 有硬性要求。没有任何理由选它。
- 结论：**用户这个方向可以明确划掉**，且这是三个方向里最不该选的。

**③ GitHub 开源渲染器——方向对，但要挑对项目。**
- 调研中发现的开源「材质预览」项目分两类：一类是 **C++ 桌面小工具**（如 josephHelfenbein/material-viewer，MIT，11★，2025-08 仍在更新，支持拖入单张贴图或 .zip 预览；FrMarchand/pbr-material-viewer，MIT，C++/OpenGL + imgui）——是完整软件不是可嵌入库，对 Electron 项目没有复用价值；一类是**完整材质创作工具**（RodZill4/material-maker，MIT，5,983★，2026-10-07 有提交，基于 Godot）——是给美术做材质的，不是给浏览器嵌预览的。
- 真正对口的「可嵌入 Electron 渲染进程」的开源渲染器是 WebGL/WASM 系的：three.js / Babylon.js / Filament / model-viewer。这才是有效候选集，见下节。
- 另有 renky1025/threejs-viewer（three.js + React 的工业级查看器，内置用 PMREMGenerator + RoomEnvironment 做的材质球实验室）证明 three.js 路线做材质球是社区验证过的成熟做法。

### 1.3 分方案详评（要点）

**three.js（推荐）**
- MIT，零依赖，719KB min / 180.6KB gzip（bundlephobia v0.186.1），116,340★，当日仍有提交。
- r186 同时提供 WebGLRenderer 与 WebGPURenderer（bestofjs 镜像的 README：「current builds only include WebGL and WebGPU renderers」）。Electron 33 = Chromium 130.0.6723.44（官方 release 页），WebGL2 是保底路径；WebGPU 在该内核可用（单一中文来源称 Electron 33 支持 WebGPU API），可作为后续升级选项而非首日依赖。
- 材质球关键能力全部齐备：`MeshPhysicalMaterial`（map / normalMap / roughnessMap / aoMap / displacementMap / clearcoat / sheen / iridescence / transmission）、`PMREMGenerator` + `RoomEnvironment`（**程序化生成环境光照，零 HDRI 文件、零下载**，三个独立来源确认用法：`pmrem.fromScene(new RoomEnvironment(), 0.04)`）、`OrbitControls`、ACESFilmic/AgX/Neutral 色调映射（bundlephobia 导出清单里确认 `AgXToneMapping`/`NeutralToneMapping` 存在于 r0.186.1）。
- 风险点：WebGL 通用瓶颈（如海量同屏材质球时上下文数量上限——Chromium 约 8-16 个活跃 WebGL 上下文，超过会掉上下文；单球预览 + 按需创建可规避）【推断】。

**Babylon.js（备选）**
- Apache-2.0，26,161★，TS 原生编写，open issues 仅 18（维护质量信号很好）。
- 优势：内置 Inspector（可视化调材质参数，设计师联调神器）、Node Material、官方 Sandbox/Playground。如果未来预览要往「可调参数面板」深走，它的工具链比 three.js 现成。
- 劣势：体积大一个量级（ES6 按需 ~352KB gzip，UMD 全量 1.7MB gzip）；为一个静态材质球引入 Engine/Scene/Camera 一整套概念，代码量比 three.js 方案多。

**Filament（质量天花板，但不推荐）**
- Apache-2.0，20,598★，Google 背书、月级发版（v1.77.0 于 2026-09-15，据 hysenlabs 项目页）。
- 致命伤是工程组织而非技术：C++ 核心 + JS 绑定暴露面小（2021 年即有中文技术博客指出「最简单的点击交互都不支持，相机自动旋转要改 C++」），材质必须经 matc 编译（运行时编译器 filamat「large」），团队 C++ 能力有限。wasm ~2.3MB gzip 在 500MB 预算内完全可接受——**否决它的不是体积，是维护与定制成本**。
- 什么条件下改选它：若未来要做移动端 AR 预览（Filament 在 Android/iOS 是原生渲染器，同一份编译产物跨平台），或预览质量要求上升到 Filament 独有的特性（如 ray tracing preview、cloth sheen 细节），再重新评估。

**model-viewer（不推荐用于本场景）**
- 70.9KB gzip 很香，但它 peer-depend three.js 且**只接受 glTF/GLB**。「贴图→材质球」要么在 three.js 里直接做（那为什么不直接用 three.js），要么先 GLTFExporter 导出 GLB 再喂给它（多一层无收益转换）。它是「给网页嵌模型查看器」的答案，不是「给材质库嵌材质球」的答案。

### 1.4 推荐方案落地细节（three.js）

技术组合（均为已验证存在的 API）：
- `three@^0.186` + `three/addons/controls/OrbitControls.js` + `three/addons/environments/RoomEnvironment.js`
- 渲染器：`WebGLRenderer({ antialias: true })`，`outputColorSpace = SRGBColorSpace`，`toneMapping = ACESFilmicToneMapping`（或 AgX，r162+ 引入），`setPixelRatio(min(devicePixelRatio, 2))`
- 环境：`PMREMGenerator.fromScene(new RoomEnvironment(), 0.04)` → `scene.environment`；`environmentIntensity` 可调。**不需要任何 .hdr 文件，天然满足离线**。若设计师觉得「摄影棚感」不够，可后续内置 1-2 个小体积 HDRI（1-3MB/张）作为可选环境【推断】
- 贴图→材质映射：BaseColor→`map`；Normal→`normalMap`；Roughness→`roughnessMap`；AO→`aoMap`；Displacement/Height→`displacementMap`；Metallic/Specular→按需
- 色彩空间纪律：BaseColor/Emissive 贴图 `colorSpace = SRGBColorSpace`；Normal/Roughness/AO/Displacement 保持线性（NoColorSpace）——PBR 正确性的关键，错了会「发灰发脏」【推断，行业通行实践】
- 法线约定：three.js 默认 OpenGL 约定（+Y 向上）；UE/Unity 生态出的 DirectX 法线贴图（-Y）建议提供「翻转 G 通道」开关【推断】
- 几何体：`SphereGeometry(1, 128, 64)` 起步；建议提供 球 / 圆角盒 / 圆柱 / 平面（平铺检查）四种形态切换——设计师验材质不只看球，还要看平铺【推断】
- 交互：OrbitControls + 空闲自动旋转 + on-demand 渲染（无输入不重绘，省电）；点击/拖拽手势与现有资产网格不冲突
- 导出 PNG：渲染同帧 `renderer.domElement.toBlob()` 或 `preserveDrawingBuffer: true`——设计师常需要「存一张效果图」【推断】
- **Electron 纹理加载**：渲染进程受 `webSecurity` 限制，直接 `file://` 贴图进 WebGL 会被 CORS 拦。建议扩展现有 `vault://` 自定义协议（docs/04 显示主进程已有 `vault://thumb/<name>` 模式）增加 texture 路由并带 CORS 头，或走 IPC 读文件转 data URL【推断，基于 docs/04 代码摘要的协议模式】
- **React 集成**：自研 hook（`useEffect` 里建 renderer/scene，卸载时 dispose）约 150-200 行即可；**不建议**上 @react-three/fiber（32,930★，MIT，当日有提交，很优秀）——为单个材质球引入声明式渲染抽象，收益不抵成本。若未来要做复杂 3D 场景再迁移【判断】
- 性能：单球 + 2048px 画布，任何独显/核显都无压力；同屏多球时注意 WebGL 上下文上限（Chromium 约 8-16 个），建议「选中项才开 WebGL，列表项用静态缩略图」【推断】

### 1.5 备选与改选条件

- **备选：Babylon.js**。改选条件：① 团队决定做「材质参数可视化调试面板」且想直接用官方 Inspector；② 愿意接受 ~1.5MB min 的 JS 体积；③ 需要 Node Material 做程序化材质演示。
- **改选 Filament 的条件**：要做 Android/iOS AR 预览；或需要 Filament 独有的渲染特性；或团队补充了 C++ 能力。
- **永远不选**：UE Pixel Streaming（违背离线单机）；Unity WebGL（为一个预览引入引擎工作流，除非未来整个产品要变成 3D 配置器——那时应该整体重新选型，而不是为材质球选型）。

## 2. 问题 B：英文材质名「显示中文、不改文件名」

### 2.1 需求拆解

- 磁盘文件名保持英文原名（SU 等 DCC 靠名字找贴图，改名即断链）——**这是不可动的硬约束，也正好是翻译层唯一正确的落点：只动显示层**。
- 用户场景：从 Crystal 等站下载的材质包，命名风格类似 `OakWoodPlanks_4K_BaseColor.jpg` / `Textures/Marble_Polished_2K_Normal.png`，多张贴图一个目录。
- 用户是设计师：**错译比不译更烦**。「橡木木板」优于「树木木材厚板」，「拉丝铝」优于「刷过的铝」。宁可显示英文，不能显示似是而非的中文。
- 压缩包结构样本未到（按多贴图目录假设），映射规则需在样本到达后校准——但下述 L1/L3 不依赖样本，可先做。

### 2.2 离线中英方案调研（已查证）

**① 通用离线词典：ECDICT（推荐的地基）**
- `skywind3000/ECDICT`：**MIT**，**8,427★**，最近推送 2025-03-28（成熟稳定，非活跃开发型），**76 万+词条**（多个中文来源一致），提供 `ecdict.csv` / `ecdict.mini.csv`（精简版）/ `stardict.7z` / `lemma.en.txt`（词干），官方推荐转 SQLite 查询。
- 对材质名的意义：`Oak` / `Planks` / `Marble` / `Granite` / `Travertine` 这类常见材质词都能命中；词条带 BNC/COCA 词频标注，可用于「一词多义时选高频/材质域义项」的启发。
- 局限：通用词典，不懂「PBR 槽位」「4K」「ORM」；组合词（OakWoodPlanks）不会作为词条存在，必须拆分。

**② 建材/材质专业术语库：没有找到权威开源方案（如实报告）**
- 搜索未发现高质量、可持续维护的开源「建筑材料中英术语库」GitHub 项目；命中的是博客级词汇表（wordln 等，不可作为工程依据）和 MidJourney 关键词列表（英文单语，无中文）。
- MDict（.mdx）/灵格斯（.ldic）生态里存在大量第三方词典（含建材类），但许可与质量参差、需人工甄别，不建议作为默认依赖【推断】。
- **替代思路（本项目的独特优势）**：docs/07 已抄录取自知末网的完整中文分类词表——22 个一级分类（石材/砖材/大理石/木地板/瓷砖/木纹/地毯/外景/木材/挂画/玻璃/金属/壁纸壁画/布纹/皮革/墙面地面屋面/HDR贴图/涂料/凹凸贴图/素材贴图/商业元素）+ 195 个二级分类。这是**行业内正在流通的中文材质词汇**，反向映射成英文（Stone/Brick/Marble/Wood Flooring/Tile/Wood Grain/Carppet/Exterior/Timber/Glass/Metal/Wallpaper/Fabric/Leather/Paint…）就是一份高质量的领域中文词表，比任何通用词典都懂设计师的语言。建议以此为主、ECDICT 兜底。

**③ PBR 槽位命名：有权威标准可依**
- glTF 2.0 规范（Khronos）定义标准槽位：`baseColorTexture`、`metallicRoughnessTexture`（G=粗糙度、B=金属度）、`normalTexture`、`occlusionTexture`、`emissiveTexture`；行业惯例还有 UE/Substance 系的 `BaseColor/Normal/Roughness/Metallic/AO/Displacement/Height/Bump/ORM`（ORM = R:AO/G:Roughness/B:Metallic 打包）。这是一个**封闭小集合**，做一张映射表即可 100% 覆盖，零错译风险。

### 2.3 组合词拆分 + 词典映射：可行性评估

以 `OakWoodPlanks_4K_BaseColor` 为例的规则化流程：

1. **分词**：按 `_ - . 空格` 切 → `[OakWoodPlanks, 4K, BaseColor]`
2. **驼峰再切**：`OakWoodPlanks` → `[Oak, Wood, Planks]`
3. **停用词过滤**：`4K`（分辨率徽标）、`CG`/`Poliigon`/`AmbientCG`/`cc0`/`texture`/`tex` 等发行商标记 → 移出名称、进结构化徽标【停用词表需人工维护，推断】
4. **分层查典**：槽位词典命中 `BaseColor` → 「基础色」；材质词表命中 `Oak/Wood/Planks` → 「橡木/木/板」→ 按中文语序拼接「橡木板」；分辨率「4K」作徽标
5. **未命中保留英文**：任何 token 查不到 → 原样保留，绝不猜

**可行性结论**：
- 槽位词（L1）：**100% 可行**，封闭集合，收益确定性最高。
- 材质核心词（L2）：**80/20 可行**。常见词（橡木/大理石/花岗岩/瓷砖/皮革/玻璃/金属/混凝土/砖）命中率高；风险集中在：① 同形异义词（`Cherry` 樱桃 vs 樱桃木、`Pearl` 珍珠 vs 珠光、`Marble` 大理石 vs 大理石纹）——需一份小的**人工 override 表**；② 品牌/人名/生造词（`Kawaii`、`Poliigon`）——靠停用词 + 未命中不译兜底；③ 语序（`Brushed Aluminum` 直译「刷过的铝」不如「拉丝铝」）——同样靠 override 表修正高频案例。override 表随用户反馈持续增长，是可控工程。
- 综合：**值得做，但必须是「词典驱动 + 未命中不译 + 人工 override」的保守形态，不能是全自动机器翻译**。

### 2.4 做 / 不做 / 怎么做：明确建议

**做。分三层，优先级从高到低：**

| 层 | 内容 | 错译风险 | 建议 |
|----|------|---------|------|
| **L1 结构化标签** | PBR 槽位封闭词典（BaseColor→基础色、Normal→法线、Roughness→粗糙度、Metallic→金属度、AO→环境光遮蔽、Displacement→置换、Height→高度、Bump→凹凸、ORM、Emissive→自发光、Opacity→不透明度…）+ 分辨率（2K/4K/8K）+ 平铺标记（Tileable/Seamless）→ **不进名称，做 UI 徽标/筛选器** | ≈0（封闭集合 + 有 glTF 标准背书） | **必做，且不等样本** |
| **L2 保守名称翻译** | 拆分算法（§2.3）+ 双词典（知末词表反向映射为主 + ECDICT 76 万词条兜底）+ 人工 override 表 + **未命中保留英文** | 低-中（override 表可收敛） | **做保守版**；命中即显示中文，不命中显示英文原文 |
| **L3 用户别名** | 用户在 UI 里给任何资产/目录设中文别名，存本地数据库（Dexie/JSON），**磁盘文件名不动** | 0（用户自己定的） | **强烈建议**——这是根治「错译烦人」的方案：自己的库自己说了算 |

**明确不做：**
- ❌ 在线翻译 API（百度/有道/Google 等）：违背「完全本地离线」硬约束，且质量不可控。
- ❌ 对未命中词强行直译/音译：`Zlj3Wood` 译成「zlj3 木」没有意义，反而污染列表。**不译 > 错译**。
- ❌ 修改磁盘文件名：SU 等软件靠名字找贴图，改名即断链，用户已明确「不改变文件本身名字」。

**落地顺序建议**：L1（第一批，零风险高收益）→ L3（别名存储 + UI，用户可控）→ L2（等压缩包结构样本到达后校准停用词/override 表再上）。

## 5. 推断清单（未经查证，基于经验/推理，采信前请知悉）

1. three.js 完整渲染层 bundle ≈ 800KB min / ~230KB gzip，electron-builder 压缩后安装包增量 ~0.3MB。
2. aoMap 的 UV 通道自 r151 起与 map 统一（uv2 废弃），可直接使用；具体以采用版本文档为准。
3. DirectX/OpenGL 法线贴图 G 通道翻转开关为行业通行做法（UE/Unity 导出资产常见）。
4. BaseColor 贴图 sRGB / 数据贴图线性的色彩空间纪律为 PBR 通行实践。
5. Chromium 活跃 WebGL 上下文上限约 8-16 个，同屏多球需「选中项才开 WebGL」。
6. Electron 渲染进程加载本地贴图受 CORS/webSecurity 限制，需扩展 `vault://` 协议或走 IPC（基于 docs/04 已有 `vault://thumb/` 模式推理）。
7. 内置 HDRI 文件 1-3MB/张的体积量级。
8. 停用词表（CG/Poliigon/AmbientCG/cc0…）与 override 表（Cherry→樱桃木、Brushed Aluminum→拉丝铝…）需人工维护，为设计提案非既有资产。
9. UE 5.8 HTML5 原生打包的实验性状态仅见于中文博客（低可信），本文未采信其可用性。
10. Babylon ES6 按需体积为单一第三方测量（webcodingcenter），与 bundlephobia UMD 数字差异大是因为构建形态不同，两者均列出供交叉参考。
