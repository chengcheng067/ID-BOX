## 1. 结论先行（按影响从大到小）

| # | 根因 | 一句话 | 预计收益 |
|---|---|---|---|
| **R1** | **8K 原图在渲染进程里被解码了两遍**，且中间那张全尺寸位图只是为了量宽高 | `loadTexture` 先 `createImageBitmap(blob)` 全解 8192²（482ms / 256MB），再带 `resize` 又解一遍（434ms）。原木色那张单图一次切换要 **~960ms** | 去掉第一遍：**-50%**（960→437ms），峰值内存 **256MB→4MB**，约 10 行 |
| **R2** | **单图资产每次切换都在主线程现算一张法线图，且 `getImageData` 是 GPU 同步回读** | 用户框出的两个样本都是"单图 → 没有 normal 槽位" → 每次切换都走 `synthesizeNormalIfMissing`，**44ms 主线程长任务**，正好卡在舞台"就绪放行"那一刻 | canvas 加 `willReadFrequently:true`：`getImageData` **30.7ms→0.4ms**（77×），整段 44→~12ms，2 行 |
| **R3** | **没有跨资产贴图缓存，也不取消在途加载** | `applyMaps` 一进来就 `dispose` 掉全部旧贴图（MaterialBall.tsx:599）；旧一代的加载只在**解码完成之后**才判 gen 丢弃（:683）→ 扫过 10 张卡就是 10 次全解码排队，双击要排在它们后面 | 切回场景 960ms→0；扫卡排队问题消失。中等实施量 |
| **R4** | **没有落盘的"球用贴图"预降采样产物** | 同一个 8K 文件每次都被重新解一遍，而它实际只需要一张 **161KB / 1024²** 的图（主进程 `nativeImage` 443ms 可一次生成，完全不占 UI 线程） | 8K 切换 960ms → **~36ms**（25×）；这是根治 8K 的唯一办法 |
| **R5** | **每次切换触发 9 个 shader program 重编译 ≈ 42ms** | 渐进式挂图 = 6 次 `material.needsUpdate` → 6 个 program 变体；实测每槽位"编译+上传"7.6–12.2ms | 预编译常用组合，可省 20–30ms；中等实施量 |

> **一句话总结**：GPU 和实时渲染**完全不是瓶颈**（稳态帧 0.2–0.9ms）；卡的是**「贴图进入显存之前」的那段
> CPU/解码/主线程活**，而其中最大的一块（8K 双解码 482ms + 主线程法线合成 44ms）**是纯浪费**。

## 2. 实测数据

### 2.1 Q1 · 这些图片的真实像素尺寸（文件头解析，不解码）

解析算法与 `src/shared/imageSize.ts` 完全一致（PNG IHDR / JPEG SOFn），只读前 64KB。

| **现代红砖_外墙_墙砖 ID_1193950340** | `.png` | 8.23 MB | 2048 × 2048 | 16 MB | 全解 87ms ／ 降采样解 54.5ms |

| 无缝黑色木纹 | `.jpeg` | 3.48 MB | 2600 × 4971 | 49.3 MB | — |

**三条必须记住的结论：**

1. **文件 MB 与解码成本完全不成比例。** 用户说"这两个材质本身的体积是不小的"——
   但 8.2MB 的**红砖只有 2048²**（解码 87ms，一点不快但也不慢），
   **13.1MB 的原木是 8192²**（解码 482ms，是红砖的 5.5 倍）。
   按 MB 判断"哪个更卡"会判错方向，必须看**像素数**。
2. **确实存在 8192×8192 的图。** 本机 `MAX_TEXTURE_SIZE = 16384`，所以不会硬失败；
   但集成显卡 / 老核显常见 `MAX_TEXTURE_SIZE = 8192` 甚至 `4096`，
   在那类机器上 8192² **直接上传失败**（球会一直停在灰白色）。这一条对"用户机器上卡不卡"是**环境依赖**的。
3. **单个 8K 贴图的解码中间产物是 256MB**。这还没算 mipmap（+33%），
   一次切换的瞬时峰值 ≈ 300MB —— 必然触发 GC，而 GC 暂停落在主线程上。

### 2.2 Q5 · 逐段量化基线

#### (a) 单张贴图：现状路径 vs 去掉第一次全解【实测，ms】

现状路径 = `MaterialBall.tsx:361-380` 的真实顺序：`fetch` → `createImageBitmap(blob)`（全尺寸）→
`createImageBitmap(blob,{resizeWidth})`（降采样）。

| 图 | fetch | 全尺寸解码 | resize 解码 | **现状合计** | 只解码一次（带 resize） | 差额 |
|---|---|---|---|---|---|---|
| 原木色 8192² | 44 | 482 | 434 | **960** | 437 | **-523ms（-54%）** |
| 红砖 2048² | 17 | 87 | 54.5 | **158** | 72 | -86ms |
| 混凝土地面 4K albedo | 24 | 147 | 140 | **310** | 156 | -154ms |
| 混凝土地面 4K normal | 22 | 149 | 133 | **304** | 161 | -143ms |
| 混凝土地面 4K roughness | 18 | 112 | 95 | **225** | 118 | -107ms |
| 混凝土地面 4K AO | 13 | 94 | 79 | **185** | 97 | -88ms |
| 混凝土地面 4K disp | 4 | 66 | 55 | **126** | 58 | -68ms |

**证据**：第二次 `resize` 解码耗时（434ms）≈ 第一次全解（482ms），说明它**不是复用第一遍的解码结果，
而是把 JPEG 从头解了第二遍**。这一条是 R1 成立的核心实测依据。

**关键负面结论（很重要，能挡掉一个错方案）**：调 `resizeQuality` / 目标尺寸**几乎没用**——

| 参数 | 8192² 解码耗时【实测】 |
|---|---|
| `resizeQuality:'low'` → 1024 | 410.8ms |
| `'medium'` → 1024 | 437.1ms |
| `'high'` → 1024 | 425.3ms |
| `'medium'` → 2048 | 432.5ms |
| `'medium'` → 512 | 423.4ms |

Chromium 对 JPEG **没有走 scaled decode**（1/2、1/4、1/8 那套），所以
"降到 512 就快了"是错的 —— 解码熵解码这一段的时间是固定的 ~410ms 下限。
**渲染进程侧再怎么调参也压不到 410ms 以下**，要根治必须换地方（见 §4 方案 C）。

#### (b) 五槽位 PBR 预设：串行 vs 并行【实测】

| 场景 | 耗时 |
|---|---|
| 5 张贴图**并行**解码（`Promise.all`） | **364 ms** |
| 5 张贴图**串行**解码 | **1175 ms** |

→ 现在 `applyMaps` 是 `entries.map(async ...)`（MaterialBall.tsx:632-636），**已经是并行**，这一点不用改。
但并行会把 5 张 4096² 位图（5×64MB = 320MB）同时压在内存里 —— 见 §4 方案 F 的"并发上限 3"。

#### (c) WebGL 侧：渲染根本不是瓶颈【实测，RTX 4080 SUPER】

| 项 | 耗时 |
|---|---|
| `new WebGLRenderer`（459² canvas, antialias） | **12.9 ms**（一次） |
| `RoomEnvironment + PMREMGenerator.fromScene`（首次） | **40.7 ms**（冷启动首跑 409ms，含流水线预热） |
| 首帧（无贴图） | 8.3 ms |
| **稳态帧**（已编译、已上传） | **0.2 ms（P95 0.4ms）** |
| 逐槽位「挂图 + 重编译 + 上传 + 渲一帧」 | albedo 10.5 / normal 8.2 / roughness 7.6 / ao 7.8 / disp 7.9 ms |
| **5 槽全挂 = 42 ms，program 总数 9 个** | |
| 全部贴图重新上传（`needsUpdate` 后再渲一帧） | 23.7 ms |

裸上传（`texImage2D` + `generateMipmap` + `readPixels` 强制同步）：

| 纹理尺寸 | 上传耗时 | 显存（RGBA8，不含 mipmap） |
|---|---|---|
| 1024² | 1.0–2.3 ms | 4 MB |
| 2048² | 2.8–4.1 ms | 16 MB |
| 4096² | 4.3–8.9 ms | 64 MB |
| 8192² | 15.2–33.6 ms | **256 MB** |

**结论：** 稳态 0.2ms / 上传 1ms / 编译 8ms —— 用户说的"实时渲染压力很大"在 GPU 上不成立。
唯一真实的 GPU 侧成本是 **42ms 的 shader 重编译**（R5），而且它是**一次性尖峰**，不是持续掉帧。

#### (d) 主线程法线合成（单图资产必经，用户两个样本都是单图）【实测】

`normalFromBitmap`（MaterialBall.tsx:292-348）在 384px 上跑：

| 步骤 | 384px | 1024px（如果把 NORMAL_FROM_ALBEDO_PX 调大） |
|---|---|---|
| `ctx.drawImage(bitmap, 0,0,w,h)` 降采样 | 0.6–11.2 ms | 0.1 ms |
| **`ctx.getImageData()`** | **30.7–40.3 ms** | 12.7–17.3 ms |
| Sobel 双循环（147k px × 8 邻域） | 10.9–17.0 ms | 68.5–69.3 ms |
| `putImageData` | 0.1 ms | 0.2–0.3 ms |
| **合计** | **44.4 ms** | **87 ms** |

**优化对照【实测】**（同一张 1024² 位图，同一个 canvas 尺寸）：

| 配置 | getImageData |
|---|---|
| `getContext('2d')`（现状） | **30.7 ms** |
| `getContext('2d', { willReadFrequently: true })` | **0.4 ms** |
| 384px + `willReadFrequently` 整段 | **0.7 ms**（read 0.4 + draw 0.2） |
| 256px + `willReadFrequently` 整段 | **1.2 ms** |

`getImageData` 在这条路径上是**同步 GPU→CPU 回读**（每帧新建 canvas，Chromium 选了加速落点），
所以一加 `willReadFrequently` 就掉到 0.4ms。**这是全篇性价比最高的一行改动。**

#### (e) 长任务实测（`PerformanceObserver('longtask')`）

在"8 张图 + 2 次法线合成 + GPU 段"整段序列中捕获到 **2 次长任务：87ms、93ms**。
其中 87ms 与 `synth 1024` 的单次实测（87.0ms）精确吻合 →
**法线合成就是这条路径上唯一能把主线程按住 ~90ms 的同步块。**

#### (f) 主进程 `nativeImage` 预降采样可行性【实测，Electron 自带，无需 sharp】

| 源图 | 解码 | `resize`→1024 | `toJPEG(82)` | 产物 |
|---|---|---|---|---|
| 原木色 8192² | 390.7 ms | 43.2 ms | 9.0 ms | **160.9 KB** |
| 混凝土地面 4096² | 114.9 ms | 14.2 ms | 17.6 ms | 129.3 KB |
| 红砖 2048² | 36.9 ms | 5.1 ms | 6.4 ms | 264.5 KB |

**443ms 一次性成本，跑在主进程（不占渲染主线程）**，产出一张 161KB 的图。
之后渲染进程读这张图：`fetch` 5ms + 解码 ~20ms。**这是把 8K 从 960ms 压到 ~30ms 的唯一低成本路径。**

### Q2 · 切换资产时到底重建了什么

**① 场景/renderer 只在挂载时建一次 —— 这一条已经修好了，不用再动。**

```ts
// src/renderer/components/MaterialBall.tsx:1069 / :1121
useEffect(() => {
  ...
  ball = new BallScene(canvas, { shape, interactive: true })   // :1080
  ...
  ball.startLoop()                                             // :1110
  return () => { ro.disconnect(); ballRef.current = null; ball.dispose(); canvas.remove() }
}, [])                                    // :1121  ← deps 为空 = 与组件同生共死
```
```ts
// src/renderer/components/MaterialBall.tsx:1126-1128
useEffect(() => {
  void ballRef.current?.applyMaps(urlsRef.current)   // 换资产只换贴图
}, [urlsKey])
```

**② 一次切换新建几个 WebGL context？** → **0 个**（主路径）。
`dispose()` 里的 `forceContextLoss()`（:834）只在组件卸载时走。
**但有一条旁路**：网格球图缩略图管线 `renderBallThumbFor`（`src/renderer/store.ts:3178-3185`）
每渲一张球就 `new BallScene(...)`（→ 新建 context）再 `dispose()`（→ `forceContextLoss`）。
它是串行队列（`runBallQueue`，store.ts:3230）、批上限 40（store.ts:75）、每张之间 `yieldToIdle`，
所以不会撞 Chromium 的 8–16 上限；但**每张都是一次"全量解码 + 新建/销毁上下文"**，
对 8K 资产就是每秒级别的后台重活。

**③ 贴图跨资产复用缓存？** → **完全没有。**

```ts
// src/renderer/components/MaterialBall.tsx:591-606
applyMaps(urls: MaterialSlotUrls): Promise<void> {
  this.mapsReady = false
  const gen = ++this.mapsGen
  for (const t of this.maps) t.dispose()   // :599  ← 旧贴图立刻释放，没有"留着备用"
  this.maps = []
  clearMaps(this.material)
  ...
  this.material.needsUpdate = true         // :606
```
```ts
// src/renderer/components/MaterialBall.tsx:676-686（loadMap）
const tex = await loadTexture(url)
if (!tex) { ... }
if (this.disposed || gen !== this.mapsGen) { tex.dispose(); return }   // :683
```
`gen` 令牌只保证"旧结果不贴到新球上"，**不阻止旧加载继续烧 CPU**：
`loadTexture` 里没有 `AbortController`、没有 `signal`，`fetch` 和两次 `createImageBitmap`
会完整跑完。扫过一排材质卡 = 一排全尺寸解码排在解码线程池里，
用户双击时新的解码只能排在队尾 → **这就是"点击的时候卡"的排队来源**。

**④ `motionQuality` 三档到底用在哪？**

| 档位字段 | 用了吗 | 位置 |
|---|---|---|
| `dprCap` | ✅ | 构造 `MaterialBall.tsx:471`，热改 `:807` |

### Q3 · 主线程在切换瞬间被什么占住

按发生顺序（全部在渲染进程）：

| # | 同步重活 | 位置 | 成本【实测】 |
|---|---|---|---|
| 1 | `fetch` + `blob()`（大文件跨进程搬运） | :361-363 | 4–44ms（8192² 那张 13MB 是 44ms） |
| 2 | **全尺寸 `createImageBitmap`** | :365 | **482ms**（8K），**只为拿 `bmp.width/height`** |
| 3 | 第二次 `createImageBitmap`（带 resize） | :371-376 | **434ms** |
| 4 | **`normalFromBitmap`：drawImage + getImageData + Sobel + putImageData** | :292-348 | **44ms 纯主线程**（其中 30.7ms 是 GPU 回读） |
| 5 | 逐槽位 `material.needsUpdate` → shader 重编译 | :701 / :606 | 7.6–12.2ms/槽，5 槽 **42ms** |
| 6 | 贴图上传（首次渲染时） | three 内部 | 1024² ≈ 1–2ms |
| 7 | React 重渲染 | 见 Q4 | 小 |

**「`OffscreenCanvas` / `createImageBitmap` 的 resize 参数可用但没用」这一条：**
resize 参数**已经用了**（:371-376），但用法错了 —— 见 §2.2(a)：
它是在"先全解一遍"之后又解一遍。真正没用上的是 **`imageSizeOf`（`src/shared/imageSize.ts`）**：
项目里明明有一份"只读文件头拿宽高、绝不解码"的纯函数，且 `importer`/`rescan` 已经在用，
`loadTexture` 却用"解一遍 8K"来拿宽高。

**上采样/下采样策略：现在会不会把 8K 原图原样上传 GPU？**
→ **不会上传原图**（:367-380 已经降到 ≤1024）。但**解码过程是原图**，而且解了两遍，
**265MB 的中间位图只是为了读两个整数**。

### Q4 · 网格卡片是否也有份

**结论：不是这一轮的原因，不建做优化。**

- 封面走**离屏渲染好的 PNG 缓存**，不是实时 canvas：
  ```tsx
  // src/renderer/components/AssetGrid.tsx:258-267
  function Cover({ asset, name }) {
    if (asset.thumbStatus === 'ready' && asset.thumbPath) {
      return <img src={thumbVaultUrl(asset.thumbPath)} loading="lazy" ... />
  ```

## 4. 优化方案

> 「预期收益」全部以 §2 的实测值为基准；「实施量级」按"几行 / 小改 / 中改 / 重构"标注。

### ⭐ 方案 A · 去掉第一次全尺寸解码（**先做这条**）

- **做法**：`loadTexture`（MaterialBall.tsx:358-399）不再先 `createImageBitmap(blob)`。
  宽高改用 `imageSizeOf(new Uint8Array(await blob.slice(0, 65536).arrayBuffer()))`
  （`src/shared/imageSize.ts` 现成，无新增依赖、无额外 IO —— blob 已经在内存里），
  然后**只做一次** `createImageBitmap(blob, { imageOrientation:'flipY', resizeWidth, resizeHeight, ... })`。
  只有 `longest <= MAX_TEX_PX` 的图才走不带 resize 的分支。
- **预期收益**：8K 单图 **960 → 437ms（-54%）**；4K 每槽位 **-140~155ms**；2K **158 → 72ms**。
  峰值位图内存 **256MB → 4MB**（GC 压力基本消失）。
- **风险**：极低。`imageSizeOf` 对非 PNG/JPEG（webp/bmp/tga）返回 `null` → 回退到"解一遍拿尺寸"的旧路径即可。
  以及 `exr` 本来就解不了（`EXT_RANK` 里 exr 最劣，`materialBall.ts:61-70`，同槽位有 jpg 时会被 jpg 顶掉），行为不变。
- **实施量级**：**约 12 行**，单文件。

### ⭐ 方案 B · 法线合成的 canvas 加 `willReadFrequently` + 尺寸 384→256（**先做这条**）

- **做法**：`normalFromBitmap`（:296-299）
  ```ts
  const ctx = cv.getContext('2d', { willReadFrequently: true })   // +1 个参数
  ```
  并把 `NORMAL_FROM_ALBEDO_PX`（:270）从 384 降到 256（256 在球上依然够，实测 Sobel 只要 ~5ms）。
- **预期收益**：`getImageData` **30.7ms → 0.4ms**；整段 **44ms → ~1–5ms**。
  **这一条直接消掉实测到的 87/93ms 长任务**，也就是用户双击时"卡一下"的那个尖峰。
- **风险**：极低。256px 合成法线的观感损失可忽略（原图在球上也只有 ~459px）。
- **实施量级**：**2 行**。

### 方案 C · 主进程预生成"球用贴图"并落盘缓存（**根治 8K**）

- **做法**：新增一个 IPC（例如 `ballTex:ensure`）——
  用 Electron 自带 `nativeImage`（**不需要 sharp/jimp**，项目里也没有）：
  `nativeImage.createFromPath(abs)` → `.resize({width:1024,height:1024,quality:'good'})` → `.toJPEG(82)`
  → 写到 thumbs 目录下的子目录（如 `thumbs/ball/`），缓存键 = `rel + mtime + size + maxPx`。
  渲染进程的 `loadTexture` 改为：**先请求这张小图；拿不到（或未生成）才回退读原图**。
  生成时机：导入时 / 首次 hover 预热时 / `runBallQueue` 里顺手做，**全部在主进程，不占 UI 线程**。
- **预期收益**：8K 单图切换 **960ms → ~36ms**（fetch 5 + 解码 20 + 上传 1 + 编译 10）；
  4K 预设 5 槽 ≈ **100ms**。**而且从此 8K 再也不会进入渲染进程。**
  额外好处：`MAX_TEXTURE_SIZE=8192/4096` 的老 GPU 上不再有上传失败风险。
- **风险**：中等。① 新增落盘目录要纳入 `pruneThumbs`/`thumbStats` 的清理口径，否则会漏清；
  ② 源图被替换后 mtime 变了要能失效（缓存键里带 mtime 即可）；
  ③ 需要一条"生成失败静默回退原图"的兜底（和现有贴图失败只 warn 的风格一致）。
- **实施量级**：**中改**（主进程 ~60 行 + preload 一行 + 渲染层 ~20 行）。**建议安排为下一个独立任务。**

### 方案 D · 贴图跨资产缓存（切回来不重解码）

- **做法**：模块级 `Map<string, Texture>` LRU（key = `url + '@' + maxPx`，上限 8–12 张）。
  `applyMaps` 不再无脑 `dispose`（:599），命中缓存直接复用。
  注意：`Texture` 与 renderer 绑定，所以缓存**必须**按 `WebGLRenderer` 分组
  （可复用 `sharedEnvCache` 那套 `WeakMap<WebGLRenderer, …>` 的写法，:246）。
- **预期收益**：A↔B 来回切（正是用户"每一次换材质点击"的场景）**960ms → 0**；
  hover 预热过再双击 → 0 成本（现在预热完再切回另一张，第一张就作废了）。
- **风险**：显存。1024²×4B = 4MB/张，12 张 = 48MB，可接受；上限要硬编码。
- **实施量级**：**小-中改**（~40 行）。

### 方案 E · 取消在途加载（只服务最后一代）

- **做法**：`applyMaps` 持有 `AbortController`；新一代进来时 `abort()` 上一代，
  把 `signal` 一路传到 `fetch(url, { signal })`。解码本身不可中断，但
  **至少不再有 N 个 `fetch` 并发抢带宽/解码线程**，且旧一代可以更早退出。
- **预期收益**：扫过 10 张材质卡的场景从"10 次全解码排队"变成"最多 1 次在跑 + 1 次在等"。
  对用户可感知的改善在**双击前的等待时间**上（不再排在队列里）。
- **风险**：低。要小心 `AbortError` 不要打成 warn 刷日志。
- **实施量级**：**小改**（~25 行）。

### 方案 F · 渐进式挂图 + 预编译 + 并发上限

- **做法**：三条一起（都属 R5）：
  1. 保持现在的"albedo 先上屏"（:631-636），但 **`ao` / `displacement` 改到 `requestIdleCallback` 里挂**
     —— 这两个对观感贡献最小、却各要一次 program 重编译 + 一次上传。
  2. `applyMaps` 里那次 `material.needsUpdate = true`（:606）在"本来就没有贴图"时可省，
     减掉一次"空 → 空"的无用重编译。
  3. PBR 预设的**并行解码上限 3**（现在 `entries.map` 无上限，5 张 4096² = 320MB 同时驻留）。
- **预期收益**：首帧前的重编译从 6 次降到 1–2 次（**42ms → ~10–20ms**）；
  峰值内存从 320MB 降到 ~192MB。
- **风险**：`requestIdleCallback` 在持续忙碌时会被推到 500ms 后（`AssetGrid.tsx:1600-1608` 已有同类处理），
  要给 `timeout` 兜底，否则 ao/disp 可能永远不挂。
- **实施量级**：**中改**。

### 方案 G · hover 预热的"取消 + 最短停留"

- **做法**：现在 `onPointerLeave` 会 `cancelPrewarm(hoverTimer)`（`AssetGrid.tsx:1679-1682`），
  但**一旦 `stageController.preview(a.id)` 发出去了就不会撤回**
  （`stageController.ts:78-81` 只写 `previewId`）。补一个"离开时 `preview(null)`"，
  并让舞台在 `previewId === null` 时**保持当前贴图不动**（现在会把 `asset` 变成 `null`）。
  注意 `MaterialStage.tsx:603` 的 `if (!slots.albedo) return null` 会**卸载整个 MaterialBall
  → `dispose()` → 丢掉 WebGL 上下文**，下次进来要重建 renderer + 重烘 PMREM（12.9 + 40.7ms）。
  改成"没有 albedo 就渲一颗灰球、保持挂载"。
- **预期收益**：快速划过一排卡时零浪费解码；避免"扫一遍卡 → 舞台反复重建上下文"。
- **风险**：低，但要确认 `preview(null)` 不会导致 `stageMounted` 抖动（`App.tsx:411-413`）。
- **实施量级**：**小改**（~30 行）。

### 方案 H · 详情面板文件行 / 拖拽卡片预热的原图解码

- **做法**：`DetailPanel.tsx:62-66` 里 `cardThumb` 对图片文件直接给**原图 URL**，
  `dragCard.ts:122-130` 用 `new Image()` 加载后 `drawContain`（只画到 176×176）。
  一张 8192² JPEG 会按自然尺寸（256MB）解码，只为了画 176px。
  改用方案 C 产出的 ≤1024 预览图（或至少 `thumbVaultUrl`）作为 `thumbUrl`。
- **预期收益**：文件行 hover 时不再有 480ms 级解码（这条路径用户"划过文件列表"就会踩到）。
- **风险**：观感上 176px 卡片用 1024 图完全够。
- **实施量级**：**小改**（~10 行，依赖方案 C 或退化为读缩略图）。

## 5. 不建议做的事（以及为什么）

| 不建议 | 为什么 |
|---|---|
| **换渲染引擎 / 上 WebGPU** | 稳态帧 **0.2ms**，5 槽上传 23.7ms。GPU 完全不是瓶颈，换引擎纯亏一年工期。 |
| **降 DPR / 关抗锯齿 / 降几何细分** | 稳态 0.2–0.9ms，888 段球体网格不是问题。省下来 <1ms，却直接掉画质。 |
| **"全部贴图降到 512"** | 实测 8192² 解码到 512 仍要 **423ms**（跟降到 1024 的 437ms 没差）。**解码成本与目标尺寸无关**，这一刀砍不到痛点。 |
| **把 Sobel 搬进 Web Worker** | 44ms 里 30.7ms 是 `getImageData` 的 GPU 回读。加 `willReadFrequently` 变 0.4ms 就解决了；搬 worker 还要把 590KB 像素过一遍结构化克隆，反而更慢。 |
| **优化网格卡片 / 给 AssetGrid 加 memo** | 19 个资产、虚拟滚动、封面是磁盘缓存 PNG。量级 1–3ms，跟 960ms 不是一个问题。真要加 memo 是另一件事，别混进来。 |
| **`forceContextLoss()` 改掉 / 复用全局 renderer** | 现在的"每卸载一次就归还上下文"是对的（Chromium 8–16 上限）。真正的浪费不在上下文，在解码。 |
| **引入 `sharp` / `jimp`** | `nativeImage` 实测 8K 解码 391ms + 缩放 43ms + 编码 9ms 已经够用，且是 Electron 自带、无需原生模块编译、不增加安装体积。 |
| **在渲染进程里对 8K 做 canvas 二次降采样** | 那要先付 482ms 全解 + 256MB 内存，等于把 R1 又做一遍。 |

## 6. 落地顺序建议

| 顺序 | 事项 | 量级 | 累计效果（用户两个样本） |
|---|---|---|---|
| 1 | 方案 B（`willReadFrequently` + 256px） | **2 行** | 消掉 87ms 长任务；双击不再"顿一下" |
| 2 | 方案 A（去掉全尺寸解码） | **~12 行** | 原木色 1014 → **~490ms**；红砖 202 → **~84ms** |
| 3 | 方案 E（取消在途）+ 方案 G（预热撤回） | ~60 行 | 扫卡不再排队；不再反复重建上下文 |
| 4 | 方案 D（贴图跨资产 LRU） | ~40 行 | 切回来 **0ms** |
| 5 | 方案 C（主进程预降采样落盘） | 中改 | 原木色 **~36ms**；8K 永不进渲染进程 |
| 6 | 方案 F（idle 挂 ao/disp + 并发 3） | 中改 | 42 → ~15ms 重编译，峰值内存 -40% |

**1+2 两条加起来不到 15 行，就能拿走一半以上的体感卡顿**——建议这一批先合。

## 附录 B · 本次测量的局限（必须如实标注）

- 所有数字来自 **一台 RTX 4080 SUPER 的台式机**。GPU 侧数字（稳态 0.2ms、上传 1–15ms）在核显上会更差，
  但结论方向不变：**解码（CPU 侧）比上传（GPU 侧）贵 1–2 个数量级**。
- `getImageData` 的 30.7ms 有**"新 canvas 首次回读"**的成分（同尺寸第二次只测到 2ms）。
  但真实代码路径**每张图都新建一个 canvas**（:296），所以"每次都付首次回读成本"才是真实情况。
- 解码耗时受**磁盘缓存/OS 文件缓存**影响；本机源文件已被反复读过，`fetch` 的 4–44ms 属**乐观值**，
  冷启动首次访问会更慢（机械盘/网络盘上差距可达数倍）。
- **没有**在真实 ID BOX 界面里跑端到端帧率采样（需要在 `App.tsx` / `MaterialStage.tsx` 里插桩，
  违反本次"不改 src"的边界）。所有"一次切换总耗时"都是**分段实测之和**【实测项相加】，
  不是一次端到端计时；这部分属**"分段实测 + 组装推断"**，已在表内逐项标注来源。
