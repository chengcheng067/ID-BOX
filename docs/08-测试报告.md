## 5. autoClassify 质量攻击测试（本轮重点）

> 方法：esbuild 打包纯函数 + 真实 `importPaths` 在 `os.tmpdir()` 落盘实测（临时脚本，已删）。50 个真实知末风资产名 + 12 组异常输入 + 4 组文件名协同场景 + rescan 回读。

### 5.1 命中率粗估（50 个常见知末素材名）

| 结果 | 数量 | 占比 |
| --- | --- | --- |
| **二级命中**（`<一级>/<二级>/`） | 16 | **32%** |
| 只命中一级（`<一级>/未分类/`） | 3 | 6% |
| 全未命中（`未分类/未分类`） | 31 | **62%** |

**给用户的预期管理：智能预分类目前大约能自动落对 1/3 的资产**（中文产品名；英文/拼音命名约 0%，刻意保守防误伤）。未命中的 62% 不是 bug，是词表覆盖面 + 构词法缺口（见 5.2/DEF-16），全部安全落 `未分类/未分类` 等用户指派——**宁可漏、不错**的取向执行得很干净，50 个样本里**零语义误命中**（唯一的"跨频道落类"见 DEF-15）。

### 5.4 异常输入与落盘形状（**DEF-14 实证**）

**异常输入全部安全**：`../../windows/system32`、`C:\evil\sofa`、纯符号、500 字点号+沙发、800 字「沙」、`\0`、emoji、`con`、SQL 注入串、超空白——全部 null 或安全命中，无崩溃、无穿越（分类值只能来自受控词表，词表无 `..`/`\`）。

**但含 `/` 词条的落盘形状破坏固定四层契约**：

```
importPaths('北欧椅子.png')  →  category2 = '椅子/凳子'（词表完整词条）
磁盘实际：贴图/家具/椅子/凳子/北欧椅子/      ← 五段！
relFolder = 贴图/家具/椅子/凳子/北欧椅子     ← 五段

重启/rescan 回读实测（rescanLibrary）：
  name=凳子   cat=家具/椅子     relFolder=贴图/家具/椅子/凳子   ← 资产名变成「凳子」、
  （真实资产目录 凳子/北欧椅子 被吞成一层，category2 丢失「凳子」）
```

受影响词条 = 词表 4 个含 `/` 词条的 8 个子词（**椅子、凳子、灯膜、灯罩、壁炉、火焰、毛毡、毛呢**）。「椅子」是家具第一高频品类，**任何以这些词结尾的资产在重启后名字/分类都会损坏**。→ 开 **DEF-14（严重）**。

#### DEF-14 已修（0.7.8）

> 上面那张表是**当时的开单记录，保持原样不改**。本节只记「后来怎么修的」。

**根因（实测确认）**：导入侧把 `classifyAssetName()` 给的**原始**分类值直接喂给
`path.join(libraryDir, kind, category1, category2)`，而 `relFolder` 走
`composeRelFolder()`（内部把 `/` 换成 `_`）。两条口径不一致 → 磁盘五段、记录四段、
`asset.folder ≠ path.join(libraryDir, asset.relFolder)`；rescan 固定三层下钻（磁盘为权威）
读成 `category2='椅子'`、`name='凳子'`，**分类与资产名同时损坏**。

**修法**（只改导入侧，`composeRelFolder` / `sanitizeCategorySegment` / `rescan.ts` 一行未动）：

1. `src/main/importer.ts` 新增纯函数 `resolveCategorySegments(category1, category2)`，

## 9. 缺陷清单（只开单，不修码）

### P0（阻塞发布）：**无**

### P1（建议本批内修）：2 条

#### DEF-Z1 · 手动路径未参与 `zhimoCoverRunning` 互斥锁（偏离设计 §4.6 硬要求）

- **设计原文**（§4.6）：「模块级 `zhimoCoverRunning` 布尔**同时锁住自动与手动**」，并给了具体的坏结局：
  `手动写 jpg（删掉 png）→ 自动写 png（删掉 jpg）→ 手动最后 commit(rel=jpg) → DB 指向一个已被删除的文件`。
- **实现事实**：`refreshZhimoCover`（`store.ts:2492-2522`）**既不检查也不置位** `zhimoCoverRunning`；代码注释明确写了「不受 `zhimoCoverBusy` 拦截……真正的手动/自动互斥由主进程的『同族清理 + 原子写』保证」——但 `writeCoverImageInto()` 是 `removeStaleCovers()` 后 `writeFile()`，**两步之间没有原子性**，注释里的这个保证**不成立**。同时 `runZhimoCovers` 也不检查 `zhimoCoverBusy`。
- **可达路径**：一批导入的第 1 个包 done 后用户点它的「从知末取封面」（请求在飞，约 0.4–1s），期间该批次 `import:batchDone` 到达 → `runZhimoCovers` 因 `zhimoCoverRunning === false` 照跑，且该资产此刻 `coverSource` 仍是旧值 → 被再次选中 → 两个写者同目录竞争。
- **后果**：DB 的 `cover` 可能指向已被同族清理删掉的 rel → 卡片封面空白、详情面板 404；**一次 rescan 即自愈**（`s.files` 里找不到就回落到扫描值），**不丢用户数据**，故不判 P0。
- **修法（约 5 行）**：`refreshZhimoCover` 开头 `if (zhimoCoverRunning) return { ok:false, reason:'network' }`，进入时置 `zhimoCoverRunning = true`、`finally` 复位；或直接按设计 §5.2 让手动也走 `runZhimoCovers([id], { force: true })`（现成的 `force` 分支已实现且已测，只是**生产路径没接**）。

#### DEF-Z2 · 单批 >50 个模型时，第 51 个起**永远不会**自动抓封面（违反 §4.3「超过则分块串行、不丢弃」）

- **设计原文**（§4.3）：「单批上限 **50**；超过则**分块串行、不丢弃**，块间停 2s」。
- **实现事实（两处叠加丢弃）**：
  1. `enqueueZhimoCover()`（`store.ts:148`）：`if (pendingZhimoIds.length >= ZHIMO_COVER_MAX_BATCH) return` → 第 51 个起的 id **根本没进队列**；
  2. `pickZhimoCoverTargets()` 的 `limit` 默认 `ZHIMO_COVER_MAX_BATCH`（=50），而 `runZhimoCovers` **不传 `limit`** → 即使 pending 里有 60 个也只出 50 个目标。
- **实测**：我构造 60 个合法模型资产调 `pickZhimoCoverTargets` → **输出 50 个**（脚本打印 `[E-1e] 60 个资产 → 50 个目标`）。`runZhimoCoverQueue` 的分块能力本身是好的（120 目标 → 50/50/20 已测），**但生产路径喂不进 >50**。
- **后果**：用户一次拖入 60 个模型包 → 后 10 个**没有任何封面**，且**不会重试**（pending 已消费）。不是错封面、不是数据损坏，但用户会认为功能"漏抓"。手动按钮可逐个补 → 缓解。
- **修法**：`runZhimoCovers` 里把 pick 的 `limit` 显式传 `Infinity`（或循环消费 pending 直到空），让队列自己的 chunkSize=50 负责分块；`enqueueZhimoCover` 去掉 50 上限（或改成"按块消费"）。**队列侧无需改动**。

### 13.6 关于 `{ok:false}` 不带 `reason` 的取舍 —— **接受**

三条理由：

1. **它不产生歧义，因为 notice 已经把原因说清楚了**。这个分支唯一入口是"用户点了按钮但没抢到锁"，UI 上必然同时出现「正在后台获取封面，请稍后再试」，用户不需要 `reason`。
2. **塞 `network` 会污染统计**。`reason` 枚举是 main/renderer 共用的（`shared/types`），main 侧 `logWarn('zhimo:cover-failed', {reason})` 靠它做归因；一个根本没发出去的请求记成"网络失败"，会让"网络失败率"这个指标永久失准。宁缺毋滥是对的。
3. **类型契约允许**（`reason?:`），运行时是扁平结构，调用方写 `if (!r.ok)` 即可。

唯一建议（已记为 DEF-Z7）：`FetchZhimoCoverResult` 头顶那句注释还写着「`ok === false` 时**只有** `reason`」，现在已经不成立，请改成「`ok===false` 且**无 reason** = 未发起抓取（如后台任务占用）」。**不建议**为此新增 `'busy'` 枚举项——那个枚举被 main 共用，而 main 永远不可能产生 `busy`，加进去是给共享契约塞一个死分支。

## 19.6 缺陷清单

### DEF-19-1（P1 · 渲染层 + 主进程契约）超时兜底后弹窗不消失，之后的点击被静默吞掉

- **现象**：故意不答复 120s 后，主进程已按超时兜底全跳过、`importPaths` 已返回 0 条、库无变化，
  但 `ImportConflictDialog` **仍留在屏幕上**（截图 `C4-timeout-dialog-stuck.png`）。用户此时点「确定」/「全部取消」，
  主进程回 `import:conflict:answer … phase:"stale"`（WARN），**界面无任何反馈**——点得动，什么也没发生，弹窗也不关。
- **复现**：制造一次同名冲突 → 不点任何按钮 → 等 120s → 观察弹窗 → 点「全部取消」→ 看日志。
- **证据**：日志三段（`phase:"timeout"` → `phase:"stale"`）；截图弹窗仍在，且此时明细已变成"库里还有 1 份同名副本"。
- **责任面**：渲染层 `store.answerConflict` 只在**自己答复**时清 `conflictAsk`；主进程超时是**单方面**结束，
  没有把"这次询问已作废"回推渲染层（没有 `conflict:closed` / `onImportConflictSettled` 之类的下行事件）。
  修法二选一：① 主进程超时/取消时向渲染层推一条"作废"事件，`store` 收到后清 `conflictAsk`；
  ② 渲染层对 `conflictAsk` 起同款 120s 兜底计时，到点自清并提示"已超时，全部按跳过处理"。
- **影响**：用户看到的是一个"永远等你选"的弹窗，但他选的每一下都不生效 —— 比"没弹窗"更迷惑。

### DEF-19-2（P1 · 交付流程）交给 QA 的包不是当前源码构建的

- **现象**：`out/renderer/assets/index-D3lLpn0j.js` 与 `app.asar` 的时间戳是 `00:34:11` / `00:34:16`，
  而 `src/` 里此后一直在改（验收结束时最新改动到 `00:51`）。打包**之后**才落盘的至少有：
  `renderer/logic/importConflict.ts`（00:36）、`main/importer.ts`（00:41）、`renderer/logic/importText.ts`（00:42）、
  `renderer/store.ts`（00:45）、`shared/types.ts`（00:40）以及球/渲染线三个文件。
- **可观测的实证**：包内弹窗写的是旧文案 `其余 ${remainingItems} 个重复项将按上方选择处理`（单参 `remainingItemsText`），
  而 `src/renderer/logic/importConflict.ts:239` 已是两参版本、文案为 `还有 ${rest} 个源文件正在检查，若也有重复将按上方选择处理`。

### DEF-19-3（P2 · 主进程守卫 + 产品可见性）换过库目录的老资产，回填**必然**全静默失败且界面无提示

- **现象**：`probeSizes` 的 IPC 层要求 `folder` resolve 后必须在 `settings.libraryDir` 内，越界一律 `return []`（只打 WARN）。
  一旦库目录被改过/搬过，DB 里老资产的 `folder` 就不在新根下 → 回填 `scanned:N, patched:0`，

- **责任面**：主进程 `index.ts:1252` 的守卫 + 渲染层缺"回填失败可见性"。

### DEF-19-4（P3 · 解析器边界）APP 段超 64KB 的 JPEG 永远读不到尺寸

## 22.5 ③ 拖出崩溃防线

用户 0.8.2 的真实崩溃：`fatal:uncaughtException — Failed to load image from path '…\Temp\idbox-drag-card.png'`。真实根因不是"先发后写"，而是**杀软（Defender）对刚落盘的 Temp PNG 的瞬时独占锁** → 主进程 `nativeImage.createFromPath` 读成空图 → Electron native 层对空图直接 throw。

1. 正常：`drag:start {iconKind:"card", iconExists:true, cardBytes:8808}` → `returned {iconKind:"card", elapsedMs:2293}`
2. thumb 被读成空图：`drag:icon-missing {kind:"thumb", reason:"decode-empty"}` → `returned {iconKind:"embedded"}`

**DEF-22-1：`window.modvault.setSettings()` 不通知渲染层 store。**

该 IPC 只写主进程与 `settings.json`，渲染层没有 `settings-changed` 事件，zustand store 不会重渲染。`App.tsx:442-458` 的主题 effect 订阅的是 store 里的 `settings.theme`，因此**通过 IPC 改主题不会改变 `document.documentElement.dataset.theme`**（实测：IPC 写 `theme:'dark'` 后，活实例仍 `themeAttr:"light"`；必须重启实例、由渲染层从 settings 重新读取才生效）。

- 影响面：正常在 UI 里点选主题没问题（UI 路径会更新 store）；任何**外部/脚本/未来新增的"从主进程改设置"**路径都会出现"设置已落盘但界面不变"的分裂状态。
- 建议：加一条 `settings:changed` 广播，或在 store 侧订阅，把"落盘"与"生效"统一到同一事件源。
- 已登记到 `docs/25-待办-用户反馈.md`；取证脚本 `scripts/theme-via-ui.mjs` 保留。

其余全是图标"）。库一旦超过 120 条，第 121 张之后**永远补不上** —— 用户看到的就是"预览图只修了一半"。

修法（`src/renderer/store.ts`）：把单轮逻辑拆成 `runThumbBatch()`（返回本轮真正写成 `ready` 的条数），
`ensureMissingThumbs()` 改成「有进展就接力」，并加三重刹车：

1. **本轮零进展即收手**（缩略图失败通常意味着源图读不了，反复试只会白烧 CPU）；
2. 每轮之间 `setTimeout(16)` 让出主线程，不堵首屏交互；
3. 硬上限 `ENSURE_THUMB_MAX_ROUNDS = 20`（= 2400 张），兜住病态数据；
4. 语义不变：进过队列的 id 都记在 `thumbAttempted`，候选集**单调收缩** → 不可能死循环。

测试（新增 `tests/thumbQueueContinue.test.ts` 4 条，全量 3085 → **3089**）：
300 条同时缺图一次补完（每张恰好一次 IPC）、补完再调 0 次 IPC、全失败只跑一轮（120 次）后收手、
部分成功（150/200）也能正常收尾。

### 客户侧的自验步骤（装机后）

1. 装 0.8.3 → 打开软件，**不要点任何按钮**，等 1–2 分钟；
2. 卡片封面应当自己回来（A）+ 缩略图在后台成批补齐（本次修的接力）；
3. 设置 → 数据与备份 → 「从知末获取封面」如果还有跳过项，汇总会写「跳过 N 条（已有 cover 文件）」——
   那是**正常**，说明它在等启动自愈，不是坏了；
4. 仍然缺图的个例：右键单张「从知末取封面」走 `force` 通道（会绕过跳过规则）；
5. 若有个别卡片始终补不上，导出日志（设置 → 数据与备份 → 导出日志）看
   `cover:folder-resync-missing`（整棵目录不在盘上 = 真漂移，不是字段问题）。

## 23.11 「重装后预览图不回来」的**真根因**（2026-10-28 21:1x，模拟重装实测发现）

§23.10 只补了"大库超过 120 条补不完"的接力，但**没有解释客户看到的现象**。这一节是实测出来的。

### 复现（模拟重装）

1. 用已验收的 profile 副本（4 条资产，缩略图均 ready）；
2. **清空 `userData/thumbs/`**（重装 / 换 userData / 清缓存后的真实状态）；
3. 用 0.8.3 启动 → 观察 30 秒：

```
T+0s   {"cards":4,"withThumb":0,"iconOnly":4}
T+2s   {"cards":4,"withThumb":0,"iconOnly":4}
T+5s   {"cards":4,"withThumb":0,"iconOnly":4}
T+10s  {"cards":4,"withThumb":0,"iconOnly":4}
T+20s  {"cards":4,"withThumb":0,"iconOnly":4}     ← 30 秒一张都不恢复，thumbs 目录仍是 0 个文件
```

**结论：修之前这条链路是断的，客户的反馈是对的。**

### 根因

`logic/recordHygiene.ts` 的 `planThumbPresenceRepair(assets, diskThumbNames)` 开头有一道
"空名单 → 直接返回空计划"的守卫，理由是"一次读盘失败绝不能把全库标成缺图"。

问题是它把**两种完全不同的情况**混成了一种：

| 情况 | 真实含义 | 旧行为 |
|---|---|---|
| `listThumbs` 抛错 | **不知道**盘上有什么 | 不动记录（正确） |
| `listThumbs` 返回 `[]` | **确定**盘上一张都没有（重装/换目录后就是） | 也当成失败 → 不动记录（**错误**） |

于是记录永远停在 `thumbStatus='ready'`（`thumbPath` 指向已不存在的文件），而补齐队列的
候选判据是 `thumbStatus !== 'ready'` → **谁也不负责重生**。卡片就一直只有类型图标。

### 修法

1. 纯函数签名改成 `diskThumbNames: string[] | null`：**`null` = 列不出来（不动）**，
   **`[]` = 真空（全部 ready 活记录进计划）**。安全方向没变 —— 失败仍然不动，
   只是"确定的空"不再被当成失败。
2. 调用方 `store.repairThumbPresence()`：`.catch(() => [])` 改成 `.then(r => r, () => null)`，
   把失败显式表达成 `null`。
3. 顺带修掉一个空的写放大：`logic/thumbRescue.ts` 的"显式偏好"分支现在会在
   「已经挂着偏好那张且 ready」时早退 —— 否则健康库里这类资产每次启动都重写同值 + 写一份快照。

### 修后同场景复测（同一 profile、同样清空 thumbs）

```
T+0s   {"cards":4,"withThumb":4,"iconOnly":0}
T+20s  {"cards":4,"withThumb":4,"iconOnly":0}
userData/thumbs 文件数：0 → 6        ← 后台自己长回来了
日志 fatal/uncaught：0
```

测试：`tests/recordHygiene.test.ts` 的空名单用例拆成两条（`null` 不动 / `[]` 全部命中），
新增 store 级"重装后整库置 none"用例；`tests/thumbQueueContinue.test.ts` 4 条；
全量 3085 → **3091**。
