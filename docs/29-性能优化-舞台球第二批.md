## 1. 候选逐条论证（D / E / F / G）

### 方案 D · 跨资产贴图复用的 **Texture LRU**（本轮选）

**机制**

1. 新增 `logic/texturePool.ts`：按 `WebGLRenderer` 分组的 `TexturePool<Texture>`（纯逻辑、不 import
   three，可在 node 单测）。key = `url|maxPx|srgb|linear`。
   - **为什么要 `colorSpace` 进 key**：`alpha` 槽位与 `albedo` 是**同一个 URL 的两个 Texture**
     （见 `applyMaps` 的 alpha 收集）——一个 sRGB、一个线性。同 key 会串味成「一半灰变几乎全透」
     （`MaterialBall.tsx` 的 `loadMap` 注释里记着这个坑）。
   - **为什么不跨 renderer 共享**：`Texture` 绑定具体 WebGL 上下文，`forceContextLoss` 之后
     再上传会失败（`textureBitmapCache.ts` 文件头已经论证过一次，这里沿用同一纪律）。
     场景在舞台是**整场会话常驻**，所以「按 renderer」= 整场会话复用，命中率就是用户来回切的命中率。
2. `applyMaps` 换资产时**不再无条件 `dispose`**：池化贴图只 `release`（引用计数 -1），
   自建贴图（合成法线、TextureLoader 兜底）照旧 `dispose`。
3. 命中路径**连 `fetch` 都不做**（关键）：`loadTexture` 先查池，命中直接返回旧 `Texture`。

**预期收益（引用 docs/26 实测，不新编数字）**

| 场景 | 现在（A/B/D-位图已落地） | 本轮之后 |
|---|---|---|
| 8K 单图**首次**切换 | 437ms（fetch + 唯一一次解码，docs/26 §2.2a）+ ~1.5ms 上传 | 不变（首次没有可复用的） |
| 8K 单图**切回来**（hover 预热过） | fetch 44ms + 位图命中 0ms + 上传 ~1.5ms + 逐槽位「重编译+上传+渲一帧」8ms 级 | **≈0ms**（只剩 `material.needsUpdate` 的程序查表，program 已在 `WebGLPrograms` 缓存里） |
| 4K 五槽 PBR 预设**切回来** | fetch 24+22+18+13+4 = **81ms** + 全量重传 **23.7ms**（docs/26 §2.2c） | **≈0ms** |
| 显存 | 同时只有 1 套在册 | 上限 12 张 / 48MB（1024² RGBA = 4MB/张，docs/26 §2.1/§2.2c 同口径） |

> 这一条正是 docs/26 §4-D 的原话预期：「A↔B 来回切 **960ms → 0**；hover 预热过再双击 → 0 成本
> （现在预热完再切回另一张，第一张就作废了）」。位图缓存只做到「不重解码」，本次补上「不重上传」。

**风险**

- 显存：硬上限 12 条 / 48MB；逐出**跳过引用计数 > 0 的条目**（正在材质上的贴图绝不能被逐出）。
- 泄漏：`BallScene.dispose()` 必须 `pool.disposeAll()`（renderer 都要销毁了，池里的贴图必须一起放）。
- 正确性：`repeat` / `anisotropy` / `colorSpace` 在每次取用时重新写一遍，不依赖创建时的状态
  （形态 / UV 倍率 / 动效档位都可能中途变）。

**改动点**：`src/renderer/logic/texturePool.ts`（新增）、`MaterialBall.tsx` 的 `loadTexture` /
`loadMap` / `applyMaps` / `applyRepeat` / `applyMotionProfile` / `dispose`。

**验收判据**

1. 同一资产连续 `preview(a) → preview(b) → preview(a)`：第二次进入 a 时控制台**没有**
   `贴图降采样` / `fetch 失败` 日志，只有 `贴图池命中`；且 `isReady()` 立刻为真。
2. 显存不随切换次数增长：池 `stats().entries ≤ 12`、`bytes ≤ 48MB`。
3. `tests/texturePool.test.ts` 全绿（LRU 顺序 / 引用计数保护 / disposeAll）。

### 方案 E · 取消在途加载（本轮选）

**机制**

1. `applyMaps` 持有 `AbortController`；新一代进来先 `abort()` 上一代。
2. `signal` 一路传到 `fetch(url, { signal })`，并在**解码入口**再判一次
   （`createBitmap` 里 `signal.aborted` → 抛 `AbortError`）：
   解码本身不可中断，但**还没开始**的必须直接判掉——扫卡时排队的那些就是靠这一行不再启动。
3. `AbortError` 与「过期代次」一律**静默返回**（docs/26 §4-E：不要打成 warn 刷日志）。

**预期收益（docs/26 §3③ 原文的量化）**

- 扫过 10 张材质卡：从「10 次全解码排队」变成「最多当前 1 批在跑 + 其余在 fetch 阶段就退出」。
  对用户可感知的改善在**双击前的等待时间**（不再排在队尾）。
- 与 D 叠加后还有一个额外收益：**hover 预热的价值不会被下一次 hover 冲掉**——上一代的加载被取消，
  解码线程不再被 10 张废图占满，最后一次 hover 的资产总是最先就绪。

**风险**：低。`AbortError` 必须静默；`TextureLoader` 兜底路径**不支持取消**（无 signal 参数），
只在进入前判一次 aborted（不假装能中断它）。

**改动点**：`MaterialBall.tsx` 的 `applyMaps`（建/换 controller）、`loadTexture`（signal + 静默）、
`loadMap`（signal 透传 + 取消判据）、`dispose`（abort）。

**验收判据**

1. 快速 `preview(a) → preview(b)`：a 的加载不再把 b 挤到队尾；控制台**没有** `AbortError` 的 warn。
2. 卸载（Esc 关闭舞台）时不留下在途 fetch。
3. 与 D 同时生效：`preview(a) → preview(b) → preview(a)` 的第三次直接池命中。

### 方案 F · ao/disp 挪到 idle + 并发上限 3（**本轮不选**）

**机制**：albedo/normal/roughness 先上，`ao`/`displacement` 走 `requestIdleCallback`；并行解码限 3。

**数据**：docs/26 §2.2c 实测「5 槽全挂 = 42ms，program 9 个」；§4-F 估 42 → 10–20ms；
并行峰值内存 320MB → 192MB。

**为什么这一轮不做**

1. **收益比 D/E 小一个量级**：42ms 是**一次性**尖峰，且 `MaterialStage` 的就绪门控（`OPEN_READY_MS`
   400ms，实测放行点在 albedo 落定时）已经把这 42ms 藏进「opacity:0 的预热帧」里；
   而 D 省的是**每次切回** 81ms(fetch) + 23.7ms(上传)，E 省的是**扫卡时几百毫秒到数秒的排队**。
2. **风险不对称**：`applyMaps` 返回的 Promise 有硬语义——「等全部槽位才 resolve」（离屏封面/缩略图
   依赖它，`renderBallToPng` 是 `await applyMaps()` 之后立刻 `renderOnce()`）。把 ao/disp 挪到
   `requestIdleCallback` 会让这条 Promise 的 resolve 时机变成「空闲回调什么时候来」，
   在隐藏窗口 / 后台标签下 rIC 可能被推到秒级 → **封面渲染可能缺图或长时间挂起**。
   要安全就得给 rIC 加 `timeout` 兜底 + 失败重试，属于「中改 + 需要独立回归」。
3. docs/26 §6 的落地顺序也把 F 放在最后一步（第 6 位）。

**结论**：留作下一批（见 §5）。

### 方案 G · hover 预热撤回 + 无 albedo 保持挂载（**本轮不选，因为一半已经做完了**）

**现状复核（重要，避免重复劳动）**


  **只增不清**）——所以换到「没有 albedo」的资产时组件不卸载、`stageMounted` 不抖动。
- **「hover 预热撤回」没做，而且不在我的文件边界内**：
  `AssetGrid.tsx:2028-2036` 的 `onPointerLeave` 只 `cancelPrewarm(hoverTimer)`，
  **已经发给 `stageController.preview(a.id)` 的预热撤不回来**。

**为什么不在这一批硬做**：G 的用户价值（「快速划过一排卡时零浪费解码」）与 E 高度重叠，
而 E 可以在我的边界内完整落地；G 的最后一行必须由 `AssetGrid` 的 owner 改。

## 2. 决策：**D + E**

| 判据 | D | E | F | G |
|---|---|---|---|---|
| 用户可感知收益（按 docs/26 实测） | 切回 **81ms + 23.7ms → ≈0**；双击预热过的资产 **0ms** | 扫卡时解码不再排队（**几百 ms~数秒**） | 首帧 **42 → 10–20ms**（一次性） | 划过卡不浪费解码 + 不重建上下文（**已做**） |
| 与已完成工作是否重复 | 否（位图层做了，GPU 层没做） | 否 | 否 | **是（一半）** |
| 是否在我的文件边界内 | 是 | 是 | 是 | **否**（要改 `AssetGrid.tsx:2028`） |
| 风险 | 低-中（显存上限 + 引用计数） | 低 | 中（Promise 语义） | — |
| docs/26 §6 顺位 | 第 4 | 第 3 | 第 6 | 第 3 |

**D 的额外理由（本轮最重要的一条）**：舞台的 `BallScene` 与组件**同生共死**（`deps: []`，
`MaterialBall.tsx:1522`），整场会话只有一个 renderer。也就是说「按 renderer 分组的贴图池」
天然就是「整场会话的贴图池」，命中率等于用户来回切的命中率——这是 D 在本项目里成立的前提，
而在「每次换资产都重建 renderer」的旧结构下 D 是无效的。
