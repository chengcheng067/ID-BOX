## TODO-2 · 封面抓取失败：瞬时超时没有重试，且日志看不出是哪一步

- **状态**：已定位，等用户决定"现在改 / 攒着一起改"。
- **记录时间**：2026-10-22 19:15（用户导出日志 `idbox-logs-20261022-1913.zip`）

### 用户原话

> 「然后再看一下我这个封面获取失败的日志，看一下我们到底是哪一个环节出问题了。」

### 日志事实（`app-2026-10-22.log`，UTC，+8 为本地时间）

```
11:12:48.027Z [main] [WARN] zhimo:cover-failed {"id":"1168792999","reason":"timeout"}
11:13:03.040Z [main] [WARN] zhimo:cover-failed {"id":"1168792999","reason":"timeout"}
```

- 两条**间隔恰好 15s** → 与 `DEFAULT_PAGE_TIMEOUT_MS = 15_000` 一致 → 是**点击 → 等 15s 超时 → 再点 → 又 15s 超时**；
- 时长落在「详情页超时」而不是「图片超时（20s）」，所以卡在**第一步取 HTML**，连图都没开始下；
- 同期日志无导入活动、无异常栈 → 不是磁盘/权限问题。

### 排除项（都在同一台机器上实测）

| 假设 | 结论 |
|---|---|
| 这个 ID 失效 / 软 404 | ❌ 页面 200、43,531 字节、正常 |
| 被 UA 拦（`Mozilla/5.0 (IDBOX cover fetcher)`） | ❌ 该 UA 与 Chrome UA 结果完全一致（200 / 0.76–0.89s） |
| 我方网络整体不通 | ❌ 在**项目内 Electron 33.4.11 / Node 20.18.3 运行时**实跑：详情页 **709ms**、图片 **65ms**（`image6` 的 `style/list`） |
| 系统代理 | ❌ `HTTPS_PROXY` 未设置 |

→ 结论：**当时是瞬时的网络/边缘节点抖动**（服务端半开连接或短暂限流都符合"连两次都卡满 15s、几分钟后完全正常"），
而实现里**一次失败即放弃、没有任何重试**，所以一次抖动就变成用户可见的"获取失败"。

### 根因（代码层）

`src/main/zhimoCover.ts`：`fetchDetailHtml` / `fetchImageBytes` 都是**单次尝试**，
`catch` 直接把 `TimeoutError` 映射成 `reason='timeout'` 返回，全模块 `grep retry` 零命中。

### 期望（修法）

1. **有界重试**，只对**瞬时类**失败：
   - 重试条件：`reason ∈ {timeout, network}`
   - **绝不重试**：`no-id` / `not-found` / `no-image` / `bad-url` / `bad-image` / `too-small` / `write-failed`
   - 参数：初次 + **1 次重试**，退避 **800ms**；重试同样受超时约束
2. **超时预算收敛**（否则重试让最坏耗时过长）：
   - `pageTimeoutMs` 15s → **10s**；`imageTimeoutMs` 20s → **15s**
   - 最坏单资产 ≈ 21s，且只在失败路径上发生
3. **日志补足定位信息**（这次就是缺它才只能靠猜）：
   ```
   zhimo:cover-failed { id, reason, step: 'page' | 'image', attempt: 1 | 2, elapsedMs }
   ```
   `step` 必须区分"取页面"与"取图片"——否则下次仍然只能从时长反推。
4. **手动按钮文案**：`timeout`/`network` 在重试后仍失败时，文案明确写「网络超时，可稍后重试」，与 `not-found`（ID 不存在）区分。

### 验收

- 单测：让 fetcher 第 1 次抛 `TimeoutError`、第 2 次成功 → 结果 `ok:true` 且 `fetcher` 被调用 **2 次**；两次都超时 → `reason='timeout'` 且调用 2 次（不是无限重）。
- 单测：`not-found` 路径 **只调用 1 次**（证明只对瞬时类重试）。
- 单测：日志上下文字段 `step` / `attempt` / `elapsedMs` 存在（handler 层用 spy）。
- 真机：拔网线 3 秒再插（或断点式限流）点手动按钮 → 应自动重试一次并成功，不再一失败就报错。

### 关联

- 与 `docs/24` §4.4 失败语义表冲突处：`timeout` 语义不变（仍是失败原因之一），但**新增"重试后仍失败"才上报**这一层。

## TODO-4 · 自定义渲染弹窗：首帧球的质感是"默认"，不是滑块值（P1 缺陷）

- **状态**：已定位到范围，等修。
- **记录时间**：2026-10-22 19:21
- **用户原话**：
> 「现在点自定义渲染的时候，第一下出来的球，它的光泽度是一个默认的显示，但实际上不是我们滑块的预期。我们滑块的预期是点了保存以后的这个球的质感，所以这部分应该是一个 bug。」

### 现象（用户截图确认）

- 弹窗打开后**首帧球偏亮/偏反光**（像默认材质）；
- 滑块已经显示 `反光强度 ×1.7 / 凹凸强度 ×1.6 / UV ×2.5`（不是默认 1.0）；
- 点「保存·设为封面」后再看 → 质感变成滑块预期的那种（偏哑光）。

### 已核实的调用链（不是猜）

| 位置 | 事实 |
|---|---|
| `CustomRenderDialog.tsx:55` | `scales` 初值 = `resolveRenderParams(asset)` → 滑块绑定 `scales`，**所以滑块显示的是存过的 1.7/1.6/2.5，参数本身没丢** |
| `CustomRenderDialog.tsx:271` | 传给球的是 `params={scales}` —— 入口参数正确 |
| `MaterialBall.tsx:1014` | 内部 state 初值 `params ?? DEFAULT_PARAM_SCALES` —— 也正确 |
| `MaterialBall.tsx:1045-1048` | 受控同步 effect，deps 为 `params?.roughness / bump / uv` |
| `MaterialBall.tsx:509` | 场景构造时调 `setParamScales(opts.params ?? DEFAULT)` |
| `MaterialBall.tsx:557-576` | `setParamScales` 内部：`roughness = effectiveRoughness(hasRoughnessMap, **this.baseRoughness**, r)` |
| `MaterialBall.tsx:614` | 只在**某一条**贴图应用分支里会在"基准复位"后重算：`this.setParamScales(this.lastScales)` |
| `CustomRenderDialog.tsx:191` | 「保存」走 `renderBallToJpeg(...)`，**离线新建场景并直接带入 params**（`MaterialBall.tsx:1357`）→ 所以保存出来的图是对的 |

### 两个待验证假设（给动手的人，按这个顺序验）

**H1（最可能）**：构造时 `this.baseRoughness` 还没被贴图流程赋值（仍是默认基准），`effectiveRoughness()` 于是算出一个"默认光泽"，而正常的 `applyMaps` 路径（单图贴图资产）**没有走到 614 行那次重算** → 首帧保持错误值；一拖动滑块（params 变）→ effect 重新 `setParamScales`，此时 baseRoughness 已就绪 → 正确。
→ 判据：在 `setParamScales` 里打点，对比构造时与拖动后的 `baseRoughness` 是否不同；若不同即坐实。

**H2**：`params` 对象的引用在首帧为 `undefined`（`Suspense` 懒加载挂载顺序），首帧用 DEFAULT，之后 effect 因 deps 未变（都是同一组值）**不触发**重同步。
→ 判据：`MaterialBall` 里记录首次 render 收到的 `params` 是否为 undefined。

### 修法方向

无论 H1 还是 H2，**收敛点都是"材质就绪后必须无条件用当前 scales 再 apply 一次"**：

1. `applyMaps()` 结束时（所有分支，不只是"基准复位"那支）统一 `this.setParamScales(this.lastScales)`；
2. `setParamScales` 里若 `baseRoughness` 尚未就绪，**标记 dirty**，等 `baseRoughness` 赋值时补算一次（不要依赖调用方时序）；
3. 受控同步 effect 的 deps 增加"材质就绪版本号"（`mapsReady` 之类），保证就绪后再同步一次。

### 验收

- 单测（纯逻辑层，不依赖 WebGL）：`effectiveRoughness` 在 `baseRoughness` 就绪前后分别求值，断言最终值等于「按滑块值算出的值」；
- 单测：`setParamScales` 在 `baseRoughness` 未就绪时被调用 → 记录 dirty；注入 baseRoughness 后 → 自动重算，`material.roughness` 与期望一致；
- **真机**：对一个存过参数的资产（如 `无缝黑色木纹ID_1151853396`，×1.7/×1.6/×2.5）打开「自定义渲染」→ **首帧**的球就应与保存后的封面一致；再点保存 → 封面与首帧一致（不再"跳一下"）。

## TODO-9 · 材质球切换卡顿（性能）—— 已量化诊断，按 A/B 先行

- **状态**：诊断完成（`docs/26-性能诊断-材质球切换.md`）；**用户 2026-10-22 19:38 拍板：全部攒批，与其余 8 条一起改、一次出包**。
- **记录时间**：2026-10-22 19:36
- **用户原话**：
> 「它本身的这个材质的体积是不小的，所以它在每一次换材质点击的时候、双击的时候，实际上都会让咱们这个整体有一点卡……包括下面的材质预设，因为它本身就是有 PBR 材质的，那咱的渲染器其实每次在贴这些 PBR 的时候，实时渲染它都是压力很大的……看一下我们的性能能不能再进一步地做优化。」

### 结论先行（与直觉相反）

**瓶颈不在 GPU，在 CPU 解码，而且一大半是白解一遍。** 实测：GPU 稳态帧 **0.2ms**、5 张 1024 贴图上传 + shader 重编译共 **42ms**；而用户框的「原木色原木清晰纹理」是 **8192×8192**（13.1MB 文件 / 解码后 **256MB**），一次切换 **~960ms** 全花在解码上。

三条根因（详见 `docs/26` §2）：

| # | 根因 | 证据 | 代价 |
|---|---|---|---|
| 1 | **同一张图解码两次**：`MaterialBall.tsx:365` 先全尺寸 `createImageBitmap`（**482ms**）只为拿宽高，`:371` 再带 resize 解一遍（**434ms**） | 行号 | ~960ms/次 + 瞬时 256MB |
| 2 | **法线合成读回踩同步 GPU 回读**：`MaterialBall.tsx:299` 的 `getContext('2d')` 没加 `willReadFrequently`，`:302` 的 `getImageData` 实测 **30.7ms** 同步阻塞；两次长任务 87/93ms 来自这里 | 行号 | 44ms 主线程/次 |
| 3 | **无跨资产缓存 + 在途加载不取消**：`:599` 进来就 dispose 旧贴图，`:683` 只在解码完成后才判 gen 丢弃 → 扫过一排卡 = 一排全尺寸解码排队 | 行号 | 排队型卡顿（体感"点一下就卡"） |

⚠️ **两个必须记住的反直觉事实**：
- **文件 MB ≠ 解码成本**：8.2MB 的红砖只有 2048²（87ms），13.1MB 的原木是 8192²（482ms）。按体积判断会判错方向。
- **"把贴图降到 512" 无效**：8192² 解到 512 仍要 **423ms**（解到 1024 是 437ms）。Chromium 对 JPEG **没走 scaled decode**，解码下限 ~410ms，**渲染进程侧再怎么调参都压不下去**。

### 实施顺序

**第一批（立刻做，合计 <15 行，拿走一半以上体感卡顿）**
- **A**：`loadTexture` 不再先全解 —— 用项目里现成的 `src/shared/imageSize.ts` 的 `imageSizeOf()` 读文件头拿宽高，只做**一次**带 `resizeWidth/Height` 的 `createImageBitmap`。实测 原木 1014ms → **~490ms**、红砖 202 → **84ms**。
- **B**：`normalFromBitmap` 的 canvas 加 `willReadFrequently: true` + 尺寸 384 → 256。实测 `getImageData` **30.7ms → 0.4ms**，两次长任务消失。

**第二批（根治 8K，中改，独立任务）**
- **C**：主进程用 `nativeImage` 预生成 **1024 预览图**并落盘缓存（实测 8K 一次性 443ms、产出 161KB，**完全不占 UI 线程**）。之后渲染进程只拿 1024 图 → 原木切换到 **~36ms**；顺带解决老 GPU `MAX_TEXTURE_SIZE=4096/8192` 时上传失败。缓存键与清理口径见 `docs/26` §4 的风险点。
- **D**：贴图 LRU 缓存（按 URL + 目标尺寸做 key）→ **A↔B 来回切 0ms**（正是用户描述的操作）。

**第三批（顺带修的相邻问题）**

### 样本实测（**这一条决定了方案，不能跳过**）

| 文件 | 体积 | 分辨率 |
|---|---|---|

**关键事实**：
1. **16384 正好是很多显卡 `MAX_TEXTURE_SIZE` 的上限**（本机 RTX 4080 SUPER 也是 16384）→ 直接上传等于踩线，PMREM 在 16K 上必然爆或卡死。

### 决策依据（值得留档的原因）

用户问的是「调焦距让 HDR 更广角，还是用更宽的比例预览」。结论：**焦距是主旋钮、比例是辅旋钮**，
因为 `PerspectiveCamera.fov` 是**垂直**方向，水平视角由「垂直 × 窗口比例」共同决定——
原来看不广，根因是垂直只有 40°，不是窗口不够宽。

| 垂直 FOV | 水平视角(比例 1.885) | 横向覆盖 | 纵向覆盖 | 边缘拉伸 `1/cos(fov/2)` | 等效焦距 |
|---|---|---|---|---|---|
| 40（旧） | 63.5°(比例1.70) | 17.6% | 22% | 1.06× | ≈29mm |
| **62（新）** | **97.1°** | **27.0%** | **34.4%** | **1.17×** | **≈16mm** |
| 90 | 119.1° | 33.1% | 50% | 1.41× | ≈11mm |

62° 的依据：等距柱状投影的边缘横向拉伸 1.17×，与真实超广角镜头同级；到 90° 就是 1.41×，极点挤压会露馅。
**HDR 源文件固定 2:1**（360×180），改窗口比例只是改取景框，不会让 HDR 本身更广——这点已在回复里讲清。

### ⚠️ 顺带纠正的历史错误

旧公式 `r = 占比 · d · tan(fov/2)` 配 `占比 = 0.2`，注释自称"投影高度占视高 20%"，
实际算出来是**半径占半屏高 20%** ⇒ 那颗球的**直径是视高的 40%**（在 1120×658 下约 264px）。
两颗球并排不能再沿用，改为按**直径占视高**定义，并用球体轮廓的精确关系反算：
`r = d · sin(atan(占比 × tan(fov/2)))`（近似式目前差 ~1%，FOV 越大偏差越大）。

## BUG-1 · HDR 预览「拍照」后主界面不刷新，重启才变

- **用户原话**：「HDR 预览以后拍照以后，在主界面不会立刻刷新，只有重启软件才会刷新，应该是个 bug。」
- **根因（缓存身份不变，不是没写盘）**：`ensureThumb` 的缓存名 = `salt` + id，而
  `salt = thumbSalt(coverAbs)` **只由封面路径算**。拍照每次写回同一个 `<资产名>.cover.png`，
  路径不变 → salt 不变 → 缓存文件名一字不差 → `vault://thumb/<同名>` 这个 URL 不变 →
  Chromium 直接命中缓存，连协议 handler 都不进。
  ⚠️ 关键事实：**磁盘上的缩略图字节其实早就是新的**，坏的只是 URL 身份。所以"重启才刷新"完全吻合。
- **修法**：salt 改由**内容身份**算出 —— `thumbFileSalt(coverAbs, st)` = `thumbSalt(路径:mtime:size)`，
  复用 `ensureThumb` 里本来就有那次 `fs.stat`（**零额外磁盘 IO**）。文件一改 → 名字换 → URL 换 → 必读新字节。
- **同族问题一起修**：详情面板大图走 `vault://asset/<rel>`（同样是"路径不变内容变"），
  改成 `vaultUrl(rel, asset.updatedAt)` 追加 `?v=`；`vaultUrl` 的新参数是**可选**的，
  不传时输出与旧实现逐字符一致，没有改全局缓存策略。
- **确定性（RA3 的前提）**：`regenThumbSweep` 会连调两次 `ensureThumb`（先生成 →
  通配删 → 再补回），两次必须同名。文件未被改写时 `mtime/size` 是稳定常量 → 成立（有测试）。
- **测试**：`tests/thumbSalt.test.ts` 15 例，核心是「同路径、只改 mtime、字节数一致 → 必须换名」。
- **残留风险（诚实）**：FAT/exFAT 等 mtime 只有 2 秒粒度的盘，若新图**恰好字节数相同**又落在同一 2 秒窗口
  → 仍会同名。彻底解法是把内容 sha1 掺进 salt（多一次 IO），本轮不做。

## 补记 · 第 1 轮真机验收后修掉的两条（01:06 冻结）

**DEF-19-1（P1）超时后弹窗变僵尸**：主进程 120s 超时是**单方面**结束（内部 `resolve(null)` = 全跳过），
从不通知渲染层 → `conflictAsk` 永久残留、弹窗关不掉，且用户之后的每次点击都被当作**过期答复**静默丢弃
（主进程回 `phase:'stale'`，界面毫无反馈）。修法（两条都要，缺一条就复发）：
1. **权威路径**：新增 `IPC.importConflictExpired` 下行事件，主进程在超时分支 `send` 后 `resolve(null)`；
   渲染层 `clearExpiredAsk(requestId)` **仅当 requestId 与当前相等**才清（迟到的作废不能关掉下一次询问）。
2. **兜底**：渲染层 121s 看门狗走同一个 `clearExpiredAsk`（窗口被遮挡时 `setTimeout` 会被 Chromium
   节流到约 1 分钟一次，所以看门狗只能兜底、不能当主路径）。
3. **点击先关窗**：`answerConflict` 先同步 `set({conflictAsk:null})` 再 `await` IPC——
   "能不能关掉"不该取决于一次往返。
4. **提示不吞汇总**：超时提示走 `enqueueNotice()`（与「已跳过 N 个」同队列）。
   真实到达顺序由主进程钉死：`send(expired)` 在 `resolve(null)` 之前 → **超时提示先、4.5s 后批次汇总**；
   **两条都必须出现**，不为了顺序牺牲"一定说出口"（没有做"等 batchDone 再提示"的延后逻辑）。

**DEF-19-4（P3）超大 JPEG 尺寸永远读不到**：某张 JPEG 的 `SOF0` 在 678557 字节处（前面是大段 ICC/APP2），
而读头只有 64KB → 该文件对分辨率筛选**永久为假**（库内 1/117）。修法：`readHeadForSize()` 分级读头——
先 64KB，解析失败**且**是 jpg/jpeg 才升到 1MB 重试一次，每文件最多两次；PNG / hdr / exr 不升级。
`probeSizes` 与 `importer.fillImageSizes` **共用**同一实现，避免"导入时读不到、回填时读得到"。
实测该文件：修复前 null → 修复后 **1260×1255**；代价是 117 张里只 1 张触发升级（≈1MB/库）。

1. **不新增 PBR 槽位、不做文件选择器**：灰度源就是当前已加载的 **albedo 本身**。

## 三、连带缺陷（比"按 Esc 没反应"更该修）

`App.tsx:437` 全局 Esc 的**尾部是无条件执行**的：

```

```

前面只对 `hdrPreviewAssetId` / `pendingDelete` / `folderViewAssetId` 做了 `return` 让路，

- 打开「批量重命名」按 Esc → 选中项被清空（右侧面板卸载），但 `renameIds` 还在，

  看着像能用，实际附带了"清空选择"的副作用（重开还得重新选）。

→ 修 `Modal` 内置 Esc 的同时，必须给 App 全局 Esc 补让路判据，否则一次按键关两层。
判据建议按**栈顶优先**写死顺序（后开的先吃），并抽出可单测的纯函数，不在 JSX 里堆 if。

1. `Modal.tsx` 加 `useEffect`：`window.addEventListener('keydown', onKey, true)`，

2. 新增可选 prop `dismissOnEsc?: boolean`（默认 `true`），与既有 `dismissOnScrim` 对齐。

   关掉整个设置弹窗。实际做法：给该输入框打 `data-esc-own` 标记，`Modal` 在捕获阶段见到

2. **`CategoryPicker:122` 不是「关弹窗」**，而是**收起内部分类下拉**。直接删会让

  **只有栈顶那层 stop + 消费**，非栈顶原样放行。
- 收益：叠层弹窗（导入重复处置 `z-[60]` 压在设置上）Esc 先答上面那个；

3. **会不会挡住拖入落点**：居中位置正好在中栏中央，用户拖文件进来时这条弹窗会出现在 drop 区域正中。需要确认"拖入瞬间弹窗出现"是否会挡住后续拖拽（同一批多文件）——如果会，考虑"导入进行中偏下、结束后才居中"或整体下移到 `bottom-24`。
4. **z 序**：现在是 `z-30`；Modal 系更高、舞台球 `zIndex: 60`（T-ZSTACK 待修）。居中后与舞台球/弹窗的重叠概率上升，必须核一遍层级（**不要**顺手改 `MaterialStage` 的 zIndex，那是独立待办）。
5. **触发范围**：用户原话是「有素材的拖入」。从"选择压缩包导入"、右键导入、监控目录导入进来的条目要不要也居中？记录为待确认（默认：所有导入条目统一，避免两处位置）。

**验收口径**
- 多条（≥3）同时在场时向上堆叠、不越出视口中线；
- 悬停暂停 / 移开续计仍正确（回归 `ImportQueue` 既有语义）；

## DEF-22-1（0.8.3 真机取证，未修）· `setSettings()` IPC 不通知渲染层 store

- **现象**：通过 `window.modvault.setSettings({theme:'dark'})` 改主题后，`settings.json` 已落盘为 `dark`，但活实例的 `document.documentElement.dataset.theme` 仍是 `light` —— 界面不变。必须重启实例（渲染层从 settings 重新读取）才生效。
- **根因**：该 IPC 只写主进程与 `settings.json`，渲染层**没有 `settings-changed` 事件**，zustand store 不重渲染；`App.tsx:442-458` 的主题 effect 订阅的是 store 里的 `settings.theme`，两者不是同一事件源。
- **影响面**：正常在 UI 里点选主题没问题（UI 路径会更新 store，所以真机目视必须走真实点击）。风险在于任何**外部/脚本/未来新增的"从主进程改设置"**路径都会出现"设置已落盘但界面不变"的分裂状态。
- **建议**：加一条 `settings:changed` 广播，或在 store 侧订阅，把"落盘"与"生效"统一到同一事件源。
- 完整验收报告：`docs/08-测试报告.md` §22。取证脚本 `qa-083-tmp/scripts/theme-via-ui.mjs` 保留。

现象：① 重装后部分模型卡片缺封面，但资产文件夹根层**明明有** `*.cover.jpg`；② 设置页「一键重扫 · 从知末获取封面」点了没效果（汇总 total=3 ok=0 failed=3）；③ 手动单个「从知末取封面」能更新。

### 根因（证据链完整）

1. **他的重扫发生在 0.8.1**（日志 07:17 appVersion=0.8.1，07:21 才升 0.8.2）。0.8.1 的 `pickCover` **根本不认识 `.cover.jpg`**（`isCoverAssetImage` 是 0.8.2 新增）→ 重扫后索引的 `cover` 字段没有指向盘上的 cover 图 → 卡片缺图。
2. **「一键补抓」按设计跳过这类资产**：候选规则④（`zhimoCover.ts:158` `hasCoverAssetFile`）= 索引文件清单里已有 `<x>.cover.(jpg|png)` 就**一律不重抓**。这些资产盘上有 cover.jpg（walkFiles 会收进 files），所以补抓永远不碰它们 → 「点了一键没反应」。
3. **手动单个能成**：手动路径走 `force`（`pickZhimoCoverTargets` force:true 绕过过滤③④）→ 从知末重抓落盘成功。
4. **缺的一环**：0.8.2 没有一条「升级后用盘上已有 cover 文件自愈索引封面」的通道。rescan 合并时 `cover` 默认取磁盘扫描值（`store.ts:3517`，manual/zhimo 才 sticky 保留），**跑一次完整「重新扫描库」其实能自愈**——但用户不会知道要这么做，且补抓按钮给了他「点了没用」的体验。

### 修法方向（待拍板，未实施）

- A（推荐）：init/启动自愈——发现 `coverSource` 非 manual/zhimo 且 `files` 根层有 cover 文件而 `cover` 未指向它时，原地改指 + 重生缩略图（幂等，一次全库扫一遍）。
- B（配合）：补抓汇总文案区分「跳过 N 条（已有 cover 文件，建议重新扫描库）」，别让用户以为按钮坏了。

2. **知末 404**：ID `1102622219` / `1120403243` / `1116806460` 详情页稳定 `not-found`（step=page，100~400ms）——这些 ID 在知末可能已下架/失效，属数据侧，不一定是代码 bug，但补抓汇总把 failed=3 全算在头上会误导用户。
